# DEPLOYMENT.md missing sync_session rate-limit zone causes nginx to reject config, silently leaving /sync/session un-rate-limited

**Status:** DONE
**Bug ID:** [[SEC-000008]]
**Severity:** Medium

## Location

- `docs/DEPLOYMENT.md`, lines 62–65 — operator setup snippet for nginx rate-limiting zones
- `nginx/sync-location.conf.template`, lines 2–4 (comment) and line 20 (`limit_req zone=sync_session`) — requires three zones but docs only declare two
- Cross-reference: [[SEC-000003]] added `sync_session` zone to the template but did not update `DEPLOYMENT.md`

## Description

`nginx/sync-location.conf.template` (the file the CD pipeline installs on the server) references three `limit_req_zone` names:

```
sync_challenge  — used at line 7 (location /sync/challenge)
sync_session    — used at line 20 (location = /sync/session)
sync_write      — used at line 13 (location ~ "^/sync/[a-f0-9]{64}$")
```

However, `docs/DEPLOYMENT.md` lines 62–65 instructs the operator to declare only **two** zones in the nginx http block:

```nginx
limit_req_zone $binary_remote_addr zone=sync_challenge:10m rate=5r/m;
limit_req_zone $binary_remote_addr zone=sync_write:10m rate=30r/m;
```

The `sync_session` zone is absent from the operator setup instructions.

**Consequence:**

When an operator follows `DEPLOYMENT.md` exactly:

1. They add only two zones to their nginx http block.
2. CD deploys `sync-location.conf.template` (rendered), which contains `limit_req zone=sync_session`.
3. `sudo nginx -s reload` fails with: `nginx: [emerg] limit_req_zone "sync_session" is not found in /etc/nginx/...`
4. nginx does not reload. The previously running nginx config (from before [[SEC-000003]] was applied) stays active.
5. The old config has no dedicated `/sync/session` location block and no rate limiting on that endpoint — it falls through to the unprotected catch-all `location /sync/`.
6. **Result: the rate-limiting fix from [[SEC-000003]] is silently bypassed.** The `/sync/session` endpoint accepts unlimited requests per second.

**Alternatively**, if the operator is setting up for the first time (no previous config):

- nginx refuses to load the new location file entirely.
- The operator sees a cryptic error and likely either removes the `limit_req` line (disabling the rate limit) or leaves the service undeployed.

**Attack enabled:**

An attacker can POST to `/sync/session` at an unlimited rate, enabling:
1. **DoS via session endpoint flooding** — each request triggers JSON parsing, nonce format validation, and a Redis `GETDEL` round-trip.
2. **Nonce exhaustion via rapid replays** — although nonces are single-use (GETDEL), an attacker can cycle through harvested nonces faster than rate limiting would otherwise permit, amplifying any nonce-collection strategy.

**Root cause:** [[SEC-000003]] was fixed by updating `nginx/sync-location.conf.template` (and its in-file comment) but the operator-facing `docs/DEPLOYMENT.md` setup snippet was not updated to include the third zone declaration. There is no automated test that cross-checks the zones used in the template against the zones documented for manual setup.

## Validation

**CONFIRMED — genuine, exploitable security issue.**

**Reachability:** The vulnerability is directly reachable. An operator following `docs/DEPLOYMENT.md` step-by-step will declare only two `limit_req_zone` entries (`sync_challenge`, `sync_write`). The rendered nginx config from the CD pipeline references a third zone (`sync_session`) that has no corresponding declaration. nginx hard-fails on an undeclared zone reference — it does not silently ignore it or fall back to a global zone. This is confirmed by nginx behaviour: `[emerg] limit_req_zone "sync_session" is not found` is a fatal startup/reload error.

**Does the template self-document its requirements?** The template does include a comment (lines 1–4) listing all three zones. However, the template comment is not sufficient: `DEPLOYMENT.md` is the authoritative operator setup guide, explicitly described as the document covering "the one-time server setup". An operator following DEPLOYMENT.md's step-by-step instructions (lines 58–65) will copy and paste exactly two `limit_req_zone` lines. The comment in the template is a maintenance hint for developers editing the template, not a substitute for the operator-facing setup guide.

**Is the zone declared inline in the template?** No. `limit_req_zone` directives must live in the nginx `http {}` block and cannot be declared inside a `location {}` block (which is all the template contains). The template correctly does not attempt to declare zones inline — it relies on the operator having followed DEPLOYMENT.md. That dependency is broken.

**Attacker control:** No attacker input or special access is required. The misconfiguration is triggered by an operator following the documented setup procedure. Once misconfigured (nginx reload fails, old config stays active), any internet-reachable client can POST to `/sync/session` without rate limiting.

**Real-world impact:**
- **DoS:** Each `/sync/session` request triggers JSON parsing, nonce format validation (regex), and a Redis `GETDEL` call. Without rate limiting, an attacker can saturate the Redis connection pool and CPU with concurrent requests.
- **[[SEC-000003]] regression:** The specific fix [[SEC-000003]] introduced (rate-limiting `/sync/session`) is silently nullified for any operator who sets up the server following the current DEPLOYMENT.md. Installations following old configs remain unprotected indefinitely.
- **Severity rationale: Medium.** The vulnerability does not directly expose data or enable authentication bypass. The attack surface is a DoS/amplification on a Redis-backed endpoint, and the nonce exhaustion angle requires an attacker to also have harvested nonces. However, the combination of a hard nginx reload failure, a plausible-to-follow documentation path, and complete nullification of a deliberate security control ([[SEC-000003]]) warrants Medium rather than Low.

## Fix Plan

### Part 1 — Docs fix (`docs/DEPLOYMENT.md`)

In `docs/DEPLOYMENT.md`, the nginx rate-limiting zone snippet on lines 62–65 declares only `sync_challenge` and `sync_write`. Insert the missing `sync_session` zone between them so the block reads exactly:

```nginx
limit_req_zone $binary_remote_addr zone=sync_challenge:10m rate=5r/m;
limit_req_zone $binary_remote_addr zone=sync_session:10m rate=10r/m;
limit_req_zone $binary_remote_addr zone=sync_write:10m rate=30r/m;
```

Also update the prose on line 60 from "Add these **two** lines" to "Add these **three** lines" so the operator is not confused by a count mismatch.

No other files need changing for Part 1.

### Part 2 — Regression test (`sync-server/nginx-config.test.ts`)

The file already exists with four tests that verify the nginx template itself. Add a fifth test to the existing `describe('nginx sync-location.conf.template security', ...)` block that cross-checks `docs/DEPLOYMENT.md` against the template.

The test must:

1. Read `docs/DEPLOYMENT.md` (path relative to `import.meta.dir`: `'../docs/DEPLOYMENT.md'`).
2. Extract every zone name referenced in `nginx/sync-location.conf.template` via the regex `/limit_req zone=(\S+)/g` — this yields `sync_challenge`, `sync_session`, `sync_write`.
3. For each extracted zone name, assert that `DEPLOYMENT.md` contains the string `zone=<name>`.

This test fails before Part 1 (DEPLOYMENT.md lacks `zone=sync_session`) and passes after adding the missing line.

Add the test **inside** the existing `describe` block, after the last existing `it(...)`, so the file structure stays coherent. Do not add a new `describe` wrapper.

### Test Plan

**Exact failing test to write:**

File: `sync-server/nginx-config.test.ts` (file already exists — add inside the existing `describe` block)

Test name: `'DEPLOYMENT.md documents all rate-limit zones used in the template'`

Insert this `it(...)` block after the last existing test (line 32, before the closing `}`):

```ts
  it('DEPLOYMENT.md documents all rate-limit zones used in the template', () => {
    const deploymentMd = readFileSync(
      join(import.meta.dir, '../docs/DEPLOYMENT.md'),
      'utf-8'
    );
    const zoneRefs = [...config.matchAll(/limit_req zone=(\S+)/g)].map(m => m[1]);
    expect(zoneRefs.length).toBeGreaterThan(0);
    for (const zone of zoneRefs) {
      expect(deploymentMd).toContain(`zone=${zone}`);
    }
  });
```

**Why it fails before the fix:** `config.matchAll(/limit_req zone=(\S+)/g)` extracts `sync_challenge`, `sync_session`, and `sync_write` from the template. DEPLOYMENT.md currently contains `zone=sync_challenge` and `zone=sync_write` but not `zone=sync_session`, so the loop assertion fails on the second zone.

**Why it passes after the fix:** Part 1 adds `limit_req_zone $binary_remote_addr zone=sync_session:10m rate=10r/m;` to DEPLOYMENT.md, making `zone=sync_session` present and all three assertions pass.

Note: `config` is already declared at the top of the `describe` block (reading the template file), so the test can reuse it directly without a new variable for the template.
