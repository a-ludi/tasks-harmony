# Documented HMAC challenge-response is unimplemented; sync auth is effectively a bearer token

**Status:** DONE
**Bug ID:** [[SEC-000024]]
**Severity:** Medium

## Location
- `sync-server/handlers/challenge.ts` (entire file, lines 1-23)
- `sync-server/handlers/session.ts` (entire file, lines 1-30)
- `sync-server/handlers/blob.ts` (authentication path, lines 9-15)
- `src/sync/server.ts` (`fetchNewSessionToken`, lines 14-31)
- `sync-server/handlers/session.test.ts:55` — explicit test asserting "no hmac required"
- `docs/DEPLOYMENT.md:125` — documented `SYNC_APP_SECRET` intended for HMAC challenge-response
- `docker-compose.yml:10` — secret plumbed into the container but never consumed

## Description
`docs/DEPLOYMENT.md` describes `SYNC_APP_SECRET` as a *"Pre-shared secret for HMAC challenge-response; written to server `.env` and baked into the client bundle"*. `docker-compose.yml` faithfully passes `SYNC_APP_SECRET` into the sync container. But **no code — server or client — ever reads that secret**. Grepping the entire tree (excluding `node_modules`) shows the identifier appears only in `.env.local`, `docker-compose.yml`, and the deployment doc; there is no `process.env.SYNC_APP_SECRET`, no `createHmac`, and no `VITE_SYNC_APP_SECRET` in the client bundle (`.github/workflows/ci.yml:121` only passes `VITE_SYNC_URL`). The test suite even codifies the omission: `sync-server/handlers/session.test.ts:55` asserts `returns 200 with sessionToken using only nonce and syncToken (no hmac required)`.

What the code actually implements is a fake challenge/response that provides **zero authentication value**:

1. `POST /sync/challenge` accepts a client-supplied `syncToken` and returns a random `nonce`, storing `nonce → syncToken` in Redis (`challenge.ts:20-22`).
2. `POST /sync/session` accepts the same `nonce` and `syncToken` back, compares them to the Redis entry, and mints a 24-hour `sessionToken` (`session.ts:23-29`).
3. The `sessionToken` is used as a Bearer credential against `GET/PUT /sync/{syncToken}` for the encrypted blob (`blob.ts:9-21`).

The "challenge" proves nothing: the client sends the `syncToken` in cleartext on both requests, so possession of the `syncToken` alone is sufficient to complete the dance. There is no signature over the nonce, no HMAC, no asymmetric proof — the two-step flow is functionally identical to `POST /sync/session { syncToken }`. The `syncToken` (derived from `SHA-256(rawAesKey)` in `src/sync/credentials.ts:17-23`) is therefore a plain bearer credential for the sync server, despite the documentation, deployment story, and endpoint naming all implying otherwise.

Exploitability and impact:

- **Anonymous DoS on Redis.** `/sync/challenge` accepts any 64-hex-char string and writes a `nonce:*` key with 60-second TTL. There is no application-layer rate limit, no proof-of-work, and no HMAC gate. Any unauthenticated attacker on the internet can allocate Redis memory at line speed. The documented `sync_challenge` nginx zone (`docs/DEPLOYMENT.md:63`) is external, per-IP, and easy to sidestep from a botnet; if the operator deploys without that manual nginx step (common in dev, staging, or misconfigured prod), there is no rate limit at all.
- **Unauthenticated session-token minting for arbitrary tokens.** Because the server accepts *any* well-formed `syncToken` in `/sync/challenge` and issues a matching session for it in `/sync/session`, an attacker can freely generate 24-hour session tokens for any candidate token, enabling online enumeration/probing against the blob endpoint without ever presenting a shared secret. The 256-bit search space makes brute force infeasible, but this removes the intended app-secret gate that would have kept non-app clients out entirely.
- **Blob overwrite / destruction if a `syncToken` leaks.** The `syncToken` is transmitted in the URL path on every blob request (`src/sync/server.ts:44`, `sync-server/index.ts:9`). URLs routinely appear in nginx access logs, browser history, referer headers on outbound links, shared-computer sessions, browser-extension telemetry, and error-tracking payloads. Any such leak grants **write access** to `{token}.enc`, letting an attacker overwrite the victim's encrypted blob with an empty or malformed body. Because `src/sync/server.ts:pull` accepts any server blob whose `syncState.lastSyncedAt` is newer than local, and `SEC-000018`'s confirmation only fires when local data would be destroyed, an attacker who overwrites the blob with a valid-schema empty state at a future timestamp can silently wipe the victim's data on next sync. The AES-GCM key never leaves the client, so confidentiality is preserved — but integrity/availability are not, and the documented HMAC gate was the sole intended control preventing arbitrary internet clients from reaching this write path.
- **Missing defense-in-depth.** The intended design (client HMAC's the server nonce with the shared secret; server verifies with `timingSafeEqual`) would have (a) proven the client is running the official app bundle rather than a scripted attacker, (b) made the `/sync/challenge` endpoint useless to non-app clients, and (c) removed the "session token derivable from `syncToken` alone" property. All three defenses are absent.

The fix is to implement the documented protocol: consume `SYNC_APP_SECRET` on the server, expose `VITE_SYNC_APP_SECRET` to the client bundle via CI, have the client compute `HMAC-SHA256(APP_SECRET, nonce || syncToken)` and submit it as `hmac`, and have `handleSession` verify it with `crypto.timingSafeEqual` before issuing a session. The existing test at `session.test.ts:55` (`no hmac required`) should be inverted to require and verify the HMAC.

## Validation

**CONFIRMED — Medium severity. Genuine security issue with real exploitable impact.**

### Verification

All claims in the report were verified against the source code:

**Q1 — No HMAC anywhere in the codebase:** A grep for `SYNC_APP_SECRET`, `createHmac`, `VITE_SYNC_APP_SECRET`, and `hmac` across all `.ts`/`.js` files (excluding `node_modules`) returns only `sync-server/handlers/session.test.ts` (which asserts `no hmac required`). No server or client code reads or consumes `SYNC_APP_SECRET`. Confirmed.

**Q2 — Challenge/session protocol proven valueless:** `challenge.ts` accepts any well-formed 64-hex `syncToken`, stores `nonce → syncToken` in Redis with 60 s TTL, and returns the nonce. `session.ts` then accepts `{nonce, syncToken}`, fetches and deletes `nonce:*` from Redis, compares the stored value to the submitted `syncToken`, and mints a 24 h `sessionToken`. Because the attacker supplies the `syncToken` in both steps, they trivially pass the comparison — the round-trip proves only that the caller remembered what they sent. No cryptographic proof of identity is established. Confirmed.

**Q3 — Unauthenticated Redis write (DoS vector):** `challenge.ts` performs `redis.set(nonce:${nonce}, syncToken, EX, 60, NX)` for any caller that sends a valid hex string. There is no application-level rate limit on this handler. The nginx `sync_challenge` zone (`5r/m per IP`, `docs/DEPLOYMENT.md:63`) is a manual operator step that is easy to omit in dev/staging, and trivially bypassed from a distributed source. Confirmed.

**Q4 — Blob write path exploitable after syncToken leak:** `syncToken` appears in the URL path on every blob request (e.g. `GET/PUT /sync/{token}`). URLs reach nginx access logs, browser history, and error-tracking tools. Any leak grants a write-capable session token (via the trivial challenge/session flow) that can overwrite `{token}.enc`. The report's silent-wipe scenario (valid-schema empty state at a future timestamp) is plausible given the pull logic in `src/sync/server.ts`. Confidentiality is unaffected (AES-GCM key never leaves the client). Integrity and availability are genuinely at risk. Confirmed.

### Severity Rationale

**Medium** (not High) because:

- Confidentiality of user data is fully preserved — the AES-256-GCM encryption key never reaches the server, so an attacker gaining write access cannot read the encrypted blob.
- The primary attack paths (blob overwrite, Redis DoS) both require the `syncToken` to be in attacker reach. The 256-bit syncToken space makes blind brute-force infeasible; real-world exposure requires a token leak via logs, browser history, or shared infrastructure.
- The missing HMAC gate removes an intended defense-in-depth control ("official app client" proof) and lowers the barrier for scripted attacks, but the remaining exposure is data integrity/availability rather than confidentiality.
- Elevated from Low because: (a) the Redis DoS vector is fully unauthenticated and requires no syncToken knowledge; (b) blob overwrite with silent data destruction is a realistic consequence of token leakage in production environments that log URLs.

## Fix Plan

### Status: REVIEW — needs policy decision before implementation

The recommended fix in the Description ("implement the documented protocol: consume `SYNC_APP_SECRET` on the server, expose `VITE_SYNC_APP_SECRET` to the client bundle via CI, have the client compute `HMAC-SHA256(APP_SECRET, nonce || syncToken)` and submit it as `hmac`") **directly reverses a prior security decision** that was finalised on 2026-07-02 and reaffirmed on 2026-07-04.

**Prior decision — [[SEC-000006]] (`security-reports/SEC-000006-1.md`, Status: DONE):**

- The HMAC mechanism was deliberately and fully removed from the codebase (session.ts, index.ts, src/sync/server.ts, three secret-\*.ts files, vite.config.ts splitSecret, ci.yml `VITE_SYNC_APP_SECRET`).
- The test at `sync-server/handlers/session.test.ts:55` (`no hmac required`) — which [[SEC-000024]] cites as evidence of a gap — was **added as part of that fix** to codify the "nonce-only authentication is sufficient" contract.
- The post-resolution discussion on 2026-07-04 (SEC-000006-1.md:257–292) explicitly considered "should we put HMAC back?" and rejected it: any secret shipped to a browser bundle is public, so HMAC only "prov[es] the client possesses `APP_SECRET`" against attackers who cannot open DevTools — described as "~zero real security, not 'some.'"

**What [[SEC-000024]] correctly identifies:**

- `docs/DEPLOYMENT.md:125`, `docker-compose.yml:10`, `README.md:40,47`, and `.env.local` still reference `SYNC_APP_SECRET` / `VITE_SYNC_APP_SECRET` even though no code reads them. These are stale artefacts from the pre-[[SEC-000006]] design that were not cleaned up during the [[SEC-000006]] fix. The [[SEC-000006]] reviewer notes flagged three cleanup items (vite-env.d.ts, server.test.ts, cd.yml) but did not sweep `docs/DEPLOYMENT.md`, `docker-compose.yml`, or `README.md`.
- The Redis-DoS concern (`/sync/challenge` accepts any 64-hex string and allocates a Redis key without app-layer rate limit) is real but is exactly the "distributed flood — per-IP nginx limits do not help" gap that SEC-000006-1.md:282 explicitly documented as an *accepted* residual risk with recommended future hardening (Turnstile / PoW / disk quota + LRU).
- The blob-overwrite-after-syncToken-leak vector is also real, but reinstating HMAC does not close it — an attacker with the recovered secret plus a leaked syncToken can still complete the flow. Only removing the syncToken from URLs, adding an unlinked authorization token, or rotating on suspicion would address it.

**Why this needs manual review, not an autonomous fix:**

Three mutually incompatible resolutions are on the table, and choosing between them is a policy call the planner cannot make unilaterally:

1. **Ratify [[SEC-000006]]'s decision, close the documentation gap.** Rewrite `docs/DEPLOYMENT.md`, `docker-compose.yml`, `README.md`, and `.env.local` to remove all `SYNC_APP_SECRET` / `VITE_SYNC_APP_SECRET` references. Explicitly document that sync auth is nonce-issued-bearer with per-IP nginx rate limits, and that no app-secret gate exists by design. Accept the residual DoS risk (as SEC-000006-1.md:291 recommends) or file a follow-up ticket for one of options 1–3 (disk quota, Turnstile, PoW). This closes [[SEC-000024]] as WONTFIX-per-[[SEC-000006]] for the HMAC portion, and as a documentation fix for the stale references.

2. **Revert [[SEC-000006]]'s decision, reinstate HMAC as [[SEC-000024]] recommends.** Re-add `SYNC_APP_SECRET` on the server, re-add `VITE_SYNC_APP_SECRET` in CI, rebuild the XOR-split (or accept a plain-text bundle constant), reinstate `verifyHmac`, invert the `no hmac required` test. This directly contradicts [[SEC-000006]]'s post-resolution reasoning (2026-07-04) and requires the reviewer to explicitly overturn that decision. If chosen, it should be paired with a rider explaining what changed in the threat model to justify reversal.

3. **Adopt a stronger control that closes the DoS gap without the bundle-secret fiction.** For example: implement Cloudflare Turnstile on `/sync/challenge` (SEC-000006-1.md:288, "kills automated flooding without a shared secret"), or client-side proof-of-work (SEC-000006-1.md:289), or a global disk quota with LRU eviction (SEC-000006-1.md:287, "highest-leverage"). This provides real DoS protection that HMAC would not (a botnet can extract the bundle secret and still flood), and does not require reintroducing a fake app-identity control. If chosen, [[SEC-000024]] is closed by whichever hardening option lands.

The reviewer needs to pick option 1, 2, or 3 (or an explicit hybrid) before an implementer can proceed. All three are defensible; the choice hinges on how much residual DoS risk the operator accepts and whether the team wants to document "nonce-only bearer" as the intended design or reverse [[SEC-000006]].
