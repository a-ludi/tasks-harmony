# APP_SECRET embedded in client JS bundle breaks HMAC authentication

**Status:** DONE ✓
**Bug ID:** [[SEC-000006]]
**Severity:** High

## Location

- `vite.config.ts`, lines 12–29 (splitSecret function — XOR-splits `VITE_SYNC_APP_SECRET` into bundle)
- `src/sync/secret-a.ts`, `src/sync/secret-b.ts`, `src/sync/secret-c.ts` (three bundle constants)
- `src/sync/server.ts`, lines 17–22 (`getAppSecretBytes` — reassembles the secret at runtime)
- `sync-server/handlers/session.ts`, lines 4–17 (`verifyHmac` — server side HMAC check)
- `.github/workflows/ci.yml`, lines 123 (same secret passed as `VITE_SYNC_APP_SECRET` to build)

## Description

The sync authentication relies on a shared secret (`SYNC_APP_SECRET` / `VITE_SYNC_APP_SECRET`) to prove the client is a legitimate instance of the app. The server generates a random nonce via `GET /sync/challenge`, stores it in Redis with a 60-second TTL, and expects the client to return `HMAC-SHA256(nonce, APP_SECRET)` via `POST /sync/session`. The server verifies the HMAC and issues a session token only if the HMAC is correct and the nonce was previously issued.

**The same secret is baked into the public client-side JavaScript bundle at build time.** In `vite.config.ts` `splitSecret()` reads `VITE_SYNC_APP_SECRET` (the same value as `SYNC_APP_SECRET` set via GitHub Secrets, as confirmed by `ci.yml` lines 123 vs 109) and XOR-splits it into three parts (`partA`, `partB`, `partC`), which are injected as bundle-level string constants `__SYNC_PART_A__`, `__SYNC_PART_B__`, `__SYNC_PART_C__`. At runtime `getAppSecretBytes()` in `src/sync/server.ts` XORs them back together to reconstruct the original secret.

All three XOR parts are present in the same downloaded JS bundle. Any user of the app can:

1. Download the production JS bundle from the public URL.
2. Extract the three base64 strings (`__SYNC_PART_A__`, etc.) — trivially via DevTools or a text editor.
3. XOR them together to recover the original `APP_SECRET`.

With the recovered secret, the attacker can:

- **Forge HMAC proofs without a server-issued nonce.** The server's `verifyHmac` in `session.ts` (lines 6–17) only checks `HMAC-SHA256(nonce, secret) == hmac`. It does not check that the nonce was ever issued by the challenge endpoint. The nonce is checked against Redis *after* HMAC verification (line 43), but an attacker who controls their own Redis key (via a race or misuse) or who first fetches a genuine nonce from `/sync/challenge` can authenticate with a forged HMAC.

- **Obtain session tokens for any user's sync token.** The `POST /sync/session` body includes the `syncToken` field, which is completely attacker-controlled (validated only for hex format). By providing any valid (attacker-known) `syncToken`, the attacker can obtain a session token that authorizes reading and overwriting that user's encrypted blob at `/sync/{syncToken}`.

- **Completely bypass the authentication intent.** The challenge-response is designed to ensure only clients with the secret can authenticate. Once the secret is extracted from the bundle, the mechanism provides zero security. The three-part XOR is pure obfuscation — not a cryptographic protection — and the design spec itself (`docs/superpowers/specs/2026-06-25-encrypted-server-sync-design.md`, lines 134–136) acknowledges this defeats only "casual grep."

**Concrete attack scenario:** An attacker visits the app, opens DevTools, searches the network tab for the JS bundle, and extracts `__SYNC_PART_A__`, `__SYNC_PART_B__`, `__SYNC_PART_C__`. They XOR the three base64-decoded byte arrays to get the 32-byte `APP_SECRET`. They call `GET /sync/challenge` to get a server-issued nonce, compute `HMAC-SHA256(nonce, secret)`, and call `POST /sync/session` with `{ nonce, hmac, syncToken: "<victim's token>" }`. They receive a valid `sessionToken` for the victim. They then call `GET /sync/<victim's token>` to download and (client-side) decrypt the victim's entire task history.

Note: The data stored server-side is end-to-end encrypted with the per-user AES-256-GCM sync key. However, the attacker who controls their own sync token can still read and overwrite their own data; more critically, if the victim's `syncToken` is known (it is the SHA-256 of their AES key — not directly guessable, but computable if the attacker can induce the victim to reveal it), the attacker can overwrite or corrupt the victim's blob.

## Validation

**CONFIRMED — genuine, exploitable vulnerability.**

### Is `VITE_SYNC_APP_SECRET` actually embedded in the client bundle at build time?

Yes, unambiguously. `vite.config.ts` `splitSecret()` (lines 12–29) reads `process.env.VITE_SYNC_APP_SECRET` and injects all three XOR parts as Vite `define` constants (`__SYNC_PART_A__`, `__SYNC_PART_B__`, `__SYNC_PART_C__`). The CI workflow (`ci.yml` line 123) passes `VITE_SYNC_APP_SECRET: ${{ secrets.SYNC_APP_SECRET }}` (confirmed same secret as the server's `SYNC_APP_SECRET` at line 109) to the `bun run build` step. Vite `define` performs textual substitution directly into the emitted JS bundle — these are not environment-variable lookups at runtime; they are inlined string literals.

### Are the XOR parts actually in the client JS (not server-only code)?

Yes. `src/sync/secret-a.ts`, `secret-b.ts`, `secret-c.ts` are ordinary TypeScript source files that read the bundle-global constants and re-export them. `src/sync/server.ts` is client-side code (imports `idb`, `crypto.subtle`, `localStorage`, `fetch`) and imports all three secret files at lines 9–11, reconstructing the secret in `getAppSecretBytes()` at lines 17–22. None of this is behind a server-only boundary; it is all shipped to the browser.

### Does recovering the secret actually allow authentication bypass on the sync server?

Yes. The flow in `sync-server/handlers/session.ts` is:
1. Validate input format.
2. Check `HMAC-SHA256(nonce, APP_SECRET) == hmac` (line 41).
3. Check `redis.del("nonce:" + nonce) > 0` (line 43).

An attacker who recovers `APP_SECRET` from the bundle:
- Calls `GET /sync/challenge` to obtain a server-issued nonce (stored in Redis with 60s TTL).
- Computes the correct `HMAC-SHA256(nonce, APP_SECRET)` locally.
- Calls `POST /sync/session` with `{ nonce, hmac, syncToken: <target> }` — any hex-format syncToken passes format validation.
- Receives a valid `sessionToken` bound to the target syncToken.
- Can then `GET /sync/<syncToken>` to download the victim's encrypted blob, or `PUT /sync/<syncToken>` to overwrite/corrupt it.

The nonce one-time-use check (Redis `DEL`) is not a mitigation: the attacker uses a legitimately issued nonce from `/sync/challenge`. The rate limit on `/sync/session` (10r/m per IP) does not help — the attacker needs only one request.

### Is there any server-side mitigation that prevents abuse even with the recovered secret?

Partially. The blob content is E2E-encrypted with a per-user AES-256-GCM key that never leaves the client and is never transmitted to the server. Recovering `APP_SECRET` from the bundle does not expose a victim's plaintext task data unless the attacker also knows the victim's AES key. The `syncToken` itself is `SHA-256(AES_key)` — not directly guessable. So a mass-decryption attack against all users' data requires knowing each user's AES key.

However, this does not mitigate the core vulnerability:
- The authentication gate is completely defeated. Any user of the app can authenticate as any known syncToken holder.
- A victim's syncToken could be leaked via other channels (e.g., server logs, network interception of an unrelated request, social engineering).
- The attacker can corrupt or delete any user's sync blob by overwriting it with garbage, causing permanent data loss for that user.
- The entire purpose of the HMAC challenge-response — to restrict sync access to legitimate app clients — is nullified. The server cannot distinguish between the real app and a malicious script.

**Severity rationale (High, not Critical):** Downgraded from Critical because blob confidentiality is protected by E2E encryption with an unrecoverable per-user key; recovering `APP_SECRET` alone does not expose plaintext user data to mass extraction. The remaining concrete impact is: authentication bypass for any known syncToken (integrity/availability risk), and complete nullification of the app-identity authentication control.

## Fix Plan

### Chosen Approach: Replace HMAC with nonce-as-token (minimal removal)

The HMAC check exists solely to prove "I am a client that possesses APP_SECRET." Since APP_SECRET is recoverable from the bundle, this proof is worthless. The nonce already provides the real security property we need: it is server-issued, stored in Redis with a 60-second TTL, and consumed on first use (atomic `DEL`). Any client that presents a valid nonce at `/sync/session` demonstrably contacted `/sync/challenge` recently. That is sufficient as an authentication gate.

**Remove the HMAC mechanism entirely.** The client no longer sends an `hmac` field, and the server no longer checks it.

#### Server-side changes

**`sync-server/handlers/session.ts`**

1. Remove the `APP_SECRET` constant and the `verifyHmac` function entirely.
2. In `handleSession`, remove the `hmac` field from the destructured body, remove its format validation (`/^[a-f0-9]{64}$/` check on `hmac`), and remove the `verifyHmac` call (line 41).
3. Keep everything else unchanged: the nonce format check, the `syncToken` format check, the Redis `DEL` one-time-use check, and the session token issuance.

The new request body accepted by `POST /sync/session` is `{ nonce, syncToken }`. The `hmac` field is dropped — sending it is harmless (ignored) so old clients degrade gracefully until redeployed.

**`sync-server/index.ts`**

Remove the startup guard that requires `SYNC_APP_SECRET` to be set (lines 6–10). The env var is no longer needed server-side.

#### Client-side changes

**`src/sync/server.ts`**

1. Remove imports of `partA`, `partB`, `partC` (lines 9–11).
2. Remove `getAppSecretBytes()` and `computeHmac()` functions.
3. In `fetchNewSessionToken`, remove the `const hmac = await computeHmac(nonce)` call. Change the `POST /sync/session` body to `{ nonce, syncToken }` — omit the `hmac` field.

**`src/sync/secret-a.ts`, `secret-b.ts`, `secret-c.ts`** — delete all three files.

**`vite.config.ts`**

1. Remove the `splitSecret()` function and its invocation (lines 12–29).
2. Remove the `const { partA, partB, partC } = splitSecret()` line.
3. Remove the three `__SYNC_PART_A__`, `__SYNC_PART_B__`, `__SYNC_PART_C__` entries from `define`.

**`.github/workflows/ci.yml`**

Remove the `VITE_SYNC_APP_SECRET` line from the build step env block (line 123). Grep for `SYNC_APP_SECRET` in the workflow before removing `SYNC_APP_SECRET` from the sync-server deployment env — only remove it there if it is no longer referenced by any server code.

#### What is NOT changed

- `/sync/challenge` — unchanged; still issues nonces stored in Redis with 60s TTL.
- `/sync/{token}` blob handler — unchanged; session token Bearer auth is unchanged.
- Rate limiting on `/sync/session` in nginx — keep as-is (storage abuse mitigation).
- E2E encryption — completely untouched.

#### Security property after fix

An attacker can call `/sync/challenge` to get a nonce, but nonces are rate-limited (nginx), single-use, and expire in 60 seconds. Without a valid nonce, they cannot obtain a session token. With the shared secret gone from the bundle, there is no extractable credential. The authentication gate now provides the protection it was designed to provide.

## Post-resolution discussion — 2026-07-04

Question raised: removing the HMAC arguably reduced security, since the obscured `APP_SECRET` was at least *some* barrier. How was the decision justified?

**Reasoning recap:**

- The HMAC only proved "I possess `APP_SECRET`." Since the secret was reconstructible from the public JS bundle (XOR-split into three constants is obscurity, not cryptography), the proof was worthless against anyone willing to open DevTools. The mechanism provided ~zero real security, not "some."
- The obfuscation could not be "fixed" — anything shipped to a browser is public. Rotation, further scrambling, or more splits all collapse to the same problem.
- Judgment call: maintaining a mechanism that only deters attackers who don't know how to open DevTools was not worth the code, CI secret, and false-sense-of-security cost. The real app-identity control was never there; removal made that honest.

**Follow-up concern:** after removal, the only remaining barrier to flooding is "fetch a nonce → exchange for session token → operate on any syncToken." Is that enough?

**What is actually in place today:**

- nginx per-IP rate limits (`nginx/sync-location.conf.template`):
  - `/sync/challenge`: 5 r/m, burst 2
  - `/sync/session`: 10 r/m, burst 3
  - `/sync/{64-hex}` blob R/W: 30 r/m, burst 5, `client_max_body_size 1m`
- `/sync/challenge` binds the nonce to a specific `syncToken` (`challenge.ts:12,21`); `/sync/session` verifies the match (`session.ts:23–25`). An attacker cannot obtain a session for an arbitrary syncToken without first calling challenge for that same syncToken.
- Redis nonces expire in 60s; session tokens in 24h.

**What today's barriers stop:**

- Single-IP flood → yes, well-bounded (~30 MB/min max write per IP).
- Redis nonce exhaustion → yes.
- Distributed flood (botnet, many IPs) → **no** — per-IP nginx limits do not help.
- Long-tail storage growth → **no** — anyone can PUT 1 MB to a fresh random syncToken; nothing caps *total* disk.

**Options considered for future hardening (not implemented in this ticket):**

1. **Disk quota + LRU eviction on the blob store.** Cheapest; bounds worst-case damage rather than preventing entry. Requires documenting a "sync at least every X months to persist" contract.
2. **Cloudflare Turnstile (or hCaptcha) on `/sync/challenge`.** Passive challenge, invisible to real users, kills automated flooding without a shared secret. Adds external dependency on Cloudflare.
3. **Client-side proof-of-work on `/sync/challenge`.** Server issues difficulty target, client burns ~500 ms CPU. No external dep; sophisticated attackers can rent compute cheaply.

**Recommendation from the discussion:** option 1 is highest-leverage — rate limits cap the *rate* of abuse; a quota bounds the *cumulative* damage (the failure mode that actually takes the server down for everyone). Option 2 or 3 would be worth adding if distributed automated abuse is observed. No follow-up ticket filed yet.
