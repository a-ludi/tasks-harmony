# Missing Bearer token format validation in blob handler enables DoS via large Redis keys

**Status:** DONE
**Bug ID:** SEC-004
**Severity:** Medium

## Location
`sync-server/handlers/blob.ts`, lines 9–12 (`authenticate` function)

## Description
The `authenticate` function in the blob handler extracts the session token from the `Authorization: Bearer {token}` header without any format or length validation:

```ts
async function authenticate(req: Request): Promise<string | null> {
  const auth = req.headers.get('Authorization');
  if (!auth?.startsWith('Bearer ')) return null;
  const sessionToken = auth.slice(7);
  return redis.get(`session:${sessionToken}`);
}
```

The `sessionToken` can be any string of any length. It is passed directly as part of a Redis key: `redis.get(`session:${sessionToken}`)`.

**Exploitable impact:**

1. **DoS via large Redis GET key.** An attacker can send `Authorization: Bearer {megabytes of data}` in a GET or PUT request to `/sync/{64-hex-token}`. The server will pass this to Redis as `GET session:{megabytes}`. Nginx does have default limits on header sizes (`large_client_header_buffers`), but the nginx template does not set these explicitly, and the default is 8KB for individual headers, meaning tokens up to ~8KB can reach the application. With repeated requests, this creates unnecessary Redis I/O.

2. **Design-contract gap (defence-in-depth).** The session token is always generated as `randomBytes(32).toString('hex')` — a 64-char hex string. The `authenticate` function should enforce this format before querying Redis, just as SEC-001 fixes enforced it for the nonce. Without this check, the server will query Redis for tokens that could never have been generated by the session endpoint.

3. **Consistency with existing validation patterns.** The router already constrains the sync token in the URL to `/^\/sync\/([a-f0-9]{64})$/` (index.ts line 15), but there is no symmetric constraint on the session token in the auth header.

**Fix:** Add a format check for the session token in the `authenticate` function, mirroring the pattern now applied to the nonce in SEC-001:

```ts
const SESSION_TOKEN_RE = /^[a-f0-9]{64}$/;
const sessionToken = auth.slice(7);
if (!SESSION_TOKEN_RE.test(sessionToken)) return null;
```

This immediately rejects requests with malformed session tokens (any length > or < 64 chars, or non-hex chars) before touching Redis.

## Validation
**Verdict: CONFIRMED — genuine defence-in-depth gap with real DoS potential.**

Reachability: The `/sync/{token}` endpoints are publicly accessible. Both GET and PUT methods reach `authenticate()` before any other check.

Attacker control: Full control over the `Authorization` header value. Nginx default limits header lines to ~8KB, so tokens up to 8KB reach the application.

Real-world impact: Each request with a malformed/oversized session token causes an unnecessary Redis GET with a potentially large key. Under concurrent load from multiple attackers, this creates disproportionate Redis I/O. The fix is a one-line regex guard, identical in pattern to the SEC-001 fix for the nonce — the same vulnerability class applied to a different endpoint.

## Fix Plan

In `sync-server/handlers/blob.ts`, add a format check for the session token immediately after extraction from the header:

```ts
const SESSION_TOKEN_RE = /^[a-f0-9]{64}$/;

async function authenticate(req: Request): Promise<string | null> {
  const auth = req.headers.get('Authorization');
  if (!auth?.startsWith('Bearer ')) return null;
  const sessionToken = auth.slice(7);
  if (!SESSION_TOKEN_RE.test(sessionToken)) return null;
  return redis.get(`session:${sessionToken}`);
}
```

The regex constant should be declared at module scope (before the function) for efficiency.

**Why this location:** The `authenticate` function is the single point where session tokens are extracted and used. Adding the check here ensures all paths through the handler are protected.

**Why return `null` (not throw):** `null` from `authenticate` already causes a 401 Unauthorized response — consistent with unknown/invalid tokens. No need for a different status for malformed tokens (avoid information leakage about the rejection reason).

```ts
it('GET returns 401 when session token is not 64 hex chars (too short)', async () => {

it('GET returns 401 when session token contains non-hex chars', async () => {

  expect(res.status).toBe(401);
  expect(mockGet).not.toHaveBeenCalled();
});
```

The `mockGet` assertion (`.not.toHaveBeenCalled()`) is critical — it confirms that Redis is not queried for malformed tokens. This test must FAIL before the fix (Redis IS queried) and PASS after (Redis is NOT queried).
