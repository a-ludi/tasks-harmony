# `updateCDP` overwrites arbitrary packs when `pack.sourceUrl` has a basename that differs from the pack id, re-enabling the [[SEC-000029]] seeded-personal-pack takeover through the [[SEC-000023]] backup-import path

**Status:** DONE
**Bug ID:** [[SEC-000033]]
**Severity:** High

## Location

- `src/store/index.ts` lines 268–284 — `updateCDP` fetches from the pack's stored `sourceUrl`, then writes the returned `Pack` back to IndexedDB **using the id derived from that URL**, not the id of the pack being updated:
  ```ts
  updateCDP: async (packId) => {
    const { db, packs } = get();
    if (!db) throw new Error('Database not initialised');
    const pack = packs.find((p) => p.id === packId);
    if (!pack) throw new Error(`Pack '${packId}' not found in store`);
    if (!pack.sourceUrl) throw new Error(`Pack '${packId}' has no sourceUrl — cannot update`);
    const { pack: updatedPack, chores: updatedChores, questions: updatedQuestions } = await fetchCDP(pack.sourceUrl);
    for (const chore of updatedChores) await putChore(db, chore);
    for (const question of updatedQuestions) await putQuestion(db, question);
    const refreshedPack: Pack = { ...updatedPack, importedAt: pack.importedAt, updatedAt: new Date().toISOString() };
    await putPack(db, refreshedPack);
    ...
  }
  ```
  Note that `refreshedPack.id` comes from `updatedPack.id` (via the spread), which is derived from the URL basename by `fetchCDP` — **not** from the `packId` argument or from the existing `pack.id`. No check verifies that `updatedPack.id === packId`.
- `src/cdp/cdp-import.ts` lines 57–58 — `fetchCDP` derives `packId` verbatim from the URL basename with no reserved-id list and no cross-check against the caller's expected id:
  ```ts
  const urlPath = baseUrl.replace(/\/$/, '');
  const packId = urlPath.substring(urlPath.lastIndexOf('/') + 1);
  ```
- `src/schemas/appState.schema.json` line 40 — the AppState schema (used to validate untrusted `.zip` backups on import) declares `sourceUrl` as bare `{ "type": "string" }`. The [[SEC-000023]] fix added `additionalProperties: false` and required-field shape checks, but placed **no format/host/basename constraint on `sourceUrl`**. Any string passes.
- `src/sync/import.ts` lines 7–28 — `importAppState` clears all stores then writes every incoming array entry directly into IndexedDB. There is no post-validation sanitisation of `sourceUrl`.
- `src/store/index.ts` lines 245–266 — `importCDP` gained a collision check in [[SEC-000029]], but `updateCDP` was explicitly documented ([[SEC-000029]] fix plan, lines 102 and 104) as "trust[ing] the *already-stored* `sourceUrl` (not the URL currently in the input field), so it does not open a takeover vector." That assumption is false whenever the stored `sourceUrl` came from an untrusted backup.
- `src/db/seed.ts` lines 15–23 — the app seeds a `personal` pack with `id: 'personal', isPersonal: true`; this is the pack the app treats as un-deletable.
- `src/db/index.ts` lines 120–121 — `putPack` is a raw `db.put('packs', pack)` against a store whose `keyPath: 'id'` **overwrites in place** when the key exists.

## Description

### Threat model

The [[SEC-000023]] fix tightened the AppState schema so that `.zip` backup imports must have well-shaped pack entries (all required fields, correct types, no extra properties). The [[SEC-000029]] fix added a collision check to `importCDP` so that a fresh CDP import cannot overwrite an existing pack via URL-basename collision. Both fixes assumed that once these guards are in place, the *stored* `pack.sourceUrl` in IndexedDB is trustworthy for future `updateCDP` calls.

That assumption breaks in the intersection of the two fixes: the AppState schema still allows **any string** for `sourceUrl`, so a crafted `.zip` backup can plant a pack whose stored `sourceUrl` points to an arbitrary host with an arbitrary basename. The pack passes [[SEC-000023]]'s shape validation, gets written to IndexedDB, and sits there dormant. Later, when the user clicks **Update** on that pack (or if any code path invokes `updateCDP` on that pack id), the "trusted local `sourceUrl`" is used to fetch attacker content, and `putPack(refreshedPack)` writes the result under the **URL-derived** id, silently overwriting whichever pack currently occupies that id — including the seeded `personal` pack, whose `isPersonal: true` guard on `deletePack` is the sole invariant preventing deletion of all user-owned chore metadata.

### The vulnerability

Consider a user who imports a crafted backup zip containing a benign-looking pack `evening-routines` with `sourceUrl: "https://raw.githubusercontent.com/attacker/routines/refs/heads/main/personal"`. The pack shape is valid, so [[SEC-000023]]'s schema check passes. `importAppState` writes it to IndexedDB verbatim.

Now the pack has:
- `id: "evening-routines"` (matches the click target in the UI)
- `sourceUrl: "https://.../personal"` (basename does not match `id`)

At some later point — perhaps hours or weeks later, after the initial import has faded from the user's memory — the user clicks **Update** on the Evening Routines pack. `PackDashboard.tsx` shows an update button next to any pack with a `sourceUrl`; the UI copy is "Update imported pack". `updateCDP('evening-routines')` runs:

1. `pack = packs.find(p => p.id === 'evening-routines')` — found.
2. `pack.sourceUrl` is `https://.../personal`.
3. `fetchCDP('https://.../personal')` — the attacker serves a schema-valid manifest and chore file. `fetchCDP` derives `packId = 'personal'` from the URL basename and returns:
   ```ts
   {
     pack: {
       id: 'personal',                                      // ← derived from URL, NOT from evening-routines
       manifest: { title: attacker.title, ... },
       isPersonal: false,                                   // ← flips the delete guard OFF
       importedAt: now, updatedAt: now,
       sourceUrl: 'https://.../personal',
     },
     chores: [ ...attacker's chores with packId: 'personal'... ],
     questions: [ ... ],
   }
   ```
4. `for (const chore of updatedChores) await putChore(db, chore)` — attacker chores are written under keys `personal/{choreId}`. Any collision with the user's existing personal chores (guessable choreIds such as `floss`, `meditate`, `brush-teeth`, `water-plants`) silently overwrites them.
5. `refreshedPack = { ...updatedPack, importedAt: pack.importedAt, updatedAt: new Date().toISOString() }` — the spread preserves `id: 'personal'`, `isPersonal: false`, `sourceUrl: 'https://.../personal'`. `pack.importedAt` is the *evening-routines* import date (a cosmetic detail; it does not change the id).
6. `putPack(db, refreshedPack)` — this **overwrites the seeded personal pack in place**. The `evening-routines` pack is untouched.

Post-condition: the personal pack is now attacker-controlled; `isPersonal` is `false`; `sourceUrl` is attacker-controlled and durable across restarts. The attacker's `updateCDP('personal')` binding is now first-class, and the personal pack appears in the CDP dialog's "Installed packs" list with its own Update button (see `CDPImportDialog.tsx:100`: `packs.filter((p) => Boolean(p.sourceUrl))`).

### Post-exploit primitives

Once the personal pack is hijacked via `updateCDP`, the attacker inherits every [[SEC-000029]] post-exploit primitive:

- **Persistent CDP hijack of the personal pack.** Every subsequent `updateCDP('personal')` pulls attacker content. The `sourceUrl` never rotates back.
- **Bypass of the un-deletable-personal-pack invariant.** `deletePack` (`store/index.ts:357`) refuses to run when `pack.isPersonal`. After the takeover `isPersonal === false`, so the pack — and, through the disposition machinery, all user-owned chores in it — can be mass-deleted or reparented.
- **Cross-pack chore overwrite.** As in step 4 above, any chore with a guessable `choreId` in the personal pack is silently replaced.
- **`updatablePacks` visibility upgrade.** The personal pack now has a visible Update button that pulls attacker content on click.

None of these post-exploit primitives are new; [[SEC-000029]] already documented them for the `importCDP` path. The novelty is the reachability: **[[SEC-000029]]'s fix does not close this attack chain**, because it only guards `importCDP` and explicitly leaves `updateCDP` unchecked on the (now-invalid) assumption that the stored `sourceUrl` is trustworthy.

### Why this survives [[SEC-000023]] and [[SEC-000029]]

- **[[SEC-000023]] (schema tightening) does not close it.** The current schema entry for `sourceUrl` is `{ "type": "string" }` (`appState.schema.json:40`). Any string — including one whose basename is `personal` and whose host is attacker-controlled — passes. [[SEC-000023]]'s fix plan explicitly kept `sourceUrl` unconstrained (see fix plan lines 155: "`sourceUrl: { type: "string" }` (optional)"), because its threat model treated the plain `updateCDP` flow as a [[SEC-000023]]-only impact ("Persistent CDP hijack" — the pack keeps its original id and every update pulls attacker content into *that* pack). That threat model missed the id-mismatch case, where the attacker doesn't merely poison the updated pack's contents but overwrites a *different* pack (specifically the seeded personal pack, whose id the user cannot legitimately have imported).

- **[[SEC-000029]] (importCDP collision check) does not close it.** The check runs in `importCDP` before the fetch (`store/index.ts:249–254`). `updateCDP` performs no equivalent check: it does not compare `updatedPack.id` to `packId`, it does not compare the URL basename to `packId` before fetching, and it does not verify that `refreshedPack.id === pack.id`. The fix plan explicitly excluded `updateCDP` from the guard on the assumption that stored `sourceUrl` is trustworthy — an assumption that fails once an untrusted backup has been imported.

- **`.enc` (encrypted) backups are not exposed.** As [[SEC-000023]] noted, the AES-GCM auth tag prevents attackers from crafting decryption-valid `.enc` files without the user's key. The attack surface is the plain `.zip` path only.

### Reachability and social-engineering realism

The pre-conditions are:

1. The user imports an attacker-crafted plain `.zip` backup via **Settings → Import Backup**. This is a first-class UI feature (`ProfilePage.tsx:298–311`), the file extension is user-friendly, and the app's own export UI produces files with the same extension. On a fresh install, `isAppStatePristine` returns `true`, and the confirmation prompt in `ProfilePage.tsx:91–99` is skipped entirely — the malicious backup is imported with *zero* prompts.
2. At any later point, the user clicks **Update** on the malicious pack. The Update button is displayed prominently in the pack dashboard header (`PackDashboard.tsx:105–117`), with the tooltip "Update imported pack". Any user who imported the pack expecting periodic content updates will click this button eventually; users who don't will simply keep the dormant attack in their store indefinitely, and any future in-app auto-update mechanism (or an attacker who tricks the user into clicking through a shared URL scheme) will trigger it.

Neither step raises a warning or a red flag; both are documented, first-class user actions.

### Root-cause summary

The security invariant "each pack's `sourceUrl` is trustworthy" was assumed by both [[SEC-000023]] (which only validated the shape of imported objects) and [[SEC-000029]] (which only guarded `importCDP`). Together they close the seeded-pack-takeover attack when the attack originates from CDP-dialog input, but they leave the same attack open when it originates from the plain `.zip` backup input and is triggered later via `updateCDP`. The specific missing check is: `updateCDP` must verify that the `updatedPack.id` returned by `fetchCDP(sourceUrl)` matches the `packId` being updated (equivalently, that the `sourceUrl` basename equals `pack.id`) — otherwise the update is silently rewriting a different pack.

[[SEC-000023-1]] and [[SEC-000029-1]] are fixed reports (not checked per instructions). ### Severity Rationale

**High** (same tier as [[SEC-000029]], whose post-exploit primitives this fully replicates):

- **Impact is severe**: Persistent takeover of the un-deletable seeded personal pack — the root anchor for all user-owned chore data. Post-exploit, the attacker can mass-delete or reparent the user's personal chores and install a permanent CDP hijack that silently overwrites pack content on every future Update click.
- **Attack chain requires two user actions**: import a crafted plain `.zip` backup, then click the Update button on the planted pack. Both are documented, first-class UI affordances. On a fresh install, step one produces no confirmation prompt.
- **No cryptographic prerequisite**: Unlike [[SEC-000025]], this attack requires no XSS; the user performs both steps willingly without any visible warning or anomaly.
- **Not Critical** because the attacker must induce the user to import a malicious file and click Update — a two-step social-engineering chain rather than a zero-click or pure-network path.
- The fix is a single missing id-equality check in `updateCDP` (verify `updatedPack.id === packId` before `putPack`), optionally supplemented by constraining `sourceUrl` basename in the AppState schema and in `importAppState`.

## Fix Plan

**Primary fix (closes the attack chain):** in `src/store/index.ts`, add an id-consistency check to `updateCDP` immediately after `fetchCDP(pack.sourceUrl)` returns, before any writes to IndexedDB. If `updatedPack.id !== packId`, throw an error and abort the update. This ensures that even when a pack's stored `sourceUrl` has a basename that differs from the pack's own id (e.g. planted by an attacker-crafted backup that passed [[SEC-000023]]'s schema check), the update will fail loudly rather than silently overwrite a different pack.

Concretely, between lines 274 and 275 of `src/store/index.ts` insert:

```ts
if (updatedPack.id !== packId) {
  throw new Error(
    `Cannot update pack '${packId}': fetched pack id '${updatedPack.id}' does not match. The pack's sourceUrl may have been tampered with.`,
  );
}
```

The check must run **before** the `putChore`/`putQuestion` loops so that no attacker chores or questions are written to disk on a mismatch (the chores carry the attacker-derived `packId` and would otherwise persist even if we later refused to write the pack itself).

**Secondary hardening (same PR):** in `src/schemas/appState.schema.json`, tighten the `sourceUrl` field on pack items so that untrusted backup imports cannot plant packs with a `sourceUrl` whose basename differs from the pack id in the first place. Change line 40 from `"sourceUrl": { "type": "string" }` to require an `https:` URL. A basename-equals-id cross-field check is not expressible in JSON Schema draft-07 without runtime code, so the schema layer restricts the scheme/format and the runtime `updateCDP` check remains the invariant enforcer. Update line 40 to:

```json
"sourceUrl": { "type": "string", "format": "uri", "pattern": "^https://" }
```

This defence-in-depth measure blocks obviously-malicious `sourceUrl` values (e.g. `javascript:`, `file:`, `data:`) at the schema boundary but is not required for the primary attack chain to be closed. The runtime check in `updateCDP` is the load-bearing fix.
