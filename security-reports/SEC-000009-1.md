# Unrate-limited /sync/ catch-all nginx location allows unlimited DoS flooding of the sync server

**Status:** DONE
**Bug ID:** SEC-000009
**Severity:** Medium

## Location

- `nginx/sync-location.conf.template`, lines 25–28 — the `/sync/` prefix catch-all location block has no `limit_req` directive

## Description

The nginx location template defines specific rate-limited blocks for each known sync endpoint:

- `location /sync/challenge` → `limit_req zone=sync_challenge burst=2 nodelay` (5r/m)
- `location ~ "^/sync/[a-f0-9]{64}$"` → `limit_req zone=sync_write burst=5 nodelay` (30r/m)
- `location = /sync/session` → `limit_req zone=sync_session burst=3 nodelay` (10r/m)

However, the catch-all block at the bottom of the template:

```nginx
location /sync/ {
    proxy_pass http://unix:__SOCKET_DIR__/sync.sock;
    proxy_http_version 1.1;
}
```

has **no `limit_req` directive**. This block matches any request whose path begins with `/sync/` that is not claimed by a more specific location — for example:

- `POST /sync/` (bare prefix)
- `GET /sync/x` (non-hex or short token paths)
- `DELETE /sync/aaa...` (token less than 64 chars)
- Any method to any `/sync/*` path that doesn't match the three specific blocks

nginx location priority is: exact match (`=`) > regex (`~`) > longest prefix. The specific blocks above are all more specific than the `/sync/` prefix, so they are matched first for their respective paths. Any other `/sync/*` request falls through to the catch-all.

The Bun server's router in `sync-server/index.ts` responds with `404 Not Found` for all of these unmatched paths. However, **each such request still traverses the full nginx → Unix socket → Bun event-loop → response path** with zero throttling.

**Exploitable DoS scenario:**

An attacker sends high-rate requests to any path matching `/sync/` but not matching a specific block — for example, rapid-fire `POST /sync/x` or `POST /sync/` itself. nginx proxies each one through the Unix socket to the Bun server with no rate limiting. The Bun server parses the URL, fails to match any route, and emits a 404. With sufficient concurrency, this saturates:

1. The Unix socket's connection queue
2. Bun's HTTP event loop
3. nginx's upstream connection pool

None of the three rate-limit zones (`sync_challenge`, `sync_session`, `sync_write`) apply to requests that match the catch-all, so the existing per-IP rate limits for the valid endpoints are completely bypassed for this attack vector.

This is distinct from the previously fixed issues (SEC-000003 rate-limited `/sync/session`; SEC-000008 documented the missing zone). The catch-all block itself is the gap — it is intentionally present to handle the case where nginx might receive `/sync/` requests not matching any specific pattern, but it was never given its own rate limit.

## Validation

**Verdict: CONFIRMED — genuine DoS vulnerability in the nginx configuration.**

**1. Does the catch-all `/sync/` location block truly lack a `limit_req` directive?**

Yes. `nginx/sync-location.conf.template` lines 25–28 show:

```nginx
location /sync/ {
    proxy_pass http://unix:__SOCKET_DIR__/sync.sock;
    proxy_http_version 1.1;
}
```

No `limit_req` directive is present. Confirmed by direct inspection.

**2. Are there other nginx-level mitigations that would prevent this?**

No. The project only ships a location block template (`nginx/sync-location.conf.template`), not a full `nginx.conf`. The deployment docs (`docs/DEPLOYMENT.md`) define only the three named `limit_req_zone` entries (`sync_challenge`, `sync_session`, `sync_write`) for the http block — there is no `limit_conn` zone, no global rate limit zone, and no other per-IP throttle documented or expected. Default nginx `worker_connections` (typically 1024) provides a coarse OS-level ceiling but no per-IP or per-path request rate constraint. None of the three existing zones apply to paths falling into the catch-all.

**3. What is the actual impact? Does nginx handle the 404 before proxying?**

No — nginx cannot determine the 404 before proxying. The `location /sync/` block unconditionally `proxy_pass`-es to the Bun Unix socket. Only after the full round-trip (nginx → Unix socket → Bun event loop → route dispatch → `new Response('Not Found', { status: 404 })` in `sync-server/index.ts` line 17) does nginx receive the 404 to return to the client. Every request to an unmatched `/sync/*` path consumes: a Unix socket connection, Bun event-loop time (URL parse, route dispatch), and nginx upstream connection pool state. This is materially more expensive than a pure nginx static-file 404, where the 404 is resolved by nginx itself without upstream involvement.

**4. Is there a global nginx connection limit?**

Not at the per-IP or per-path level. `worker_connections` is a global concurrency cap (not per-IP) and not part of the project's config. Without `limit_conn`, a single IP can hold many simultaneous connections within the global cap. No `limit_conn_zone` is defined in this project's deployment instructions.

**5. Is this meaningfully different from any standard "unprotected 404 endpoint"?**

Yes. For a typical web server, nginx resolves 404 by checking the filesystem — no upstream is involved. Here, every `/sync/*` request (matched or not) is forwarded through a Unix socket to the Bun server. The Bun server parses the URL, runs route matching, and returns a response before nginx can reply to the client. The cost per request is therefore a proxy round-trip, not a local file lookup. At high concurrency, this saturates: (a) the Unix socket connection queue, (b) Bun's HTTP event loop, and (c) nginx's upstream connection pool.

**Exploitability:**

The regex location `~ "^/sync/[a-f0-9]{64}$"` is strict — exactly 64 lowercase hex characters. Any path that doesn't match that pattern and isn't exactly `/sync/challenge` or `/sync/session` falls to the catch-all. An attacker can trivially pick paths like `GET /sync/x` or `POST /sync/` to bypass all three named zones with zero throttle.

**Severity rationale: Medium.** The vulnerability does not expose data or enable authentication bypass. Impact is DoS: the catch-all acts as an unthrottled proxy for arbitrary `/sync/*` paths, enabling an attacker to saturate the Bun event loop and Unix socket queue. This is meaningful given that the specific named endpoints already have carefully configured rate limits — the catch-all undermines the overall rate-limiting posture. A simple `limit_req` addition fixes it. Medium (not High) because it requires sustained, deliberate flooding and affects availability only.

## Fix Plan

Two files change. No new files are created.

### 1. `nginx/sync-location.conf.template` — add `limit_req` to the catch-all block

The catch-all block at lines 25–28 currently reads:

```nginx
location /sync/ {
    proxy_pass http://unix:__SOCKET_DIR__/sync.sock;
    proxy_http_version 1.1;
}
```

Add a `limit_req` directive as the first line inside the block, mirroring the style used by all three specific blocks above it:

```nginx
location /sync/ {
    limit_req zone=sync_catchall burst=5 nodelay;
    proxy_pass http://unix:__SOCKET_DIR__/sync.sock;
    proxy_http_version 1.1;
}
```

The zone name `sync_catchall` is new and must match the declaration added in step 2.

### 2. `docs/DEPLOYMENT.md` — declare the new `limit_req_zone`

In the "nginx — rate limiting zones" section (lines 62–66), a code block currently declares exactly three zones. Add a fourth line for `sync_catchall`:

```nginx
limit_req_zone $binary_remote_addr zone=sync_challenge:10m rate=5r/m;
limit_req_zone $binary_remote_addr zone=sync_session:10m rate=10r/m;
limit_req_zone $binary_remote_addr zone=sync_write:10m rate=30r/m;
limit_req_zone $binary_remote_addr zone=sync_catchall:10m rate=20r/m;
```

`rate=20r/m` (approx. one request every 3 seconds per IP) is a generous ceiling that will never affect legitimate clients — the Bun router returns a 404 for everything that reaches this block — while still preventing rapid-fire DoS flooding.

### Why these two changes and nothing else

- The existing `'DEPLOYMENT.md documents all rate-limit zones used in the template'` test in `sync-server/nginx-config.test.ts` (line 33) already scans the template for every `limit_req zone=…` reference and asserts each one appears in `DEPLOYMENT.md`. Adding `zone=sync_catchall` to the template without adding it to `DEPLOYMENT.md` would cause that existing test to fail — so both files must be updated together.
- No other nginx config files, server code, or tests need to change.

### Test Plan

**Exact failing test to add** (before touching any production file):

File: `sync-server/nginx-config.test.ts` — add inside the existing `describe('nginx sync-location.conf.template security', ...)` block.

Test name: `'catch-all /sync/ location block includes a rate limit'`

```ts
it('catch-all /sync/ location block includes a rate limit', () => {
  const catchallMatch = config.match(/location \/sync\/ \{[^}]+\}/s);
  expect(catchallMatch).not.toBeNull();
  expect(catchallMatch![0]).toContain('limit_req');
});
```

**Why this test fails before the fix:** The regex `/location \/sync\/ \{[^}]+\}/s` matches the catch-all block (`location /sync/ {` … `}`) and asserts the matched text contains the string `limit_req`. Currently the block contains only `proxy_pass` and `proxy_http_version`, so `toContain('limit_req')` fails.

**Why this test passes after the fix:** After step 1 inserts `limit_req zone=sync_catchall burst=5 nodelay;` as the first directive inside the block, the matched text contains `limit_req` and the assertion passes.

**Second test that will also fail before the fix** (already present — no change required):

`'DEPLOYMENT.md documents all rate-limit zones used in the template'` (line 33 of the test file) — once `zone=sync_catchall` appears in the template, this existing test will fail until `docs/DEPLOYMENT.md` is also updated. This confirms both files must be updated in the same commit.
