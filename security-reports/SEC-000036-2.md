# Legacy AES-encrypted blob is orphaned on the sync server after PQ migration, permanently exposing pre-migration data under the weak legacy auth/encryption

**Status:** WONTFIX
**Bug ID:** [[SEC-000036]]
**Severity:** High

## Location
- `src/sync/migrate.ts` lines 31-74 (whole `migrate()` function; no `DELETE /sync/{legacySyncToken}` call anywhere)
- `src/sync/server.ts` lines 111-125 (`deleteRemote()` explicitly refuses to act on `LegacySyncCredentials`: `if (!creds || isLegacyCredentials(creds)) return { deleted: false };`)
- `src/components/profile/ProfilePage.tsx` lines 174-177 (`handleKeyImport` gates the deletion behind `!isLegacyCredentials(oldCreds)`, so a user importing a v2 key file while still on legacy credentials does not scrub the legacy blob either)
- `sync-server/handlers/session.ts` lines 70-90 (`handleSessionLegacy` remains fully functional and is never fenced off; the legacy blob remains reachable via `handleSessionLegacy` as long as it exists on disk)
- Related: `src/sync/credentials.ts` lines 27-33 (`deriveSyncToken(key)` from an exportable `CryptoKey`) — the token that authenticates the orphaned blob is deterministically derivable from the AES key that lives in IndexedDB.

## Description
`migrate(db)` (called from `MigrationModal` on app startup whenever the stored credentials are `LegacySyncCredentials`) performs three steps:

1. Best-effort **pull** with legacy credentials.
2. Generate a fresh PQ key bundle and overwrite the stored credentials with it (`putCredentials(db, pqCreds)`).
3. **Push** the local state to the server under the new PQ `syncId`.

There is **no fourth step** that deletes the legacy blob (`DELETE /sync/{legacySyncToken}`). Because the migrate function has the legacy `CryptoKey` in memory only through the end of step 1, and because `deleteRemote()` in `src/sync/server.ts` short-circuits with `{ deleted: false }` when `isLegacyCredentials(creds)` is true, no code path anywhere in the client will ever DELETE the legacy blob. The blob therefore remains on disk in `SYNC_BLOB_DIR` forever (nginx enforces no TTL; the server only evicts on explicit DELETE or when a new-identity admission hits the count cap, which does not touch existing blobs — see `blob.ts` lines 59-79, which explicitly rejects new admissions rather than evicting anyone).

The orphaned blob is authenticated by the **legacy** `syncToken`, which the sync server continues to accept via `handleSessionLegacy` in `sync-server/handlers/session.ts`. The legacy `syncToken` is a public function of the AES `CryptoKey` (`deriveSyncToken = SHA-256(rawKeyBytes)`, `src/sync/credentials.ts` L27-33). The AES key is stored in IndexedDB with `extractable=true` (`src/sync/credentials.ts` L15-19, `src/sync/credentials.ts` L95), so once the migrate function runs, the same threat model that motivates migration in the first place still applies to the *pre-migration* data:

1. Any XSS in the app before, during, or after migration can `crypto.subtle.exportKey('raw', ...)` the legacy AES key from IndexedDB — but wait, after `putCredentials(db, pqCreds)` in step 2 the AES key is overwritten. However, the *derived* legacy `syncToken` is deterministic and only 256 bits, and the *ciphertext of the last pre-migration push is still on the server*. Any prior exfiltration of the AES key (which is trivial under exclusion #2) is sufficient to fetch **and decrypt** the orphaned blob **at any point in the future**, without any further access to the user's device.
2. Because `handleSessionLegacy` grants a session token from `nonce+syncToken` alone (exclusion #1), the attacker only needs the legacy `syncToken` (equivalent to the AES key hash) to authenticate. There is no HMAC challenge-response gate.
3. Migration was intended to be a hardening step; instead it creates a "the door is locked, but we left the previous door standing next to it" situation. Users who complete migration are left with a false sense of security: their *current* data is protected by PQ credentials, but their entire pre-migration snapshot (including all completions, XP history, profile info, and any personal chore data captured in the last legacy `push()`) sits on the sync server encrypted under a key whose ciphertext-to-plaintext transformation the attacker only needs one AES key exfiltration to defeat, permanently.

Additionally, the on-disk blob is retained under an identifier the *server operator* also cannot invalidate on the user's behalf: since the file is named `{legacySyncToken}.enc` and there is no user identity that ties it to the user's new PQ `syncId`, an admin cleaning up "old" blobs cannot correlate a legacy blob with a migrated user account. Right of erasure / GDPR-style requests cannot be honoured without the user manually deleting the legacy blob (which the UI provides no button for).

### Concrete exploitation path
Preconditions:
- Attacker has the legacy AES key, e.g., via prior XSS (exclusion #2), an old exported key file that the user still has on disk, an old device backup, or a compromised device that had the app installed pre-migration.
- Attacker knows the sync server URL.

Steps:
1. Compute `syncToken = hex(SHA-256(rawAESKeyBytes))`.
2. `POST /sync/challenge` with `{ syncToken }` → server responds with a `nonce` (see `sync-server/handlers/challenge.ts` L15-28; the legacy path is still enabled).
3. `POST /sync/session` with `{ nonce, syncToken }` → server responds with a 24-hour `sessionToken` (see `sync-server/handlers/session.ts` L70-89).
4. `GET /sync/{syncToken}` with `Authorization: Bearer {sessionToken}` → orphaned encrypted blob.
5. Decrypt with the AES key using `decryptState` (`src/sync/encrypt.ts` L68-84).

The attacker now has the full pre-migration `AppState`: packs, chores, questions, completions (with all answer values and XP), the user profile (including `displayName` and `email`), and quick-answer sets. This works forever — the migrate function will not run again on the user's device, no client code ever attempts to delete the legacy blob, and `handleSessionLegacy` never gets disabled.

### Why this is a distinct issue from the excluded ones
- Exclusion #1 ("Documented HMAC challenge-response is unimplemented; sync auth is effectively a bearer token") concerns the *auth protocol*. This report is about a *data-retention* defect that keeps a bearer-token-authenticated blob on the server after the user has intentionally moved off bearer-token auth. Fixing the challenge-response auth would not fix this issue, because the migrated user has *already* moved to PQ signatures — the concern here is that the pre-PQ ciphertext is still stored and still auth'd by the legacy scheme for the specific user who has just been told they are safe now.
- Exclusion #2 ("Sync AES-256 master key stored in IndexedDB is exportable, enabling XSS to exfiltrate it and permanently decrypt all backups") concerns the *client-side key storage*. This report is about the server-side *retention* of ciphertext that becomes decryptable via any past exfiltration of that key. Fixing IndexedDB storage (e.g., non-extractable key) would not retroactively help users who have already migrated, because the legacy blob will remain on the server encrypted under a key that used to be extractable; any past exfiltration is still weaponisable against the orphaned blob for as long as it exists.

The fix — deleting the legacy blob as a Step 4 of `migrate()` (using the still-in-memory legacy `CryptoKey` to auth one final `DELETE /sync/{legacySyncToken}`) and disabling the legacy session path on the server once no legacy blobs remain — is orthogonal to both excluded issues and closes a permanent data-exposure window that the current migration flow silently leaves open.

## Validation

**CONFIRMED — High severity. Genuine, exploitable data-retention defect.**

### Verification

All code claims verified against source:

**Q1 — No Step 4 DELETE in `migrate()`:** Confirmed. `src/sync/migrate.ts` lines 31-74 show three steps (pull, generate PQ credentials, push) with no `DELETE /sync/{legacySyncToken}` call anywhere. The legacy `CryptoKey` is held in memory only through Step 1 (line 38: `const syncToken = await deriveSyncToken(creds.cryptoKey)`); after `putCredentials(db, pqCreds)` overwrites credentials in Step 2, no code path retains a reference to the old key that could be used to authenticate a deletion.

**Q2 — `deleteRemote()` hard-gates on `isLegacyCredentials`:** Confirmed. `src/sync/server.ts` line 116: `if (!creds || isLegacyCredentials(creds)) return { deleted: false };`. The function returns immediately without making a network call when called with legacy credentials, and there is no alternative deletion function for legacy blobs anywhere in the codebase.

**Q3 — `handleSessionLegacy` is fully functional and never fenced:** Confirmed. `sync-server/handlers/session.ts` lines 70-90 implement the full legacy session flow: validate `syncToken` hex-format (line 79), verify it against the stored nonce (lines 83-85), issue a 24-hour `sessionToken` (lines 87-88). The path is reached whenever the request body lacks an `mldsaPublicKey` field (line 22 of the same file). There is no server-side flag, migration check, or TTL that disables this path for accounts that have migrated to PQ.

**Q4 — `handleChallenge` still accepts legacy `syncToken`:** Confirmed. `sync-server/handlers/challenge.ts` lines 19-23 accept `syncToken` in the request body and use it as `identity` for the nonce. The challenge-response pair for the legacy path is therefore fully operable.

**Q5 — Server blob persists indefinitely under `{legacySyncToken}.enc`:** Confirmed. `sync-server/handlers/blob.ts` lines 59-79 show the count-cap guard only rejects *new* blobs (those for identities not yet having a file). Existing blobs are never evicted by the admission cap. No TTL or cleanup job exists in the server code. The file named `{legacySyncToken}.enc` will remain on disk unless the corresponding DELETE endpoint is called — which nothing ever does.

**Q6 — `deriveSyncToken` is a public, deterministic SHA-256 of the raw AES key:** Confirmed. `src/sync/credentials.ts` lines 27-33. Anyone holding the raw AES key can recompute the `syncToken` without any app interaction and use it to authenticate to the legacy challenge-response path.

**Q7 — Distinct from both exclusions:** Confirmed.
- Exclusion 1 ("Documented HMAC challenge-response is unimplemented") concerns the *quality* of the legacy auth protocol. This finding is about a migration flow that leaves a blob permanently behind after the user intentionally moves to stronger auth. Hardening the challenge-response would not cause the legacy blob to be deleted.
- Exclusion 2 ("Sync AES-256 master key stored in IndexedDB is exportable") concerns the *client-side key storage*. This finding concerns the *server-side retention* of ciphertext that remains decryptable via any historical exfiltration of the key. Making the key non-extractable going forward does not retroactively remove the orphaned legacy blob.

### Severity Rationale

**High** (not Critical):

- **Impact is severe and permanent.** The orphaned blob contains the user's full pre-migration `AppState`: profile (including `displayName` and `email`), all packs, chores, completions with answer values and XP history, and quick-answer sets. The blob is never deleted, so the exposure window is indefinite.
- **The attack persists after migration.** A user who completes PQ migration is given a false sense of security. Their current data is protected by PQ credentials, but their entire pre-migration snapshot remains accessible to anyone who ever obtained the legacy AES key.
- **Exploitation requires possession of the legacy AES key.** This is a realistic precondition: prior XSS (as tracked by [[SEC-000025]]), an old exported key file still on disk, an old device backup, or any previously compromised device with the pre-migration app installed. It is not a zero-click or network-only attack.
- **Not Critical** because the attacker cannot obtain the legacy blob without first having the AES key; raw network access to the server without the key is insufficient (the challenge-response requires `syncToken = SHA-256(rawKey)`, which cannot be reversed from the `syncToken` alone).

The fix is clear and self-contained: add a Step 4 to `migrate()` that, while the legacy `CryptoKey` is still in memory, derives `syncToken`, authenticates one final legacy session, issues `DELETE /sync/{syncToken}`, and only then overwrites the credentials. The server's DELETE handler in `blob.ts` lines 89-93 already supports this. No server changes are required for the deletion itself; only the client migration flow needs the fourth step.

## Fix Plan

This issue is tracked and will be addressed in GitHub issue #65. The code changes implemented as part of this security report have been reverted; the fix will be delivered through that issue.

The original proposed fix was to add a **Step 1b** to `migrate()` in `src/sync/migrate.ts` that, while the legacy `CryptoKey` and legacy `sessionToken` are still in scope, issues a `DELETE /sync/{legacySyncToken}` with the legacy `Authorization: Bearer {sessionToken}` header. This must run **before** Step 2 (`putCredentials(db, pqCreds)`) because after the credential swap the legacy `CryptoKey` is no longer retrievable from the DB.

### Concrete changes in `src/sync/migrate.ts`

1. Restructure the current Step 1 block so the derived `syncToken` and `sessionToken` remain in scope until after the DELETE call. Suggested shape:

   ```ts
   let legacyDeleted = false;
   if (SYNC_URL) {
     try {
       const syncToken = await deriveSyncToken(creds.cryptoKey);
       const sessionToken = await legacyFetchSessionToken(syncToken);
       if (sessionToken) {
         // Step 1: best-effort final pull (existing logic, unchanged)
         const res = await fetch(`${SYNC_URL}/sync/${syncToken}`, {
           headers: { Authorization: `Bearer ${sessionToken}` },
         });
         if (res.ok) {
           /* … existing decrypt/import block … */
         }
         // Step 1b: authoritative delete of the legacy blob
         try {
           const delRes = await fetch(`${SYNC_URL}/sync/${syncToken}`, {
             method: 'DELETE',
             headers: { Authorization: `Bearer ${sessionToken}` },
           });
           // 204 = deleted, 404 = already gone — both count as success
           if (delRes.status === 204 || delRes.status === 404) legacyDeleted = true;
         } catch { /* leave legacyDeleted=false; will retry next run */ }
       }
     } catch { /* pull failure does not block delete attempt */ }
   }
   ```

2. **Gate the credential swap on `legacyDeleted` when the server is reachable.** If `SYNC_URL` is set and `legacyDeleted === false`, do **not** call `putCredentials(db, pqCreds)`. Instead `return` early so the next app launch will retry the migration (which still holds the legacy key in IndexedDB). This preserves at-least-once deletion semantics: the legacy blob is guaranteed to be removed before the client forgets the key.

3. If `SYNC_URL` is unset (offline / no server configured), skip the delete gate and proceed with the credential swap as today — there is no orphan blob to delete because the client never pushed one.

4. No server-side changes are required. The DELETE handler in `sync-server/handlers/blob.ts` lines 89-93 already returns 204 on success and 204 on ENOENT.

5. The `legacyFetchSessionToken` helper is already local to `migrate.ts` and does not need to be exported or duplicated.

### Notes / trade-offs

- We deliberately keep the retry loop implicit (relies on the user reopening the app) rather than adding an in-session retry, because Step 1 already has best-effort semantics for transient network failures and adding synchronous retries risks blocking the migration modal.
- Exclusion #1 (weak legacy auth) and exclusion #2 (extractable IndexedDB key) are unchanged — this fix simply eliminates the **window during which** those weaknesses translate into a permanent decryptable ciphertext on the server.
- The `handleSessionLegacy` server path remains enabled (out of scope; would break users mid-migration if disabled here). Once telemetry confirms all users have migrated, a follow-up ticket can gate `handleSessionLegacy` behind a feature flag.
