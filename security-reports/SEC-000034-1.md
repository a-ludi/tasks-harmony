# Compress-then-encrypt in sync blob enables BREACH/CRIME plaintext recovery via ciphertext length side channel

**Status:** DONE
**Bug ID:** [[SEC-000034]]
**Severity:** Low

## Location

- `/home/claude/projects/tasks-harmony/src/sync/encrypt.ts` lines 50–59 (`encryptState`) — gzip-compresses the JSON plaintext, then AES-GCM-encrypts the compressed output.
- `/home/claude/projects/tasks-harmony/src/sync/server.ts` lines 69–97 (`push`) — calls `encryptState(key, appState)` and PUTs the resulting blob to `/sync/{syncToken}`.
- `/home/claude/projects/tasks-harmony/sync-server/handlers/blob.ts` lines 40–109 — stores the blob on disk with its exact (compressed+encrypted) length, which is trivially observable by anyone with read access to the sync directory, by the sync-server operator, and by any on-path observer that can measure request body size.

## Description

`encryptState` performs classic **compress-then-encrypt** (`compress(state) → AES-GCM`). AES-GCM ciphertext length equals plaintext length + 16 (auth tag), so the on-wire and on-disk blob size is a direct function of the *compressed* plaintext size. This is the exact primitive that enables the CRIME (2012) and BREACH (2013) attack families: if an attacker can inject chosen prefixes into the plaintext and then observe the resulting compressed-and-encrypted size, they can recover unknown secrets in the plaintext byte-by-byte, because gzip's LZ77 back-references shrink whenever the injected guess matches a nearby secret.

For this application, the two attacker capabilities are both realistic:

1. **Chosen plaintext injection into `AppState`.** Any of the following user-triggered actions writes attacker-controlled strings into the `AppState` object that is later serialized and gzip-compressed by `encryptState`:
   - Importing a CDP pack (`src/store/index.ts` `importCDP` → `fetchCDP`, which reads attacker-controlled `title`, `description`, `author`, `license`, chore `title`, chore `description`, question `prompt`, question `choices[].label`, etc. from a URL the attacker chooses; the JSON schema for these fields has no length caps and permits arbitrary UTF-8).
   - A shared/synced pack description or chore description edited by a second device the attacker controls (e.g., a coerced key-file swap or a family/shared account).
   - Any UI field that accepts free-form text and lands in a store that `exportAppState` includes.
2. **Ciphertext length observation.** After each `push`, the blob is written to `/data/{syncToken}.enc` with its exact length. The sync-server operator can `stat` the file. An on-path observer can measure the PUT body size (nginx `client_max_body_size 1m` sees the length; even without body logging, request lengths appear in most access-log formats and in TLS record sizes). The `Content-Length` header is also emitted by `fetch()` for `PUT` with a `Uint8Array` body.

With both capabilities, a BREACH-style oracle recovers any target secret that lives elsewhere in the same `AppState`. The concretely valuable secrets present in the plaintext today are:

- `profile.email` (schema `src/schemas/appState.schema.json` line 158) — a PII field the user might reasonably assume is protected by the sync encryption.
- `profile.displayName`.
- Any chore/question/completion answer content the user considers private (medical logs, journal-style completions, quantities, timestamps of sensitive activities).
- `syncState.lastSyncedAt` and other timing metadata that leak sync frequency to a non-server on-path attacker.

The attack does not require breaking AES-GCM, does not require the AES key, and works even though the compression happens before encryption "inside" the encrypted envelope — precisely because compression is a distinguisher that survives the encryption step as a length observation.

Standard mitigations, none of which are currently applied:

- **Do not compress before encryption when any part of the plaintext is attacker-influenceable.** For a chore tracker whose plaintext is a few tens of KB, dropping gzip entirely costs at most a few times the bandwidth and eliminates the class of attack.
- If compression is retained, **pad the ciphertext to a fixed size or to a coarse bucket (e.g. next multiple of 16 KiB)** before writing to storage / sending; this destroys the length-side-channel signal. The current blob is capped at `MAX_BYTES = 1 MiB` (`sync-server/handlers/blob.ts` line 6), so padding all blobs to 1 MiB is affordable.
- Separate secrets that must not leak (e.g. `profile.email`) from attacker-influenceable fields into a distinct encrypted envelope with independent length so that CRIME/BREACH on the chore payload cannot leak profile data.

Notes on scope:

- The two existing exclusions cover (1) the missing HMAC challenge-response and (2) the extractable AES key in IndexedDB. This finding is orthogonal: it is a *cryptographic-envelope* weakness in the blob itself, not a key-management or authentication weakness, and holds even if both existing issues were fixed and even if the AES key were non-extractable.
- The corresponding compress-then-encrypt pattern also lives on the decrypt side (`decryptState` at `src/sync/encrypt.ts` lines 61–67, decompressing after decrypting) — the fix must be applied symmetrically at both push and pull.

## Validation

**CONFIRMED — Low severity. Genuine cryptographic weakness; exploitation requires compound attacker capabilities.**

### Verification

**Q1 — Compress-then-encrypt confirmed:** `src/sync/encrypt.ts` lines 50–59 verify the claim exactly. `encryptState` calls `compress(plaintext)` via the `CompressionStream('gzip')` API, then feeds the result directly to `crypto.subtle.encrypt` with AES-GCM. The resulting blob is `iv (12) + ciphertext (compressed_len + 16)`, so the blob size is a direct function of the gzip-compressed plaintext size. The pattern is confirmed.

**Q2 — Ciphertext length is observable:** The blob is written to disk at `join(BLOB_DIR, token + '.enc')` with its exact byte length (`blob.ts` line 108). The PUT body length is sent as `Content-Length` from `fetch()` in `server.ts` line 50. The sync server operator and any on-path observer with access to TLS-layer metadata or server logs can observe the length. Confirmed.

**Q3 — Attacker-controlled plaintext injection:** CDP pack import via `importCDP` can pull attacker-controlled string fields (title, description, chore titles, question prompts/choices) into `AppState`. These fields have no length cap in the schema (`src/schemas/appState.schema.json`). Any such field that lands in the store will be included in the next `exportAppState` call and thus compressed in the next push. Injection capability confirmed.

**Q4 — Compound attacker requirement assessed:** A classic BREACH oracle requires the adversary to (a) repeatedly inject *varying* chosen prefixes into the plaintext *and* (b) observe the resulting ciphertext length *each time*. In this application these two capabilities must be held by the same adversary simultaneously:
- A passive on-path observer can see blob sizes change over sync cycles but cannot drive the oracle (they cannot cause the user to re-import different CDP content).
- A malicious CDP server can serve different content on different fetches, but only if the user voluntarily re-imports. There is no auto-refresh of CDPs; each injection requires a user action.
- A shared-sync-account attacker already holds the AES key by assumption, which renders the oracle moot.

The compound requirement materially raises exploitation complexity compared to classic BREACH (which is a fully automated server-side attack). Practical exploitation requires either (a) an on-path TLS-decrypting adversary that also controls the CDP origin, or (b) social engineering the user into repeated CDP re-imports. Neither is zero-click or fully remote.

**Q5 — Duplicate check:** [[SEC-000022-0]] (cache headers, DISCARDED) and [[SEC-000025-3]] (extractable key in IndexedDB) are both unrelated to compression side-channels. No prior report covers this finding.

### Severity Rationale

**Low** (not Medium or High) because:

- **Genuine cryptographic weakness:** Compress-then-encrypt is a documented vulnerability class (CRIME 2012, BREACH 2013) and the code exhibits the exact pattern. The theoretical attack is sound.
- **Exploitation requires compound adversary capabilities:** The oracle requires injection control *and* length observation simultaneously. No single-position attacker (network observer, malicious CDN host, sync server operator) holds both without additional steps.
- **No automated exploitation path:** Unlike web BREACH attacks (which exploit server-side compression on every HTTP request), here each injection step requires a user action (CDP import). The attacker cannot drive the oracle automatically.
- **Concrete secrets at risk:** `profile.email` and other private fields genuinely live in the same compressed plaintext, so if the oracle were successfully driven, sensitive data could be recovered. This prevents further downgrade.
- **Straightforward mitigation available:** Dropping gzip compression eliminates the class entirely with minimal bandwidth cost for a chore-tracker payload. Alternatively, fixed-size blob padding would destroy the side-channel signal without any protocol change.

The finding is real and should be fixed, but the exploitation barrier is substantially higher than the report's framing implies. Low severity reflects a genuine, theoretically exploitable weakness with high practical exploitation complexity.

## Fix Plan

Eliminate the compress-then-encrypt primitive by removing gzip compression from `encryptState` entirely. Blobs are already capped at 1 MiB by the sync server (`sync-server/handlers/blob.ts` line 6) and typical `AppState` payloads for this chore-tracker are on the order of tens of KiB — the bandwidth cost of shipping raw UTF-8 JSON instead of a gzipped payload is minor compared to eliminating the BREACH/CRIME attack class.

The fix is symmetric across encrypt and decrypt in `src/sync/encrypt.ts`.

**Changes to `src/sync/encrypt.ts`:**

1. `encryptState` (lines 50–59): drop the `await compress(plaintext)` call. AES-GCM-encrypt the raw UTF-8 JSON bytes directly. New shape:
   - `plaintext = TextEncoder.encode(JSON.stringify(state))`
   - `ciphertext = AES-GCM(key, iv, plaintext)` — no compression step
   - blob layout `iv(12) || ciphertext(plaintext.length + 16)` is unchanged; only the meaning of the encrypted payload changes (raw JSON, not gzip).

2. `decryptState` (lines 61–67): after `crypto.subtle.decrypt` returns the payload, add gzip-magic detection for backward compatibility with blobs written by older clients still in circulation on the sync server. Concretely:
   - Compute `payload = new Uint8Array(await crypto.subtle.decrypt(...))`.
   - If `payload.length >= 2 && payload[0] === 0x1f && payload[1] === 0x8b`, treat the payload as legacy gzipped JSON and pass it through the existing `decompress()` helper before `JSON.parse`. The existing 10 MiB `MAX_DECOMPRESSED_BYTES` guard stays in place.
   - Otherwise, treat the payload as raw UTF-8 JSON and `JSON.parse` directly.
   - No fragile "try-then-fall-back" is needed because gzip has a stable two-byte magic header (`0x1f 0x8b`) and raw JSON always begins with `{` (`0x7b`) — the two byte spaces cannot collide.

3. Keep the `compress` helper deleted (or leave it unused and stripped by dead-code elimination). Keep the `decompress` helper — it is still needed for the legacy-blob path in `decryptState`.

**Files touched:** `src/sync/encrypt.ts` only. All callers (`src/sync/export.ts`, `src/sync/import.ts`, `src/sync/server.ts`) keep their existing signatures and require no changes.

**Backward compatibility:** Any blob already on the sync server that was encrypted by a pre-fix client will still decrypt correctly: the magic-byte check routes it through `decompress()`. New blobs written by a post-fix client contain raw JSON and skip decompression. Once every client has pushed at least once after the fix, all live blobs are raw JSON, but the legacy branch is cheap to keep indefinitely.

**Non-goals / deliberately excluded:**
- No fixed-size padding on the blob. Removing compression already destroys the CRIME/BREACH oracle; padding would add complexity without addressing a distinct threat here. The `Content-Length` of a raw-JSON `AppState` is still a coarse size signal, but it is no longer a compression-driven differential oracle.
- No change to the wire format header/versioning. The blob layout is unchanged (`iv || ciphertext`); disambiguation happens on the decrypted-plaintext byte level via the gzip magic, which is unambiguous against JSON.
- No key rotation, no re-encrypt-on-read migration. Legacy blobs stay readable until the owning client next pushes.
