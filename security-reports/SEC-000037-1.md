# Legacy session code path lets any attacker who knows a PQ user's syncId hijack their sync blob, bypassing ML-DSA authentication entirely

**Status:** DONE
**Bug ID:** SEC-000037
**Severity:** Critical

## Location
- `sync-server/handlers/challenge.ts` lines 14-27 (identity acceptance)
- `sync-server/handlers/session.ts` lines 13-25 (path dispatch) and lines 70-90 (`handleSessionLegacy`)
- `sync-server/handlers/blob.ts` lines 15-27 (session -> blob authorization)

## Description

The sync server offers two authentication code paths that share the same nonce store and the same blob namespace but are dispatched purely on client-supplied fields:

1. `handleChallenge` (`sync-server/handlers/challenge.ts`) accepts either
   `{ syncId }` (PQ) or `{ syncToken }` (legacy). Both are 64-char hex strings
   and both are stored in Redis under the identical key `nonce:${nonce} =
   <identity>`. The server does not record which flavour the identity is.

2. `handleSession` chooses the PQ or legacy path solely on whether the body
   contains `mldsaPublicKey` (line 19). If it does not, `handleSessionLegacy`
   runs and simply compares `storedSyncToken !== syncToken` (line 85) — no
   cryptographic authentication, the identity itself is treated as a bearer
   secret.

3. The resulting session token grants the holder GET/PUT/DELETE on the blob at
   `/sync/<identity>` (`blob.ts` line 27).

For **legacy** users this is documented in exclusion #1 (identity == bearer
secret). For **PQ** users this is catastrophic, because the PQ `syncId` is by
design NOT secret — it is `SHA-256(mlkemPublicKey || mldsaPublicKey)`, derived
entirely from public keys (`src/sync/credentials.ts` `deriveSyncId`, lines
119-125) and transmitted on every sync request as part of the URL path
(`src/sync/server.ts` line 63: `fetch(\`${SYNC_URL}/sync/${syncId}\`, ...)`).

The entire security value of the ML-DSA challenge/response — the reason the PQ
migration exists — is that only the holder of `mldsaPrivateKey` should be able
to authenticate to a `syncId`. That guarantee is nullified by the legacy path,
which the attacker can reach at will.

### Exploit

Given any PQ user Alice with syncId `H` (public knowledge — visible in URLs,
proxy metadata, service worker cache entries, shared devices, browser history,
CSP reports, or any observer of Alice's traffic to `${VITE_SYNC_URL}`):

```
# 1. Attacker requests a challenge using the LEGACY body shape
POST /sync/challenge
{ "syncToken": "<H>" }
-> 200 { "nonce": "<n>" }

# 2. Attacker completes session on the LEGACY path
POST /sync/session
{ "nonce": "<n>", "syncToken": "<H>" }
-> 200 { "sessionToken": "<S>" }
# handleSessionLegacy only checks storedSyncToken (= H) === body.syncToken (= H).
# No signature, no ML-DSA, no possession-of-key check.

# 3. Attacker operates on Alice's blob
DELETE /sync/<H>       Authorization: Bearer <S>    -> 204  # wipes Alice's backup
PUT    /sync/<H>       Authorization: Bearer <S>    -> 204  # replaces with attacker chosen bytes
GET    /sync/<H>       Authorization: Bearer <S>    -> 200  # exfiltrates the ciphertext
```

### Impact

- **Integrity / availability**: attacker can permanently DELETE Alice's
  server-side backup or overwrite it with garbage. On her next `pull()`
  (`src/sync/server.ts` line 138) the client will either 404 or fail
  `decryptStatePQ` / `validateAppState` and silently discard — the user has
  lost their remote copy, and if the local device is later lost/wiped there is
  no recovery.
- **Confidentiality of ciphertext**: attacker can download the encrypted blob
  and keep it forever. If Alice's ML-KEM secret key later leaks (device
  seizure, malware, future cryptanalytic advance) the attacker already has the
  ciphertext ready to decrypt. This turns any casual observer of a syncId
  into a "harvest-now, decrypt-later" adversary against a PQ user without
  needing any server compromise or MitM.
- **Complete bypass of the entire PQ auth scheme** shipped in commits
  `443c7ba` / `af75bfc` / `8423096`. Every migrated user is exposed the
  moment their syncId is observed anywhere.

### Why it is not covered by existing exclusions

- Exclusion #1 describes the *legacy* channel using a bearer syncToken. This
  finding is about *PQ* accounts being attackable through that same channel
  even though they never opted into bearer semantics — the ML-DSA signature is
  simply skipped because the code path is chosen by the attacker's request
  shape, not by the identity's registered scheme.
- Exclusion #2 (exportable IndexedDB master key) is a client-side XSS
  concern; this attack requires no XSS and works against fully migrated PQ
  users whose devices are uncompromised.
- Exclusion #3 (orphan legacy blob after migration) covers the
  pre-migration ciphertext left behind; this finding targets the *current*
  post-migration blob under the PQ syncId.

### Root cause

Two independent authentication schemes are multiplexed on the same
identity/blob namespace with client-controlled dispatch and no server-side
binding of "this identity is a PQ identity, therefore the legacy path is
forbidden for it". The fix must either (a) tag identities in Redis / a
persistent store as PQ-only once first seen with a valid ML-DSA signature and
reject the legacy path for tagged identities, (b) partition the namespaces
(e.g. `/sync/pq/<id>` vs `/sync/legacy/<id>`) with the legacy route entirely
removed once migration is complete, or (c) drop `handleSessionLegacy` /
`syncToken` challenge acceptance now that PQ is the only supported client
scheme.

## Validation

**CONFIRMED — Critical severity. Genuine, fully exploitable authentication bypass.**

### Verification

All code claims verified against source:

**Q1 — `handleChallenge` accepts both `syncId` (PQ) and `syncToken` (legacy) with no type tagging:**
Confirmed. `sync-server/handlers/challenge.ts` lines 15-24 accept either field and store the value as `identity` under `nonce:${nonce}` in Redis. There is no flag recorded to distinguish which flavour was used; both paths share the identical Redis key format.

**Q2 — `handleSession` dispatches to `handleSessionLegacy` purely on the absence of `mldsaPublicKey` in the request body:**
Confirmed. `sync-server/handlers/session.ts` line 19: `if ('mldsaPublicKey' in body)` — the entire PQ path is gated on an attacker-controlled field. An attacker who omits it falls through to the legacy path unconditionally, regardless of what identity the nonce was issued for.

**Q3 — `handleSessionLegacy` only compares `storedSyncToken !== syncToken` — no cryptographic check:**
Confirmed. Lines 83-85 of `session.ts`: `getDel` retrieves the stored identity, then `if (storedSyncToken !== syncToken) return Unauthorized`. This is a string equality check between what the server retrieved from Redis (which for a PQ-path challenge request is the `syncId`, a public value) and what the attacker supplied as `syncToken`. An attacker who issues a challenge with `{ syncToken: "<syncId>" }` stores `syncId` in Redis, then sends `{ nonce, syncToken: "<syncId>" }` to the legacy session endpoint — these two values are identical, so the check passes and a 24-hour `sessionToken` is issued.

**Q4 — The `syncId` is a public, non-secret value derived entirely from public keys:**
Confirmed. `src/sync/credentials.ts` `deriveSyncId` (lines 119-125): `SHA-256(mlkemPublicKey || mldsaPublicKey)`. The public keys are, by design, not secret. The `syncId` appears in all blob operation URLs (`src/sync/server.ts` line 63: `fetch(\`${SYNC_URL}/sync/${syncId}\`, ...)`), making it observable by any network intermediary, proxy log, browser history entry, or CSP report.

**Q5 — The session token issued via the legacy path grants full GET/PUT/DELETE access to the PQ user's blob:**
Confirmed. `sync-server/handlers/blob.ts` lines 25-27: `authenticate()` retrieves the identity stored under `session:${sessionToken}` and line 27 checks `storedSyncToken !== token` — where `token` is the URL path segment. The attacker's session stores `syncId` as the identity (see Q3 above), and the blob path is `/sync/${syncId}`, so the authorization check passes. All three methods (GET, PUT, DELETE) are then reachable.

**Q6 — Not a duplicate of any completed report:**
- **SEC-000022-0** (Cache-Control header): completely unrelated.
- **SEC-000025-3** (Extractable IndexedDB AES key): that finding requires prior XSS to exfiltrate the key, concerns the legacy AES encryption scheme, and targets plaintext confidentiality. This finding requires zero client-side access — only knowledge of the `syncId`, which is a public URL component — and directly defeats the ML-DSA signature authentication that was the entire purpose of the PQ migration.
- **SEC-000036-2** (Orphaned legacy blob): that finding is about pre-migration ciphertext left on the server under the old `syncToken`. This finding is about the *current* PQ-protected blob under the PQ `syncId` being writable/readable/deletable by anyone who knows the `syncId`, without ever presenting a valid ML-DSA signature.

The three exclusion titles in `exclusions.txt` describe different attacks; this finding is distinct.

### Severity Rationale

**Critical** (not merely High):

- **Authentication is completely bypassed with zero prerequisites.** No XSS, no device compromise, no prior key exfiltration is needed. The attacker only needs to observe the `syncId`, which appears in HTTP request URLs that any network intermediary sees.
- **The attack is fully network-reachable and trivially scriptable.** Two HTTP requests to the public sync server endpoint are sufficient to obtain a 24-hour session token that grants unrestricted access to any PQ user's backup.
- **Impact is total across all three pillars.** Integrity (overwrite or DELETE wipes the user's only remote backup), availability (permanent data loss if local device is lost after wipe), and confidentiality (harvest-now, decrypt-later against the ML-KEM–encrypted blob).
- **Nullifies the entire PQ migration.** The migration was designed to guarantee that only the holder of `mldsaPrivateKey` can authenticate. Every migrated user is equally exposed the moment their `syncId` appears in a URL — which occurs on every sync operation.
- **No server-side mitigation exists.** There is no per-identity scheme tag, no rate-limiting on the challenge endpoint, and no age-gating on the legacy path. The attack can be repeated at will as long as the legacy path remains live.

## Fix Plan

Tag the identity stored under `nonce:${nonce}` with the auth flavour the
challenge request took, then, at session issuance, require the flavour tag to
match the code path being executed. This prevents an attacker who observes a
PQ `syncId` from replaying it through the legacy session path (or vice
versa), because the tag written at challenge time is bound to the request
shape used at challenge time and cannot be changed by the attacker at
session time.

### Changes

1. **`sync-server/handlers/challenge.ts`** — after selecting `identity`, also
   record a `flavour` string:
   - if the body arrived with `syncId`, `flavour = 'pq'`
   - if the body arrived with `syncToken`, `flavour = 'legacy'`

   Store the tagged value in Redis:
   ```ts
   await redis.set(`nonce:${nonce}`, `${flavour}:${identity}`, 'EX', 60, 'NX');
   ```
   (Both flavours are known-safe prefixes — colon is not a hex character, so
   parsing back is unambiguous.)

2. **`sync-server/handlers/session.ts`** — introduce a small helper that
   `getDel`s the nonce and returns `{ flavour, identity } | null`, splitting on
   the first `:`. Both `handleSessionPQ` and `handleSessionLegacy` call this
   helper and reject with `401 Unauthorized` when the flavour does not match
   the path they are running on:
   - `handleSessionPQ` accepts only `flavour === 'pq'`
   - `handleSessionLegacy` accepts only `flavour === 'legacy'`

   Downstream, the stored identity continues to be written into
   `session:${sessionToken}` **without** the flavour prefix, so `blob.ts`
   (which compares the session's stored value against the URL path segment
   `syncId` / `syncToken`) is unaffected and requires no change.

3. Legacy challenge/session records already in Redis at deploy time (max age
   60 s TTL) will fail the new flavour check and force one retry from the
   client. This is acceptable — the sync client retries on 401 (see
   `authorizedFetch` in `src/sync/server.ts`, line 72).

### Why this is minimal

- No new persistent store, no per-identity registry, no client-visible
  contract change: the wire format for both challenge and session requests is
  unchanged.
- Blob namespace and session storage untouched — the flavour tag lives only
  inside the 60-second nonce record.
- The client already only ever uses the PQ path for authenticated sync
  (`src/sync/server.ts:22-49` builds a `syncId` challenge; the legacy path in
  `src/sync/migrate.ts:13-29` is only invoked with a genuine legacy
  `syncToken` derived from the old AES key). Neither client caller crosses
  flavours, so no client change is required.

## Implementation Notes

### RED phase (failing test before the fix)

Wrote test `'rejects legacy session request when the nonce was issued for a PQ syncId'` in `sync-server/handlers/session.test.ts` under the new describe block `'handleSession — cross-flavour attack refusal'`.

Test setup mocks `getDel` to return untagged syncId (`'b'.repeat(64)`), which is what today's `challenge.ts` writes. The attacker tries to replay this syncId through the legacy session path by supplying it as `syncToken`.

**Failure output before fix:**
```
Expected: 401

      at <anonymous> (/home/claude/projects/tasks-harmony/sync-server/handlers/session.test.ts:112:24)
(fail) handleSession — cross-flavour attack refusal > rejects legacy session request when the nonce was issued for a PQ syncId
```

The test fails because the current code's string equality check (`storedSyncToken !== syncToken`) passes when both are the same value, issuing a session token (200) instead of rejecting (401).

### GREEN phase (passing test after fix)

Applied fix as specified in Fix Plan:

1. **`sync-server/handlers/challenge.ts`** — Modified to tag identities with flavour before storing in Redis:
   - Detects `syncId` vs `syncToken` in the request body
   - Sets `flavour = 'pq'` for `syncId` or `flavour = 'legacy'` for `syncToken`
   - Stores value as `${flavour}:${identity}` in Redis

2. **`sync-server/handlers/session.ts`** — Added helper function `getAndDeleteNonce` that:
   - Retrieves and deletes the nonce from Redis
   - Parses the `flavour:identity` format by splitting on the first `:`
   - Returns `{ flavour, identity }` or `null` if parsing fails or nonce doesn't exist
   - Both `handleSessionPQ` and `handleSessionLegacy` now call this helper and validate the flavour matches the code path being executed:
     - `handleSessionPQ` rejects with 401 if `flavour !== 'pq'`
     - `handleSessionLegacy` rejects with 401 if `flavour !== 'legacy'`
   - Session storage continues to use the untagged identity, so `blob.ts` requires no changes

3. **Updated test expectations:**
   - `sync-server/handlers/challenge.test.ts` — Updated assertions to expect flavour-prefixed values (`'legacy:' + SYNC_TOKEN` and `'pq:' + SYNC_ID`)
   - `sync-server/handlers/session.test.ts` — Updated all existing mocks to return the tagged form
   - Added symmetric test `'rejects PQ session request when the nonce was issued for a legacy syncToken'` to verify both cross-flavour attack directions are blocked
