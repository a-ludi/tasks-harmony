# Unauthenticated session creation for arbitrary syncToken after HMAC removal

**Status:** DONE
**Bug ID:** SEC-000007
**Severity:** Medium

## Location

- `sync-server/handlers/session.ts`, lines 1–29 — `handleSession` accepts any `{nonce, syncToken}` without proof of syncToken ownership
- `sync-server/handlers/challenge.ts`, lines 1–8 — `handleChallenge` issues nonces to any caller with no authentication
- `src/sync/server.ts`, line 40 — syncToken is embedded in the URL path for every GET/PUT blob request (`/sync/${syncToken}`)

## Description

When SEC-000006 was fixed (removing the shared HMAC secret from the client bundle), the HMAC challenge-response was replaced with nonce-only authentication. The current `POST /sync/session` handler accepts a request body `{nonce, syncToken}` and — after verifying the nonce is valid and single-use — issues a session token granting full read/write access to the blob at `/sync/{syncToken}`. **No proof that the caller owns or controls the syncToken is required.**

The syncToken is `SHA-256(AES-GCM key)` — it appears verbatim as the URL path segment in every GET and PUT blob request (`/sync/{syncToken}`). This means it is recorded in:
- Nginx proxy access logs
- Server-side access logs
- Any CDN, load balancer, or reverse-proxy logs
- HTTPS endpoint logs visible to the server operator
- Browser history / developer tools network tab on the victim's own device

**Concrete attack path:**

1. An attacker learns a victim's syncToken (e.g., from server access logs, or by operating a malicious CDP pack that tricks the victim into visiting a page that logs the Referer header containing the app URL after a sync round-trip — though HTTPS makes this harder, server-side log access is sufficient).
2. Attacker calls `GET /sync/challenge` → receives a server-issued nonce (rate-limited to 5 req/min by nginx, but a single nonce is all that is needed).
3. Attacker calls `POST /sync/session` with `{nonce: "<valid nonce>", syncToken: "<victim's token>"}` → server verifies nonce is valid (consumed from Redis), issues sessionToken tied to the victim's syncToken.
4. Attacker calls `PUT /sync/{victim's syncToken}` with the sessionToken to **overwrite the victim's encrypted blob with garbage**, causing **permanent, silent data loss** for the victim (all tasks, completions, XP history destroyed).
5. Alternatively, attacker calls `GET /sync/{victim's syncToken}` to download the encrypted blob. The blob is AES-256-GCM encrypted so plaintext is inaccessible without the AES key, but the attacker has it for offline cryptanalysis attempts and for confirming the victim's sync identity.

**Why this is exploitable now (post-SEC-000006):**

The original HMAC design proved identity via `HMAC-SHA256(nonce, APP_SECRET)` — an attacker needed the shared secret. SEC-000006 correctly removed the secret from the bundle. However, the replacement "proof" is just presenting any server-issued nonce: any caller can get a nonce by calling `/sync/challenge`. The nonce proves "I recently called `/sync/challenge`" but proves nothing about ownership of the supplied `syncToken`. The nonce is the authentication token, and it is freely issuable to anyone.

**Impact:**

- **Integrity/Availability (High):** Any attacker who learns a victim's syncToken can overwrite or corrupt the victim's sync blob, causing irreversible data loss. Since the client's pull logic only imports data if `serverTs > localTs`, an attacker who pushes a blob with a future `lastSyncedAt` value could also trick the victim's client into importing garbage data — if the attacker knew the envelope format. Even without knowing the AES key, the attacker can PUT arbitrary bytes, causing decryption to fail and sync to silently break.
- **Confidentiality (Low to Medium):** The blob is E2E encrypted; plaintext is safe if the victim's AES key is not known. But downloading the blob leaks ciphertext for offline analysis.
- **Authentication bypass:** The authentication gate is structurally broken: any party that can call `/sync/challenge` and knows a syncToken can authenticate as that syncToken's owner.

**Root cause:** The nonce-only scheme provides no binding between the nonce and the claimed syncToken. A proper fix requires the client to demonstrate knowledge of the AES key (or a derivative) without transmitting the key. For example: `HMAC-SHA256(nonce, syncToken_raw_bytes)` using the syncToken as the key (since it is derived from the AES key, knowledge of the syncToken equals knowledge of `SHA-256(key)` which is still not the key itself), OR signing the nonce with a separate per-device keypair. A simpler approach: treat the syncToken itself as a bearer secret (do not put it in the URL), and use a separate opaque blob ID for the URL path.

## Validation

**CONFIRMED — genuine architectural vulnerability; Medium severity.**

### Question 1: Does `POST /sync/session` accept any `syncToken` paired with a valid nonce, with no ownership proof?

**Yes, confirmed.** `sync-server/handlers/session.ts` (lines 12–28) validates that `nonce` and `syncToken` are both 64-char hex strings, then atomically deletes the nonce from Redis (`redis.del`). If the nonce was present (i.e., server-issued and not yet consumed), it issues a `sessionToken` mapped to the caller-supplied `syncToken` in Redis (`session:{sessionToken}` → `syncToken`). There is no HMAC, no signature, no proof that the caller has ever interacted with the blob at `/sync/{syncToken}`. Any caller who can call `/sync/challenge` and then `/sync/session` with an arbitrary 64-char hex `syncToken` will receive a valid session token.

### Question 2: Is the `syncToken` actually logged in access logs?

**Yes, confirmed.** `src/sync/server.ts` line 40 constructs every blob request as `fetch(\`${SYNC_URL}/sync/${syncToken}\`, ...)`. The syncToken is a 64-char hex URL path segment. The nginx config at `nginx/sync-location.conf.template` does not include `access_log off` on the `/sync/[a-f0-9]{64}` location block, meaning nginx default access logging applies and the full URI (including the 64-char syncToken) is written to the access log on every GET and PUT. Any process or operator with read access to nginx logs can extract syncTokens from log lines.

### Question 3: Does the blob PUT handler check that the session token corresponds to the correct syncToken?

**Yes, but this does not mitigate the root cause.** `sync-server/handlers/blob.ts` lines 17–20 authenticate the request by looking up the session token in Redis to get the stored syncToken, then compare it to the URL path token (`storedSyncToken !== token` → 403). This cross-check is correct and necessary — it prevents a session issued for syncToken A from being used against blob B. However, it provides no protection against an attacker who obtained a session for the victim's syncToken in the first place (which the broken session handler permits). The blob handler's check is sound; the vulnerability is upstream in the session handler.

### Question 4: What is the actual threat model — who are the realistic attackers?

This is a **single-user personal PWA** (`CONTEXT.md`: "A single-user PWA for tracking recurring chores"). The design spec (`docs/superpowers/specs/2026-06-25-encrypted-server-sync-design.md`) confirms: "Multi-user / shared accounts" is explicitly out of scope. The intended deployment is a single operator self-hosting their own nginx + Docker Compose stack on a VPS.

In this model:
- **"Server operator" = "the user"** — so the "log reader can steal syncToken from nginx logs" scenario means the user attacks themselves. Not a realistic threat.
- **The realistic attacker** is a third party who has somehow gained (a) network access to the sync server endpoint (which is publicly exposed via nginx for the app to work) AND (b) knowledge of the victim's syncToken. The syncToken is 256 bits of entropy (SHA-256 of a 256-bit AES key), so brute force is computationally infeasible.
- **Plausible syncToken leak vectors for a realistic attacker**: log aggregation services (e.g., if nginx logs are shipped to a third-party SIEM or log service), backup tools that archive nginx logs, monitoring agents, or a compromised developer machine that has access to the server's log files. These are non-trivial but not purely theoretical — log forwarding to a less-trusted system is common operational practice.

The attack succeeds immediately once the attacker has the syncToken — no brute force, no further access to the server. The impact is permanent data destruction (overwrite blob with garbage) or blob exfiltration (ciphertext only; plaintext requires the AES key which is never server-side).

### Question 5: Is there any existing mitigation — e.g., is the syncToken embedded in the session token, or does the blob handler cross-check?

No existing mitigation closes the gap:
- The blob handler cross-check (Q3 above) is necessary but not sufficient — it prevents cross-token session reuse, not initial session theft.
- The nonce is rate-limited at the challenge endpoint (5 req/min per IP by nginx), but an attacker needs only **one** nonce, so rate limiting is not an effective mitigation here.
- The nonce is single-use and 60-second TTL, which prevents replay, but does not prevent a fresh challenge-session cycle.
- E2E encryption protects blob confidentiality (impact reduction only — attacker can still destroy data by overwriting).
- The syncToken has 256-bit entropy, preventing enumeration — the vulnerability only matters when the syncToken is leaked out-of-band.

### Severity: Medium

**Why not High/Critical:**
- This is a single-user self-hosted app. There is no large population of victims; the attack surface is one person's data.
- Exploiting this requires knowing the victim's syncToken (256-bit entropy — only obtainable via log access or other privileged position, not by any network-facing operation alone).
- Blob confidentiality is fully protected by AES-256-GCM E2E encryption; plaintext task data is not exposed.
- The app is designed for a scenario where the server operator is the only user, limiting real-world attacker opportunity.

**Why not Low:**
- The vulnerability is structurally complete — no ownership proof exists and none can be added by configuration; code must change.
- The syncToken is by design exposed in nginx access logs on every sync operation, creating a persistent leak surface that is hard to remediate operationally (log rotation doesn't help if logs are already forwarded).
- Impact of a successful attack is irreversible data destruction (all tasks, completions, XP history) with no server-side recovery path.
- The root cause is an architectural regression introduced when SEC-000006 removed HMAC without adding any equivalent ownership proof — the auth gate is now structurally weaker than it was designed to be, and the design spec (`docs/superpowers/specs/2026-06-25-encrypted-server-sync-design.md` section 4) explicitly specifies "HMAC proof" as the auth mechanism for `/sync/session`. The implementation no longer matches the design intent.

## Fix Plan

### Chosen approach: Option C — Bind nonce to syncToken at challenge time

**Why Option C over the others:**
- Option A (turn off nginx logging) hides the symptom but leaves the auth hole structurally open; any other log consumer still captures the syncToken and the attack path still works.
- Option B (move syncToken to a header) closes the log-exposure path but still leaves unauthenticated session creation intact — an attacker who learns the syncToken through any other channel can still exploit the broken session handler.
- Option C closes the root cause: it proves the caller who gets a nonce is the same caller who submits it at session time together with a specific syncToken. Because the nonce is single-use and server-generated, binding `nonce → syncToken` at issuance means only the party who registered that exact syncToken with the challenge can redeem it. No new secrets, no new endpoints, no crypto changes — three small edits.
- Option D adds client-side secret management complexity (generation, storage, migration) with no advantage over Option C for a single-user app.

### What changes

**1. `POST /sync/challenge` — accept syncToken in request body and bind it to the nonce**

The client already knows its syncToken before calling challenge (it derives it from the AES key on every sync). Change `handleChallenge` to:
- Parse a JSON body `{ syncToken: string }`.
- Validate syncToken is a 64-char hex string; return 400 if not.
- Store `nonce:${nonce}` → `syncToken` (the actual token value, replacing `"1"`) with the existing 60 s TTL.
- Return `{ nonce }` as before.

**2. `POST /sync/session` — verify the submitted syncToken matches the one stored with the nonce**

After deleting the nonce key from Redis (`redis.del`), the deleted key no longer holds just `"1"` — it now holds the bound syncToken. Change the delete call to `redis.getDel` so we retrieve-and-atomically-delete the stored value. Then compare it against the syncToken submitted in the session request body. If they don't match, return 401.

Concretely:
- Replace `redis.del(`nonce:${nonce}`)` with `redis.getDel(`nonce:${nonce}`)`.
- If the result is `null`, return 401 (nonce not found / already consumed — same as before).
- If the result does not equal the submitted `syncToken`, return 401 (syncToken mismatch — new check).
- Otherwise, proceed to issue the session token as today.

**3. `src/sync/server.ts` — send syncToken in the challenge request body**

The client call to `/sync/challenge` is a plain `GET` today. Change it to a `POST` with body `{ syncToken }`:

```ts
const chalRes = await fetch(`${SYNC_URL}/sync/challenge`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ syncToken }),
});
```

The `syncToken` is already in scope at that call site (it is a parameter of `fetchNewSessionToken`).

**Files to touch:**
- `sync-server/handlers/challenge.ts` — accept syncToken, store it as the nonce value
- `sync-server/handlers/challenge.test.ts` — update existing tests; add test for syncToken binding
- `sync-server/handlers/session.ts` — switch to `getDel`, check stored value equals submitted syncToken
- `sync-server/handlers/session.test.ts` — update existing mock; add test for mismatch rejection (see Test Plan)
- `src/sync/server.ts` — change challenge call to POST with syncToken body

**No nginx config changes needed.** The syncToken remains in the blob URL path (this is a separate concern; the auth bypass is fixed by the binding, and Option B's log-exposure aspect is a lower-severity residual risk acceptable at Medium severity for a self-hosted single-user app).

### Test Plan

**File:** `sync-server/handlers/session.test.ts`

**Test name:** `'returns 401 when submitted syncToken does not match the syncToken bound to the nonce'`

**How the test works:**

The mock for `redis.del` must become a mock for `redis.getDel` (since the implementation will switch to `getDel`). The mock should return the syncToken that was stored at challenge time. To test the mismatch case, the mock returns a *different* syncToken than what the attacker submits in the session request body.

```ts
it('returns 401 when submitted syncToken does not match the syncToken bound to the nonce', async () => {
  // Simulate: nonce was issued to the real owner (SYNC_TOKEN = 'a'.repeat(64))
  // but the attacker submits their own syncToken ('f'.repeat(64)) at session time
  const legitimateToken = 'a'.repeat(64);
  const attackerToken = 'f'.repeat(64);
  // Mock getDel to return the legitimate owner's token (what was stored at challenge time)
  mockGetDel.mockImplementationOnce(async () => legitimateToken);

  const nonce = randomBytes(32).toString('hex');
  const res = await handleSession(makeReq({ nonce, syncToken: attackerToken }));
  // FAILS before fix (getDel doesn't exist; del returns 1 → session issued for attacker token)
  // PASSES after fix (mismatch detected → 401)
  expect(res.status).toBe(401);
});
```

**Supporting change to the test file:**

The existing `mockDel` mock must be replaced with `mockGetDel` (returning the stored syncToken string instead of a numeric `1`), and the existing passing tests must be updated accordingly. For example the "nonce not found" test should mock `mockGetDel` returning `null` instead of `mockDel` returning `0`.

**Assertion that FAILS before fix:** `expect(res.status).toBe(401)` — currently the handler uses `redis.del` which returns an integer count; it would throw (or behave unexpectedly) if `getDel` is not yet used, and the nonce-only check passes → status 200.

**Assertion that PASSES after fix:** The handler calls `redis.getDel`, receives the legitimate owner's token, compares to the attacker's submitted token, finds a mismatch, returns 401.

### Code quality findings

**BLOCKER — Router not updated: `sync-server/index.ts` line 13 still routes `GET /sync/challenge` but the client now sends `POST /sync/challenge`**

The fix correctly updated `handleChallenge` to expect a POST body with `syncToken`, and `src/sync/server.ts` now sends a POST. However, `sync-server/index.ts` line 13 was not updated:

```ts
// Current (broken):
if (pathname === '/sync/challenge' && req.method === 'GET') return handleChallenge(req);

// Required:
```

As a result, a POST to `/sync/challenge` falls through to the 404 handler (no other branch matches), and the entire sync flow is broken in production.
