# AppState JSON Schema does not validate array items — malicious `.zip` backup can inject attacker-controlled `pack.sourceUrl` that triggers arbitrary fetch on next "Update from URL"

**Status:** DONE
**Bug ID:** SEC-000023
**Severity:** High

## Location

- `src/schemas/appState.schema.json` (lines 8, 33–37) — schema declares `packs`, `chores`, `completions`, `xpSettings`, and `quickAnswerSets` as `{"type": "array"}` with **no `items` clause**, and declares `profile`/`syncState` with only a `required` list and no `additionalProperties: false`, no per-property `type`.
- `src/schemas/validate.ts` — `validateAppState` compiles that schema unchanged.
- `src/components/profile/ProfilePage.tsx` (lines 101–118) — plaintext `.zip` backup import path calls `unwrapStateFromZip(zipBytes)` → `validateAppState(state)` → `importAppState(db, state)`.
- `src/sync/import.ts` (lines 7–28) — `importAppState` clears all object stores and `put`s every array entry into IndexedDB with no further sanitisation.
- `src/store/index.ts` (line 266) — `updateCDP` calls `fetchCDP(pack.sourceUrl)` on the value that came directly from the imported backup.
- `src/cdp/cdp-import.ts` (lines 44–45) — `fetchCDP` does `fetch(`${baseUrl}/__pack__.yaml`)` with no URL scheme/host allowlist.

## Description

`validateAppState` is the sole gatekeeper between a `.zip` backup file the user opens
via **Settings → Import** and the IndexedDB write in `importAppState`. The schema
enforces the top‑level object shape (`schemaVersion === 1`, all required keys present)
and does perform tight per‑item validation on the `questions` array — but for every
other array (`packs`, `chores`, `completions`, `xpSettings`, `quickAnswerSets`) the
schema is literally `{"type": "array"}`. Any object of any shape passes.

Concretely, an attacker who convinces a user to import a crafted
`tasks-harmony-backup-*.zip` (a plausible social‑engineering vector — the file
extension is user‑friendly, the export UI advertises the plain format, and — see
below — an initial-install user gets no confirmation prompt) can inject a
`Pack` entry such as:

```json
{
  "id": "morning-routines",
  "manifest": { "title": "Morning Routines" },
  "isPersonal": false,
  "importedAt": "2026-07-04T00:00:00Z",
  "updatedAt":  "2026-07-04T00:00:00Z",
  "sourceUrl":  "https://evil.example/packs/morning-routines"
}
```

`validateAppState` returns `valid: true`. `importAppState` writes it to the `packs`
object store. From the user's point of view the pack appears normal in the
sidebar, with a subtle "Update" button in the CDP Import dialog because
`sourceUrl` is set (`CDPImportDialog.tsx:100`,
`updatablePacks = packs.filter((p) => Boolean(p.sourceUrl))`).

**When the user later clicks that Update button**, `updateCDP(packId)` runs and
calls `fetchCDP(pack.sourceUrl)` — an unconstrained `fetch()` to the
attacker‑controlled URL. Attacker then serves a valid CDP manifest + chore
definitions of their choosing, and those become the user's chores /
questions / descriptions for the pack. Because the pack keeps its original
`id`, this is a **persistent CDP‑binding** — every subsequent update pulls from
the attacker.

Impact chain (all pre-existing behaviour once `sourceUrl` is planted):

1. **Persistent CDP hijack.** The user's pack is silently bound to an
   attacker‑controlled endpoint. Every "Update" pulls attacker content, even
   after the malicious `.zip` file itself has been deleted.
2. **Cross-tenant fetch / limited SSRF.** `fetch()` is invoked with the raw URL
   in the user's browser session. Requests to arbitrary intranet URLs
   (`http://192.168.…`, `http://router.local`) are dispatched from the user's
   network. Same-origin URLs (`https://tasks.example.com/admin/…`) can be read
   without CORS restriction, so any same-origin secret reachable via GET is
   exfiltratable to the attacker via the returned CDP body.
3. **Seeded-pack takeover.** Attacker can also inject
   `id: "personal"` (the seeded personal pack). `db.put('packs', pack)` on a
   `keyPath: 'id'` store overwrites in place, flipping `isPersonal: true` to
   `false` and grafting a `sourceUrl` onto the user's personal pack.
4. **Non-numeric or malformed `xpSettings` / `chore.recurrence`.** The absence
   of items validation on these arrays lets the attacker plant
   `recurrence.interval: 0` (produces `Infinity` in
   `getCurrentWindowIndex` at `src/chores/recurrence.ts:59`) or non-number
   `xpEarned` / `maxStreakMultiplier` values that propagate `NaN` throughout
   the XP and streak subsystems (`App.tsx:29` totals XP with `+`,
   `xp/calculator.ts:23` returns `Math.round(NaN * NaN * NaN)`).

**Prompt bypass on fresh install.** `ProfilePage.tsx:91–99` only shows the
"This will replace all your current data" confirmation when
`!isAppStatePristine(packs, completions)`. On a fresh install (no packs
imported yet, no completions), the import proceeds with **no confirmation
prompt at all**, so a first‑time user who is directed to import an "example
starter pack" backup receives the malicious pack silently.

The root cause is that `AppState.packs / chores / completions / xpSettings /
quickAnswerSets` are validated only for `type: "array"`. `Question` — the one
class of item that *does* have a strict `items` sub-schema — demonstrates the
intended pattern; the fix is to bring the other five arrays up to that same
bar and to add `additionalProperties: false` (plus per-property types) to
`profile` and `syncState`.

Note that the `.enc` (encrypted) import path is not exposed to this specific
attack: AES-GCM auth‑tag validation ensures only blobs the user themselves
encrypted with their own key can decrypt. This finding is scoped to the
plain-`.zip` backup input, which is the only untrusted‑file surface into
`importAppState`.

## Validation

**CONFIRMED — High severity.**

### Code verification

Every claim in the report was verified against the actual source:

**Schema gap confirmed.** `src/schemas/appState.schema.json` (line 8, 33–34, 37) declares `packs`, `chores`, `completions`, `xpSettings`, and `quickAnswerSets` as bare `{"type": "array"}` with no `items` clause. `questions` is the lone exception and has a full `items` sub-schema with `additionalProperties: false`. The gap is real and exactly as described.

**No sanitisation in importAppState.** `src/sync/import.ts` lines 7–28 clear all stores then `put` every element of each incoming array directly into IndexedDB — no field filtering, no type coercion, no allowlist. A crafted `sourceUrl` field inside a pack entry passes straight through.

**Unconstrained fetch via sourceUrl.** `src/store/index.ts` line 266 calls `fetchCDP(pack.sourceUrl)` using the value read from IndexedDB. `src/cdp/cdp-import.ts` line 44 does `fetch(`${baseUrl}/__pack__.yaml`)` with no scheme or host allowlist. Any URL (including `http://192.168.x.x`, `file://`, or attacker-controlled HTTPS) is accepted.

**Prompt bypass on fresh install confirmed.** `src/components/profile/ProfilePage.tsx` lines 91–99 show the `window.confirm` guard is conditional on `!isAppStatePristine(packs, completions)`. A user with no packs and no completions receives no confirmation prompt before the import overwrites their state.

**Encrypted path unaffected — report is correct.** The `.enc` path goes through `decryptedImport` → `decryptState` which requires the user's own AES-GCM key; an attacker cannot supply a plausible `.enc` file. The attack is scoped to the plain `.zip` path.

### Reachability and attacker control

The attack vector is fully reachable by any user who opens a crafted `.zip` file via Settings → Import. Convincing a user to import a "starter backup" or "example pack" is a plausible social-engineering step — the plain `.zip` format is human-readable and the app's own export UI produces files with the same extension. The attacker controls `sourceUrl` completely; no guessing, brute-forcing, or special privilege is required.

### Real-world impact

The primary exploit is a **persistent CDP binding hijack**: once the malicious pack is in IndexedDB the attacker receives a fetch on every "Update from URL" action the user takes, indefinitely. Secondary impacts (SSRF to intranet hosts, NaN corruption of XP/streak state) are real but less severe. The severity is **High** rather than Critical because: (a) user interaction is required (the victim must voluntarily import the file), (b) the app runs client-side only so there is no server-side RCE or privilege escalation, and (c) the fetch is made in the user's own browser, not from a backend, limiting the SSRF blast radius to resources reachable from the user's network.

## Fix Plan

**Status:** IMPLEMENTED

**Root cause.** `src/schemas/appState.schema.json` gates the untrusted `.zip` backup import path
but validates most arrays as bare `{ "type": "array" }`, so any attacker-shaped item passes.
Tighten the schema so every array validates its items — matching the pattern already used for
the `questions` array — and lock down the `profile` and `syncState` object shapes with
`additionalProperties: false` plus per-property types.

**Scope.** Edit `src/schemas/appState.schema.json` only. No source changes to
`validate.ts`, `import.ts`, `ProfilePage.tsx`, `store/index.ts`, or `cdp-import.ts` — the
existing `validateAppState` call in `ProfilePage.handleImport` already runs against the
compiled schema, so tightening the schema is sufficient to reject the crafted `.zip`
before `importAppState` writes anything to IndexedDB.

**Changes to `src/schemas/appState.schema.json`:**

1. `packs` — add `items` with `type: "object"`, `required: ["id", "manifest", "isPersonal", "importedAt", "updatedAt"]`,
   `additionalProperties: false`, and per-property types:
   - `id: { type: "string" }`
   - `manifest: { type: "object" }` (deep validation happens via `validatePackManifest` at CDP import; here we just gate the shape)
   - `isPersonal: { type: "boolean" }`
   - `importedAt: { type: "string" }`
   - `updatedAt: { type: "string" }`
   - `sourceUrl: { type: "string" }` (optional)
   - `aliasFor: { type: "string" }` (optional; type-defined but unused today, kept for forward-compat with foundation plan)

2. `chores` — add `items` with `type: "object"`, `required: ["key", "choreId", "packId", "title", "xpSize", "recurrence", "repeatable", "active", "createdAt"]`,
   `additionalProperties: false`, and:
   - `key`, `choreId`, `packId`, `title`, `createdAt`: `{ type: "string" }`
   - `description`: `{ type: "string" }`
   - `xpSize`: `{ oneOf: [{ type: "string", enum: [XXS…XXXL] }, { type: "number" }] }`
   - `recurrence`: `{ type: "object", required: ["frequency", "interval", "startDate", "windowStartTime"], properties: { frequency: enum daily|weekly|monthly, interval: { type: "integer", minimum: 1 }, startDate: { type: "string" }, windowStartTime: { type: "string", pattern: "^([01]\\d|2[0-3]):[0-5]\\d$" } }, additionalProperties: false }`
   - `repeatable`, `active`: `{ type: "boolean" }`
   - `duePeriod`: object matching the shape already used in `choreDefinition.schema.json`
   - `syncStatus`: `{ type: "string", enum: ["in-sync", "out-of-sync"] }`

3. `completions` — add `items` with `required: ["id", "choreKey", "completedAt", "xpEarned", "streak", "answers"]`,
   `additionalProperties: false`, and:
   - `id`, `choreKey`, `completedAt`: `{ type: "string" }`
   - `xpEarned`, `streak`: `{ type: "number" }`
   - `answers`: `{ type: "array", items: { type: "object", required: ["questionId", "value"], properties: { questionId: { type: "string" }, value: { type: ["string", "number", "boolean", "null"] } }, additionalProperties: false } }`

4. `xpSettings` — add `items` with `required: ["id", "name", "maxStreakMultiplier", "decayFloor", "streakHalfLife", "decayHalfLife"]`,
   `additionalProperties: false`, and all fields strictly typed (strings for `id`/`name`, numbers for the four numeric fields).

5. `quickAnswerSets` — add `items` with `required: ["id", "choreKey", "label", "answers"]`,
   `additionalProperties: false`, strings for `id`/`choreKey`/`label`, and the same `answers` sub-schema as `completions`.

6. `profile` — add `additionalProperties: false` and per-property types:
   `id: { type: "string", const: "me" }`, `displayName: { type: "string" }`, `email: { type: "string" }`, `activeXPSettingsId: { type: "string" }`.

7. `syncState` — add `additionalProperties: false` and per-property types:
   `id: { type: "string", const: "main" }`, `pendingSync: { type: "boolean" }`, `lastSyncedAt: { type: "string" }` (optional).

**Compatibility check.** `exportAppState` (`src/sync/export.ts`) produces objects whose
shape is the concrete `AppState` type. Every field the schema will now require is written
by the type system: `Pack` requires `id/manifest/isPersonal/importedAt/updatedAt`, `Chore`
requires `key/choreId/packId/title/xpSize/recurrence/repeatable/active/createdAt`, etc.
`validateAppState` is not called on the export path, but round-trip export→import will
continue to work because real exports satisfy the tightened schema. `Question` items
already have a strict sub-schema and are unchanged. The only optional inline field in
`Pack` is `aliasFor` (defined in foundation plan but currently unused); we include it in
the schema so future data doesn't break validation.

7. **syncState** — added `additionalProperties: false`, per-property types, and `const` constraint on `id` field

All value fields that can be null/string/number/boolean (in Answer objects) were defined using `oneOf` to avoid strict mode warnings.
