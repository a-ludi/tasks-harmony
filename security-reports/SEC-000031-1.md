# No Content-Security-Policy is served for the app root, leaving markdown-XSS and supply-chain script execution with unbounded blast radius (including exfiltration of the extractable AES sync key)

**Status:** DONE
**Bug ID:** SEC-000031
**Severity:** High

## Location

Verified against the current tree — no Content-Security-Policy is emitted anywhere. A repository-wide grep for `content-security` returns zero hits in `nginx/`, `index.html`, `vite.config.ts`, and `src/`.

- `index.html` (lines 1–61) — the `<head>` block contains a `charset`, viewport, title, favicon, apple-touch splash links, and PWA-related meta only. There is no `<meta http-equiv="Content-Security-Policy" content="…">` tag. This is the only HTML document shipped by Vite for the app shell.
- `nginx/` — the directory contains a single file, `nginx/sync-location.conf.template`, whose four `location` blocks (`/sync/challenge`, `~ "^/sync/[a-f0-9]{64}$"`, `= /sync/session`, `/sync/`) all configure `proxy_pass` for the sync API only. No `add_header Content-Security-Policy …` directive is present, and there is no location block, template, or included conf that covers the static app root (`/` and asset paths) where `index.html`, hashed JS bundles, and the service worker are served. As a result, the reverse proxy adds no CSP header for either the HTML document or the built JS.
- `vite.config.ts` (lines 1–47) — the build declares only `@vitejs/plugin-react`, `@tailwindcss/vite`, and `vite-plugin-pwa`. No CSP plugin (e.g. `vite-plugin-csp`, `csp-html-webpack-plugin` equivalent, per-hash nonce injection) is configured. The `server` block (lines 42–46) proxies `/sync` in dev but does not attach any `Content-Security-Policy` response header to the dev server either. There is therefore no CSP plumbing in either the production build or the dev server, so a developer running `bun run dev` sees no policy and neither does an end user hitting the built bundle.
- No other headers-injection surface exists in the deploy: there is no `_headers` file (Netlify-style), no `public/_headers`, no service-worker header injection in `vite-plugin-pwa`'s Workbox config, and no middleware in front of the static app.

## Description

The application ships without any Content-Security-Policy (CSP) — neither as an HTML `<meta http-equiv>` tag in `index.html`, nor as an HTTP response header from nginx for the app root, nor injected by Vite at build time. This finding was noted in passing during SEC-000025-3's investigation (see `security-reports/SEC-000025-3.md` §Verification Q3 and §Location bullet 4), which fixed the immediate high-severity extractable-key issue but explicitly did not track the missing CSP as a first-class defect. This report addresses it as its own defence-in-depth control.

### What CSP would provide

CSP is the browser-enforced allowlist that constrains, per-response, which script origins may execute (`script-src`), which endpoints scripts may talk to (`connect-src`), whether inline event handlers or `eval` are allowed (`unsafe-inline`, `unsafe-eval`), which origins may be embedded (`frame-ancestors`), what document base URL is permitted (`base-uri`), where forms may submit (`form-action`), what objects can be embedded (`object-src`), and where styles may load from (`style-src`). It is the standard defence-in-depth control that turns "any XSS is game over" into "an XSS still needs to bypass an origin-and-primitive allowlist." Without CSP, the browser applies no such limits and a single successful script-injection reaches every browser capability available to the origin.

### Why the absence matters here specifically

This app has two properties that make the missing CSP unusually costly:

1. **It renders user-controlled markdown through a rich editor.** Pack descriptions and chore descriptions are rendered via Milkdown in `src/components/ui/MarkdownDisplay.tsx`. This rendering surface has already produced confirmed cross-site injection issues (SEC-000019 and SEC-000021, both fixed). The Milkdown / remark / prosemirror stack is complex and dependency-heavy; new bypasses in link sanitisation, HTML-in-markdown handling, or transformer plugins are a realistic recurring risk. Without CSP, the next bypass immediately reaches full origin authority.

2. **A single successful XSS is catastrophic, not merely disruptive.** The E2E-encrypted-sync feature stores the AES-256-GCM master key in IndexedDB as `extractable: true` (`src/sync/credentials.ts` line 10; see SEC-000025-3 for full analysis). Exfiltration of that key permanently compromises confidentiality of every past and future encrypted backup — no forward secrecy, no rotation-on-detection. The exfiltration payload is two lines (documented in SEC-000025-3 §Description). A CSP with a locked-down `connect-src` and no `unsafe-inline` would meaningfully raise the bar for that exfiltration even in the presence of an XSS. Today no such bar exists.

### Attack surface an XSS reaches today (all uncapped)

An arbitrary script executing on the app's origin can currently:

- **Exfiltrate the AES sync key** to any attacker-controlled host via `fetch()`, `navigator.sendBeacon()`, WebSocket, image-tag beacon, or DNS-prefetch — `connect-src`, `img-src`, and `prefetch-src` are all unrestricted.
- **Inject additional `<script>` tags** loaded from any origin (e.g. weaponised CDN, attacker-controlled subdomain) — `script-src` is unrestricted.
- **Execute `eval` / `new Function` payloads** to obfuscate exploitation or bypass simple sanitisers — `unsafe-eval` is not blocked.
- **Attach inline event handlers** (`onclick`, `onerror`, `onload`) to any element rendered from markdown or DOM manipulation — `unsafe-inline` is not blocked.
- **Rewrite the document base URL** via `<base href="…">` so all relative `fetch()` calls (including sync API calls to `/sync/…`) silently route to an attacker-controlled origin — `base-uri` is unrestricted.
- **Embed the app in an attacker-controlled iframe** for clickjacking against the sync-key export dialog or profile export dialog — `frame-ancestors` is unrestricted (there is also no `X-Frame-Options`).
- **Redirect form submissions** from the profile/import UI to attacker endpoints — `form-action` is unrestricted.
- **Load embed/plugin content** (`<object>`, `<embed>`) — `object-src` is unrestricted.

### Distinction from prior findings

This finding is *not* about any specific unfixed injection sink. SEC-000019 and SEC-000021 patched concrete link-sanitisation and script-execution paths in the Milkdown pipeline. SEC-000025-3 constrained the extractable-key defect and included CSP as one observation in its verification. The defect described here is separate and structural: the app operates a *browser-layer* defence-in-depth control (CSP) at level zero. Even if every currently-known injection sink is patched, the absence of CSP means:

- Every future dependency update (Milkdown, remark, prosemirror, React, Vite, `vite-plugin-pwa`, transitive dependencies) that introduces a new HTML-injection or eval-injection gadget re-arms the full unbounded blast radius.
- Every supply-chain compromise (npm typosquat, a compromised transitive dep, an attacker-published patch version) that lands a script in the built bundle executes with full origin authority.
- Every misuse of `dangerouslySetInnerHTML` or an unsafe DOM sink added in future code has no browser-layer safety net.

Deploying CSP is therefore a *broad* mitigation — it does not fix a specific bug, but it measurably reduces future-exposure risk on a codebase whose worst-case XSS outcome is permanent decryption of every user's encrypted-sync backups. The mitigation belongs at both the nginx layer (as `add_header Content-Security-Policy …` on the static app root location block) and, ideally, as a build-time-injected `<meta http-equiv="Content-Security-Policy">` tag as a fallback for local/dev builds and non-nginx deploys.

## Validation

**CONFIRMED — High severity. Genuine, exploitable security defect (defence-in-depth control entirely absent).**

### (a) Verification of Finder's claims against source

All four location claims verified directly:

**`index.html` — no CSP meta tag:** Confirmed. The `<head>` block (lines 1–56) contains charset, viewport, title, favicon, and 32 apple-touch splash `<link>` elements. There is no `<meta http-equiv="Content-Security-Policy" …>` tag anywhere in the file. The body is a bare `<div id="root">` plus a `<script type="module" src="/src/main.tsx">` — no inline or meta-equivalent policy.

**`nginx/sync-location.conf.template` — no CSP header for app root:** Confirmed. The file defines exactly four `location` blocks: `/sync/challenge`, `~ "^/sync/[a-f0-9]{64}$"`, `= /sync/session`, and `/sync/`. All four configure `proxy_pass` to the sync socket only. There is no location block for `/` or any static-asset path, and no `add_header Content-Security-Policy …` directive anywhere in the file. nginx therefore emits no CSP header when serving `index.html` or the built JS/CSS bundles.

**`vite.config.ts` — no CSP plugin or server middleware:** Confirmed. Plugins are `@vitejs/plugin-react`, `@tailwindcss/vite`, and `VitePWA`. The `server.proxy` block routes only `/sync` to localhost:3001. No `server.headers` configuration exists. No CSP-injection plugin (nonce-based, hash-based, or meta-tag injection) is present. The dev server also serves responses with no CSP header.

**Repository-wide grep returns zero hits:** Confirmed by running `grep -ri "content-security"` across all four surfaces. Exit code 0 with no output — no CSP string exists in the codebase.

### (b) Severity rationale

**High** (not Medium, not Critical):

- **Why not Medium:** Medium would be appropriate for a defence-in-depth control whose absence has only theoretical impact. Here the impact is concrete: this application has an open AES key exfiltration path (the `extractable: true` key in IndexedDB, tracked in SEC-000025-3) and a history of confirmed XSS issues in the Milkdown rendering pipeline (SEC-000019, SEC-000021). The missing CSP is the only browser-layer control that would cap the blast radius of any future or currently-unknown injection in this pipeline. Its absence is not theoretical — the attack path it would blunt is documented and partially already fixed at the source level.

- **Why not Critical:** The CSP absence is not itself directly exploitable. It does not grant an attacker any new capability on its own; it removes a mitigation that would otherwise constrain an attacker who has *already* achieved script execution via another vector. There is no zero-click or network-only exploit path through the missing CSP alone. Critical is reserved for direct exploitability without a prerequisite.

- **Why High:** CSP is universally recognised as the standard browser-layer containment control for XSS on applications that handle sensitive material. This application handles AES-256-GCM key material whose exfiltration permanently decrypts all user backups with no forward secrecy. A locked-down `connect-src` and absent `unsafe-inline` / `unsafe-eval` would meaningfully raise the bar for that exfiltration even after a successful injection. The absence of this control on such an application, given a confirmed adjacent exfiltration path and a markdown rendering surface with a documented prior-issue history, is a High-severity defect — on the same tier as SEC-000025-3, which rated the extractable key High for requiring an XSS prerequisite. The two findings are peer in severity: one is the exploit payload (extractable key), the other is the missing containment layer that would blunt delivery of that payload.

  Severity anchors: SEC-000019 and SEC-000021 (confirmed XSS issues in Milkdown, now fixed) were presumably High or Critical since they had direct exploitability. SEC-000025-3 is High. The missing CSP is best understood as a structural amplifier for that class of finding — High, consistent with SEC-000025-3.

### (c) Explicit non-duplication with SEC-000025-3

SEC-000025-3 mentions the missing CSP in two places:

1. **§Location, bullet 4:** "index.html — no Content-Security-Policy (nor is one set by nginx for the app root …)" — cited as a supporting observation that explains why XSS is a plausible threat on this app, not as the primary defect being reported.
2. **§Validation Q3:** "No CSP to cap XSS blast radius — Confirmed." — again a supporting verification step confirming the pre-condition that makes XSS on this origin unconstrained, subordinate to the primary finding.

The title, description, fix plan, severity rationale, and test plan of SEC-000025-3 concern exclusively the `extractable: true` AES key stored in IndexedDB. Its proposed fix is to persist the key as `extractable: false`. That fix, if implemented, would close the immediate exfiltration path — but would leave the app with zero CSP, meaning any *other* XSS vector (supply-chain compromise, a new Milkdown bypass, a future `dangerouslySetInnerHTML` misuse) would still execute with full origin authority and reach IndexedDB, the service worker, form submissions, and iframes with no browser-layer constraint.

SEC-000031 is therefore a distinct, independent defect: it is the structural absence of a browser-layer containment control, not a duplicate of the specific extractable-key storage defect. The two defects amplify each other but have separate fixes: SEC-000025-3's fix is a key-generation code change; SEC-000031's fix is adding `add_header Content-Security-Policy …` directives to the nginx static-root location block and optionally a `<meta http-equiv>` fallback in `index.html`.

## Fix Plan

**Root cause.** No Content-Security-Policy is emitted for the app shell. Neither `index.html` nor `nginx/sync-location.conf.template` declares one, and Vite's dev-server has no `server.headers` config. Adding a policy is a pure delivery-layer change — no application code needs to move.

### Delivery choice — meta-tag in `index.html` (single-source)

We ship the CSP as a single `<meta http-equiv="Content-Security-Policy">` tag in `index.html`. Justification:

- **One source of truth, applies everywhere.** The same policy applies in production behind nginx, in `bun run dev` (Vite dev server), in `bun run preview`, and in any non-nginx deploy. There is no meta/nginx duplication to keep in sync, and no risk of nginx serving a weaker policy than the built HTML advertises.
- **No new nginx surface required.** The existing `nginx/sync-location.conf.template` covers only `/sync/*` and is included into an operator-provided `server` block. The static app root is already served by whatever `location /` the operator configured; introducing a mandatory `add_header` there would require every deploy to install a new conf snippet before this fix takes effect. A meta CSP ships with the bundle and is enforced by the browser regardless of proxy configuration.
- **`frame-ancestors` gap is accepted as a documented limitation.** Browsers ignore `frame-ancestors` in meta CSP. We accept this trade-off for now because (a) the app has no server-side redirector or opener that trusts framing state, (b) the anti-clickjacking risk is one narrow row of the threat surface enumerated in this report, and (c) an operator who wants belt-and-braces clickjacking protection can add `add_header X-Frame-Options DENY;` in their own `location /` block — this is documented as a follow-up in `docs/DEPLOYMENT.md`, not gated on this fix. If, in future, a `location /` template is introduced for another reason, the CSP can be duplicated there and `frame-ancestors` added — no rework of the meta CSP is needed.
- **`report-uri` / `report-to` also ignored in meta CSP** — we don't need violation reporting right now, and no infrastructure exists to receive it. Follow-up work.

### CSP directive list — exact policy string to ship

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self' data:; connect-src 'self' https:; worker-src 'self' blob:; manifest-src 'self'; base-uri 'self'; form-action 'self'; object-src 'none'; frame-ancestors 'none'
```

Directive-by-directive rationale:

- **`default-src 'self'`** — safe fallback; every unspecified fetch directive falls through here.
- **`script-src 'self'`** — Vite production builds emit only hashed static JS bundles under `/assets/*.js`; no CDN, no inline `<script>` in `index.html` (verified — the only `<script>` is `type="module" src="/src/main.tsx"`), no `eval` in first-party code, and no `wasm-unsafe-eval` needed (no WebAssembly deps identified in `vite.config.ts` or in the current bundle). If a future dep turns out to need `wasm-unsafe-eval`, the failing test will catch a policy change and the addition can be reviewed then.
- **`style-src 'self' 'unsafe-inline'`** — Milkdown, Tailwind's runtime style injection, and React's inline `style={{ … }}` all inject inline styles. Committing to hash/nonce-based style-src is a large migration and out of scope for a defence-in-depth CSP rollout; ship `'unsafe-inline'` for styles and treat style hashing as separate future work. This is the same trade-off virtually every Vite+React+rich-editor stack makes and does not undermine the value of the rest of the policy (the exfiltration attack surface enumerated in this report is on `script-src`, `connect-src`, `base-uri`, and `form-action`, none of which relax under `style-src 'unsafe-inline'`).
- **`img-src 'self' data: blob:`** — `'self'` for splash/icon assets in `public/`; `data:` for inline SVG icons emitted by React icon libraries and by the `icon-template.svg` favicon path; `blob:` for any future object-URL image (none today, but cheap and safe to allow).
- **`font-src 'self' data:`** — Tailwind CSS may embed font faces via `data:` URIs; also covers any self-hosted font in `public/`.
- **`connect-src 'self' https:`** — **`'self'`** covers `/sync/*` when the app is deployed same-origin (the reference/default deployment). **`https:`** is required because `src/cdp/cdp-import.ts` performs `fetch(manifestUrl)` and `fetch(choreUrl)` against arbitrary HTTPS origins (github.com, raw.githubusercontent.com, gitlab.com, github.mycompany.com, etc.) resolved by `src/cdp/normalizePackUrl.ts`, and because `import.meta.env.VITE_SYNC_URL` is baked in at build time and may point to a cross-origin sync host (see `vite.config.ts` line 40, `src/sync/server.ts` line 11). We do **not** try to enumerate git-forge hosts — the CDP feature is designed for user-supplied URLs and a closed allowlist would break the feature. Narrowing to `https:` (as opposed to `*`) still blocks: exfiltration to `http:` beacons, `ws:`/`wss:` endpoints, `data:` URLs used as connect targets, and DNS-prefetch and blob-URL fetch tricks — a meaningful reduction of the surface enumerated in §"Attack surface an XSS reaches today", even though it does not fully close cross-origin HTTPS beacons.
- **`worker-src 'self' blob:`** — `vite-plugin-pwa` registers a Workbox service worker from `/sw.js` (`'self'`). `blob:` is included to keep future Web Workers instantiated from bundled code working (not required today; low cost).
- **`manifest-src 'self'`** — the PWA manifest emitted by `vite-plugin-pwa` is same-origin.
- **`base-uri 'self'`** — blocks the `<base href="attacker.example">` rewrite documented in §"Attack surface" bullet 5, which would silently redirect every relative `/sync/*` `fetch()` to an attacker origin.
- **`form-action 'self'`** — the app has no cross-origin form submission; blocks redirect-form-post exfiltration.
- **`object-src 'none'`** — no `<object>`/`<embed>`; universally safe.
- **`frame-ancestors 'none'`** — declared in the meta tag even though browsers ignore it there, so that a future migration to nginx-served CSP or a compliant delivery layer picks it up unchanged. Present as declarative intent; not enforced today. See "Delivery choice" rationale above.

### Approach — files to change

1. **`index.html`** — add a single line inside `<head>`, immediately after the `<meta name="viewport" …>` on line 5 (so the CSP is parsed before any resource-fetching tags):

    ```html
    <meta http-equiv="Content-Security-Policy" content="default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self' data:; connect-src 'self' https:; worker-src 'self' blob:; manifest-src 'self'; base-uri 'self'; form-action 'self'; object-src 'none'; frame-ancestors 'none'">
    ```

    No other change to `index.html`; the 32 apple-touch splash `<link>` tags, the favicon, and the `<script type="module">` all remain and all satisfy the new policy.

2. **No changes to `vite.config.ts`, `nginx/sync-location.conf.template`, or any source file under `src/`.**
3. **No changes to `docs/DEPLOYMENT.md`** in the mandatory scope of this fix. A separate follow-up doc pass may add "operators who wish to enforce `frame-ancestors` can add `X-Frame-Options: DENY` in their `location /` block"; that is not a blocker for closing this defect.


Why this test is sufficient: the fix is a documentation-consistency change — a static string in a static HTML file. String-match against the intended policy is the shortest test that fails today, passes after the fix, and catches accidental future weakening (someone adds `'unsafe-eval'` to `script-src`, or drops `object-src 'none'`, or narrows `connect-src` and breaks CDP import). A boot-Vite integration test would add cost without meaningfully increasing coverage: Vite serves `index.html` verbatim in dev, so the meta tag reaches the browser identically to the string on disk.
