# Bun.serve missing `error` handler leaks internal error details in development mode

**Status:** DONE
**Bug ID:** SEC-000015
**Severity:** Medium

## Location
`sync-server/index.ts`, lines 22–27 (both `Bun.serve` calls):

```ts
Bun.serve({ unix: SYNC_SOCKET, fetch: handler, maxRequestBodySize: MAX_BODY_SIZE });
// ...
Bun.serve({ port: SYNC_PORT, fetch: handler, maxRequestBodySize: MAX_BODY_SIZE });
```

Neither `Bun.serve` invocation provides an `error` callback.

## Description

When `fetch()` throws an unhandled exception — for example, if Redis is unavailable and
`redis.get()` rejects, or `readFile`/`writeFile` throws an unexpected filesystem error —
Bun falls through to its built-in default error handling.

**Development-mode exposure (the concrete risk):**
Bun's documentation explicitly states that in *development mode* (`development: true`),
unhandled errors produce a rich in-browser error page that includes the exception message,
type, and full stack trace. If an operator runs the sync server locally or in a staging
environment with `development: true`, or if a future Bun version changes what "no error
handler" means in production, internal details are sent verbatim to the HTTP client.

The ioredis client embeds the configured `REDIS_URL` (e.g. `redis://localhost:6379` or a
URL containing credentials) inside connection-error messages. If such an error reaches the
client, it leaks the Redis connection string. Similarly, Node/Bun `ENOENT` / `EACCES`
filesystem errors include the full blob file path (`/data/<syncToken>.enc`), which exposes
the internal storage layout and confirms whether a given syncToken has a blob on disk.

**Production mode:** Bun currently returns a plain `"Internal Server Error"` 500 in
production without an explicit `error` handler, so the *current default* is safe. However:

1. This relies on an undocumented implementation detail rather than an explicit contract.
2. The production/development distinction is not enforced anywhere in the Dockerfile or
   `index.ts`; an operator who sets `development: true` (or runs `bun --development`) for
   debugging is unknowingly enabling the error page in a live environment.
3. No test currently covers the error-handler path, so a regression would be undetected.

The fix is a one-liner: add an explicit `error` handler that logs to stderr and returns a
generic 500, matching the pattern recommended by Bun's own documentation.

## Validation

**Confirmed genuine. All four preconditions are simultaneously true in the current production deployment.**

### Q1: Are `error` callbacks missing?

Yes. Both `Bun.serve` calls in `sync-server/index.ts` (lines 22 and 26) omit the `error` option entirely.

### Q2: Is development mode actually active in production?

Yes — and this is the crux. The `bun-types` type declaration for the `development` option reads:

```
@default process.env.NODE_ENV !== 'production'
```

The Dockerfile (`sync-server/Dockerfile`) does **not** set `NODE_ENV`. The production `docker-compose.yml` does **not** set `NODE_ENV`. No `.env` file sets it either. Therefore every deployed container runs with `NODE_ENV` undefined, making the default evaluate to `true` — development mode (rich error pages) is **silently active in production** without any explicit flag required.

### Q3: Can `fetch` throw unhandled errors that reach Bun?

Yes. Two concrete paths exist:

1. **Redis failure:** `authenticate()` in `blob.ts` (line 14) calls `redis.get()` with no surrounding try/catch. If Redis is unavailable, `ioredis` throws a connection error. The `handler()` function in `index.ts` has no try/catch either, so the exception propagates to `Bun.serve`.
2. **Filesystem failure (PUT path):** `blob.ts` lines 38–39 call `mkdir()` and `writeFile()` without try/catch. A permissions error or full disk will throw.

### Q4: Does the rich error page include the Redis URL?

Yes. `ioredis` embeds the full connection string in its error messages (e.g., `connect ECONNREFUSED redis://localhost:6379`). If `REDIS_URL` contains credentials — e.g., `redis://:s3cr3t@redis-host:6379` — those credentials appear verbatim in the exception message that Bun renders and sends to the HTTP client. The `redis.ts` module uses `process.env.REDIS_URL` directly with no masking.

### Q5: Realistic production risk?

Yes. The missing `NODE_ENV=production` in the Dockerfile means the current Docker image ships with Bun's error page enabled. A transient Redis restart or any unhandled filesystem error during a PUT would return a 500 response body containing the full stack trace and any credential-bearing Redis URL to the unauthenticated requester (since the error occurs before or during authentication).

**Severity rationale (Medium):** Exploitation requires triggering an unhandled exception (e.g. Redis downtime during a request), which is not directly attacker-controlled. However, the missing `NODE_ENV` in the Dockerfile means the risk is active in every production deployment by default, not just misconfigured ones. A credential-bearing `REDIS_URL` would constitute a secret leak.

## Fix Plan

Two targeted changes, one per root cause. Neither touches business logic.

### Change 1 — `sync-server/Dockerfile`

Insert `ENV NODE_ENV=production` immediately before the `CMD` line so that every
container image built from this file runs Bun in production mode regardless of
how docker-compose or the host environment is configured.

```dockerfile
# …existing lines…
USER bun
ENV NODE_ENV=production
CMD ["bun", "run", "index.ts"]
```

Placing it after `USER bun` keeps all privilege-dropping before the runtime
variable, and setting it as a Docker `ENV` (not `ARG`) means it is baked into
the image layer and visible to the process at runtime.

### Change 2 — `sync-server/index.ts`

Add an `error` callback to both `Bun.serve` invocations. The callback must:

1. Log the full error to stderr (so operators retain visibility without
   exposing it to HTTP clients).
2. Return a plain `Response("Internal Server Error", { status: 500 })` with no
   details in the body.

Both calls receive an identical handler — extract it into a named
`errorHandler` constant above the `if (SYNC_SOCKET)` block to avoid
duplication:

```ts
function errorHandler(err: Error): Response {
  console.error(err);
  return new Response('Internal Server Error', { status: 500 });
}
```

Then pass `error: errorHandler` to each `Bun.serve` call:

```ts
Bun.serve({ unix: SYNC_SOCKET, fetch: handler, error: errorHandler, maxRequestBodySize: MAX_BODY_SIZE });
// …
Bun.serve({ port: SYNC_PORT, fetch: handler, error: errorHandler, maxRequestBodySize: MAX_BODY_SIZE });
```

### Test Plan

#### Test A — Dockerfile (`sync-server/dockerfile.test.ts`)

Add to the existing `describe('sync-server Dockerfile security')` block:

```ts
it('sets NODE_ENV=production', () => {
  expect(dockerfile).toMatch(/^ENV\s+NODE_ENV=production$/m);
});
```

This reads the Dockerfile as a string (the file is already loaded at the top of
the describe block) and asserts the exact `ENV NODE_ENV=production` directive is
present. The regex anchors to line boundaries (`^…$` with `m` flag) so a
commented-out line or an `ENV NODE_ENV=development` would not satisfy it.

#### Test B — error handler (`sync-server/handlers/blob.test.ts`)

Add to the existing `describe('handleBlob')` block, immediately after the
existing mock setup (which already mocks `../redis`). Override `mockGet` for
one test to throw a credential-bearing connection error, call `handleBlob`
directly, and assert the response body is sanitised:

```ts
it('returns 500 with no internal details when redis throws', async () => {
  mockGet.mockImplementationOnce(() => {
    throw new Error('connect ECONNREFUSED redis://secret:password@redis-host:6379');
  });
  const res = await handleBlob(makeReq('GET', SYNC_TOKEN), SYNC_TOKEN);
  expect(res.status).toBe(500);
  const body = await res.text();
  expect(body).not.toContain('ECONNREFUSED');
  expect(body).not.toContain('redis://');
  expect(body).not.toContain('password');
  expect(body).not.toContain(' at ');       // no stack trace frames
});
```

Note: this test validates that `handleBlob` wraps errors internally. The
`Bun.serve` `error` callback is a second line of defence for errors that escape
all handlers; both must be present. If `handleBlob` does not currently catch
Redis errors, the test will drive adding a try/catch there (or in the top-level
`handler` in `index.ts`, whichever the Implementer judges cleaner — the test
is the contract, not the location of the catch).
