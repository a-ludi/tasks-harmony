# Missing nonce format validation in session handler allows unissued nonces

**Status:** DONE
**Bug ID:** SEC-001
**Severity:** Medium

## Location
`sync-server/handlers/session.ts`, lines 28–40

## Description
The `handleSession` function validates that `syncToken` and `hmac` are 64-char hex strings, but applies **no format check on the `nonce` field**. The intended security model is:

1. The server issues a cryptographically random 64-char hex nonce via `/sync/challenge` and stores it in Redis with a 60-second TTL (`nonce:{hex64}`).
2. The client signs the nonce with the shared HMAC key and sends it back via `/sync/session`.
3. The server verifies the HMAC, then atomically deletes the nonce from Redis (`del nonce:{nonce}`). If `del` returns 0 the nonce was already consumed — this is the one-time-use guard.

Because the nonce is never checked to be a 64-char hex string, an attacker who knows the app secret can:

**Forge sessions using never-issued nonces.** If the attacker sends a nonce that was never stored in Redis (e.g., arbitrary string `"foo"`), `redis.del("nonce:foo")` returns 0 and the request is rejected — so far so good. However, if the attacker finds (or pre-populates via a side channel) any key of the form `nonce:<X>` in Redis, they can pick any nonce value `<X>` and forge a valid HMAC for it, successfully authenticating. The lack of format validation means the server never enforces that only nonces it actually issued (and stored) are acceptable.

**Nonce injection targeting other Redis keys.** The nonce is used directly in `redis.del(`nonce:${nonce}`)` without sanitisation. If the nonce contains characters that are significant in the Redis protocol (e.g., newlines `\r\n` in RESP2), an attacker controlling the nonce value could craft multi-command payloads. While ioredis serialises keys as RESP bulk strings (which include length prefixes and thus resist classical injection), this is a defence-in-depth gap — the format check that would prevent this class of attack is simply absent.

**Unbounded nonce length leading to DoS.** Without a length cap, an attacker can supply a nonce of arbitrary length. `createHmac('sha256', secret).update(nonce)` will process the entire string, and `redis.del(`nonce:${nonce}`)` will send a proportionally large command to Redis. A sustained stream of requests with megabyte-sized nonces can exhaust CPU and network bandwidth.

The root cause is the omission of `/^[a-f0-9]{64}$/.test(nonce)` before using the nonce value — a check already present for both `syncToken` and `hmac` in the same function.

## Validation
**Verdict: CONFIRMED — genuine, exploitable security issue.**

Reachability: The `/sync/session` POST endpoint is publicly accessible — no prior authentication required. Any HTTP client can reach it.

Attacker control: The attacker fully controls all three fields in the JSON body: `nonce`, `hmac`, `syncToken`.

Real-world impact:

1. **DoS (no secret required, fully exploitable today):** The server accepts nonces of unbounded length. An attacker can send POST `/sync/session` with a nonce that is, say, 10 MB of arbitrary text. The server will: (a) call `createHmac('sha256', secretBytes).update(nonce)` over 10 MB of data, (b) send `DEL nonce:<10MB>` to Redis. Repeated at scale this saturates CPU and Redis network I/O. The existing `maxRequestBodySize` guard (1 MB + 1 KB overhead in index.ts) limits the body but only partially mitigates this, because the nonce is one field inside a JSON body — a 900 KB nonce is still 900 KB of HMAC computation and a ~900 KB Redis key delete.

2. **Design-contract violation (with secret):** If an attacker possesses the app secret, they can fabricate a valid HMAC for any nonce string. Without the 64-char hex check, they can use nonces that the server never issued, bypassing the intended challenge-response flow. For example, they can authenticate with nonce `"x"`, which was never stored in Redis — the `del` returns 0 and they are blocked — but they can also enumerate or guess the pattern of nonces already in Redis and forge sessions against those.

The fix is minimal and obvious: add the same regex guard that already exists for `syncToken` and `hmac` to the `nonce` field before any further processing.

## Fix Plan

In `sync-server/handlers/session.ts`, add a format validation for the `nonce` field immediately after the existing type checks (lines 28–34), mirroring the pattern already used for `syncToken` and `hmac`:

```ts
if (!/^[a-f0-9]{64}$/.test(nonce)) {
  return new Response('Bad Request', { status: 400 });
}
```

Insert this check BEFORE the `verifyHmac` call and BEFORE the `redis.del` call — so that malformed nonces never reach HMAC computation or Redis.

**Why this location:** Lines 31–36 already validate `syncToken` and `hmac` with identical patterns. Adding the nonce check here is symmetric and immediately obvious to the next reader.

**Why this is minimal:** One line of code, no new imports, no new dependencies. It exactly mirrors the existing guards.

**What it fixes:**
- Unbounded nonce length: a nonce longer than 64 chars fails the regex immediately — no HMAC computation, no Redis round-trip.
- Non-hex nonces: rejected before any processing.
- The design-contract gap: only properly server-issued nonces (which are always 64-char hex) can ever reach the HMAC check and Redis lookup.

### Test Plan

**File:** `sync-server/handlers/session.test.ts`

**Test name:** `'returns 400 when nonce is not a 64-char hex string'`

**Assertion:**
```ts
it('returns 400 when nonce is not a 64-char hex string', async () => {
  const res = await handleSession(makeReq({
    nonce: 'not-a-hex-nonce',
    hmac: makeHmac('not-a-hex-nonce'),
    syncToken: SYNC_TOKEN,
  }));
  expect(res.status).toBe(400);
});
```

This test must **fail** (return 401 or 500) before the fix because the malformed nonce currently reaches `verifyHmac` and `redis.del`. It must **pass** (return 400) after adding the format guard.

A second test covers the DoS boundary:
```ts
it('returns 400 when nonce is too long (> 64 chars)', async () => {
  const longNonce = 'a'.repeat(65);
  const res = await handleSession(makeReq({
    nonce: longNonce,
    hmac: makeHmac(longNonce),
    syncToken: SYNC_TOKEN,
  }));
  expect(res.status).toBe(400);
});
```
