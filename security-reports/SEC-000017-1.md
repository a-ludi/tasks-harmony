# ReDoS bypass: `safe-regex` misses ambiguous alternation patterns

**Status:** DONE
**Reviewed by:** Claude Sonnet 4.6, 2026-07-03
**Bug ID:** SEC-000017
**Severity:** Medium

## Location

`src/questions/validation.ts`, line 17 (`isSafeRegex` — delegates to `safe-regex` library)

Secondary surfaces (all inherit the bypass):
- `src/questions/validation.ts`, lines 40–49 (`validateAnswer` — executes the regex at completion time)
- `src/components/chores/choreFormValidation.ts`, line 29 (chore-editor form guard)
- `src/components/questions/QuestionFormFields.tsx`, line 34 (question-editor field guard)

## Description

### Background

SEC-000005 added a `isSafeRegex()` guard inside `validateAnswer` to prevent catastrophic
backtracking. SEC-000011 patched a bypass where `{n,m}` range quantifiers inside groups
were missed by the hand-rolled heuristic. SEC-000012 replaced the heuristic entirely with
the `safe-regex` npm library (v2.1.1), which correctly handles arbitrarily nested
quantifiers.

The SEC-000012 reviewer explicitly identified one remaining limitation:

> "The anchored `^(a|a)+$` gap is a separate issue that would require a new SEC report
> if deemed important enough to fix."

This report documents that gap.

### The vulnerability

`safe-regex` cannot detect **ambiguous alternation**: patterns of the form `(A|A)+` where
both branches of the `|` can match the same character, and the whole group is followed by
an unbounded quantifier. These patterns look like legitimate validators and pass
`isSafeRegex` with `{ valid: true }`, but cause exponential backtracking when a
sufficiently long, non-matching input is tested against an anchored version.

Confirmed bypass patterns (all return `safeRegex(pattern) === true`):

| Pattern | Appearance to victim | Timing at n=25+non-match |
|---|---|---|
| `^(\w\|\w)+$` | "only word characters allowed" | ~800 ms |
| `^([A-Z]\|[A-Z])+$` | "uppercase letters only" | ~700 ms |
| `^([a-zA-Z]\|[a-zA-Z])+$` | "letters only" | ~1000 ms |
| `^(a\|a)+$` | (documented in SEC-000012) | ~730 ms |

Timing measured in bun runtime; results consistent with exponential growth.

### Attack vector

Identical to SEC-000005 and SEC-000012 — a malicious CDP pack:

1. Attacker publishes a CDP whose chore YAML contains a `TEXT`-type question with
   `regexPattern: "^(\\w|\\w)+"` — a pattern that looks like a reasonable "word
   characters only" validator.
2. Victim imports the CDP. `isSafeRegex('^(\\w|\\w)+$')` returns `{ valid: true }`.
   No warning is shown; the pattern is stored permanently in IndexedDB.
3. Victim opens the "Complete Chore" modal and types 25+ word characters followed by
   one non-word character (e.g., a space or punctuation mark), then submits.
   `validateAnswer` calls `new RegExp('^(\\w|\\w)+$').test(value)`, which triggers
   exponential backtracking — hanging the browser main thread for ~800 ms per submission
   attempt.
4. Each subsequent attempt (re-opening the modal and submitting) triggers the same hang.
   The pattern persists in IndexedDB with no expiry.

The victim does not need to provide a maliciously long input; a typical name or username
(25+ alphanumeric characters followed by a space) is sufficient. The hang worsens
non-linearly: n=20 → ~23 ms, n=25 → ~800 ms, n=28 → ~1500 ms (estimated).

### Why this is distinct from SEC-000012

SEC-000012 fixed a structural deficiency in the hand-rolled heuristic: it could not
see inside nested group boundaries. The fix was to replace the heuristic with `safe-regex`.

This report describes a **distinct, independent limitation of the `safe-regex` library
itself**: it does not model regex semantics well enough to detect ambiguous alternation
(where both branches of `|` match an overlapping set of characters). The fix adopted in
SEC-000012 does not help here — `safe-regex` explicitly returns `true` for these patterns.

### Impact

- **Browser main-thread hang / tab freeze** triggered when a user submits a completion
  for a chore with an ambiguous-alternation `regexPattern`, using an input ≥ ~20
  characters with a trailing non-matching character.
- No authentication bypass, data exfiltration, or RCE. The impact is DoS (unresponsive
  browser tab, forced reload to recover).
- The pattern persists in IndexedDB, so the hang recurs every time the completion modal
  is used for the affected chore.
- Attack barrier: low — hosting a YAML file on any public URL is sufficient. The CDP
  import UI is accessible to any user who opens the dialog.

## Validation

**Verdict: CONFIRMED — genuine, exploitable ReDoS bypass**

### Reachability

The attack path is fully reachable with no authentication requirement:

1. `cdp-import.ts` fetches chore YAML from any attacker-supplied URL and calls `parseChoreQuestions`, which passes the raw `regexPattern` string through without any safety check.
2. `choreDefinition.schema.json` accepts `regexPattern` as an unconstrained `{ "type": "string" }` field — the JSON Schema layer performs no content validation.
3. The imported question is stored in IndexedDB. On every chore completion, `validateAnswer` in `validation.ts` (line 40) calls `isSafeRegex(question.regexPattern)` before executing the regex. Because `safe-regex` returns `true` for ambiguous alternation patterns, the guard is bypassed and `new RegExp(pattern).test(value)` runs on line 44–45.

### Attacker control

Verified independently: `safeRegex('^(\\w|\\w)+$')` returns `true`, as do `^([A-Z]|[A-Z])+$`, `^([a-zA-Z]|[a-zA-Z])+$`, and `^(a|a)+$`. The `safe-regex` library has no semantic model for alternation overlap and cannot detect these patterns. This is not a regression — the library never handled this class.

The attacker controls the full `regexPattern` string from the YAML file and can craft a pattern that appears semantically valid ("word characters only") while being structurally catastrophic.

### Impact assessment

- **Exploitability**: Low barrier — hosting a single YAML file at a public URL is sufficient. No special victim interaction beyond importing the pack and attempting chore completion.
- **Effect**: Browser main-thread hang (~800 ms at n=25, growing non-linearly). The tab becomes unresponsive; the user must force-reload. Because the pattern persists in IndexedDB without expiry, every subsequent completion attempt for that chore triggers the same hang.
- **Scope**: DoS only — no authentication bypass, data leak, or code execution.
- **Severity rationale**: Medium. The impact is limited to a single browser tab DoS with no data loss, but the attack is trivially mounted via the CDP import feature (open to any user), the effect persists indefinitely, and the pattern looks indistinguishable from a legitimate validator. This is meaningfully worse than Low (which would require significant effort or have negligible impact).

## Fix Plan

### Approach

Add a small structural pre-check to `isSafeRegex` in `src/questions/validation.ts`
that runs **after** the `new RegExp(...)` validity check and **before** delegating to
`safeRegex(pattern)`. If the pre-check flags the pattern as ambiguous-alternation, return
the same `{ valid: false, error: 'Pattern may cause catastrophic backtracking' }` shape
already used by the `safeRegex` failure branch, so downstream callers
(`validateAnswer`, `choreFormValidation`, `QuestionFormFields`) require no changes.

The pre-check is intentionally narrow — it targets the exact exploit family
(identical-branch alternation under an unbounded quantifier) and accepts a modest
false-negative rate for exotic overlaps in exchange for a near-zero false-positive
rate on realistic user patterns.

### Implementation

1. Add a top-level helper `hasAmbiguousAlternation(pattern: string): boolean` in
   `src/questions/validation.ts` (above `isSafeRegex`, not exported).

2. Algorithm — walk the pattern once and, for every top-level group `(...)` that is
   **immediately followed by an unbounded quantifier** (`+`, `*`, `+?`, `*?`, or
   `{n,}` with no upper bound), split the group body on top-level `|` (respecting
   nested `()` and `[]` and backslash escapes) and check whether **any two branches
   are byte-identical after trimming surrounding whitespace**. Identical branches
   under an unbounded outer quantifier are, by definition, exponentially ambiguous.

   Concretely:
   - Scan character-by-character, tracking `parenDepth` and `inCharClass`.
   - When `parenDepth` transitions from 0 → 1 at `(`, record `groupStart = i + 1`
     (and skip a leading `?:`, `?=`, `?!`, `?<=`, `?<!`, `?<name>` non-capturing/lookaround marker so the branch comparison operates on the actual alternation body).
   - When `parenDepth` transitions from 1 → 0 at `)`, capture `groupBody =
     pattern.slice(groupStart, i)`. Peek at the next character(s):
     - If it is `+`, `*` (optionally followed by `?`), or `{` starting an unbounded
       range like `{n,}` with no max — this group is quantified unboundedly.
   - For an unbounded-quantified group, split `groupBody` on top-level `|` using the
     same depth/char-class/escape tracking. If the resulting branches array has any
     duplicate entry (`new Set(branches).size < branches.length`), return `true`.

3. In `isSafeRegex`, before the `if (!safeRegex(pattern))` block, add:

   ```ts
   if (hasAmbiguousAlternation(pattern)) {
     return {
       valid: false,
       error: 'Pattern may cause catastrophic backtracking',
     };
   }
   ```

   Reuse the exact error string so the existing `validateAnswer` catastrophic-regex
   test (`validation.test.ts:203`) and the two consumer components continue to
   match on `/catastrophic backtracking/i`.

### Why this scope

- The 4 confirmed bypass patterns in the report (`^(\w|\w)+$`, `^([A-Z]|[A-Z])+$`,
  `^([a-zA-Z]|[a-zA-Z])+$`, `^(a|a)+$`) all fall under "identical branches under
  unbounded quantifier" and are caught by this check.
- Non-ambiguous alternations like `^(foo|bar)+$`, `^(cat|dog|bird)*$`, `^(https?|ftp)://`
  have distinct branches and are unaffected.
- Non-quantified alternations like `^(yes|yes)$` are structurally harmless (no
  exponential blow-up without an outer `+`/`*`) and are correctly ignored.
- We deliberately do not attempt to detect semantic overlap between different
  character classes (e.g. `(\w|[a-z])+`) — that requires a full semantic analyzer
  (`recheck` etc.), is out of scope for a targeted fix, and has not been reported
  as exploited. If it appears in the wild, it can be addressed in a follow-up SEC.

### Implementation

Added `hasAmbiguousAlternation(pattern: string): boolean` helper to `src/questions/validation.ts` that:
1. Parses the regex pattern character-by-character, tracking parenthesis depth and character class state
2. For each top-level group `(...)` immediately followed by an unbounded quantifier (`+`, `*`, `+?`, `*?`, or `{n,}`):
   - Extracts the group body
   - Skips non-capturing/lookaround markers (`?:`, `?=`, `?!`, `?<=`, `?<!`, `?<name>`)

3. Returns `true` if duplicate branches found under unbounded quantifier, `false` otherwise
