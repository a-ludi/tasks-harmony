# Sync-server PUT quota enforcement evicts other users' encrypted backups, enabling cross-tenant data destruction

**Status:** DONE
**Bug ID:** [[SEC-000035]]
**Severity:** High

## Location
`sync-server/handlers/blob.ts` — `handleBlob`, `PUT` branch, lines 40–109 (specifically the enumeration + eviction block, lines 50–101).

Related:
- `SYNC_BLOB_QUOTA_BYTES` / `SYNC_BLOB_MAX_COUNT` env-var defaults (`10 GiB` / `10_000`) in `readCaps` at lines 9–13.
- `authenticate` (lines 15–21) confirms only that the caller owns a session bound to the URL-path token; it does **not** grant the caller ownership over any other blob.
- Client-side PQ credential generation is free and unregistered — see `generatePQCredentials` in `src/sync/credentials.ts` (uses `ml_kem1024.keygen()` + `ml_dsa87.keygen()`) and `handleChallenge` in `sync-server/handlers/challenge.ts` which issues nonces for any well-formed `syncId` with no proof of prior existence.

## Description

The sync-server stores each user's encrypted backup as a single file `${BLOB_DIR}/${syncId}.enc`, where `syncId` is a 64-hex identity derived from the user's ML-KEM + ML-DSA public keys. The server enforces global storage caps (default 10 GiB / 10,000 files) that are **shared across all users** because the caps are checked against `readdir(BLOB_DIR)` — the entire on-disk blob directory — not against per-user usage.

When a `PUT /sync/<syncId>` would push the aggregate directory over either cap, the handler evicts other blobs from oldest `mtime` to newest, deleting any that do not belong to the current caller:

```ts
for (const blob of sortedByMtime) {
  if (blob.name === `${token}.enc`) continue;     // only skips the caller's own blob
  await unlink(join(BLOB_DIR, blob.name));         // <-- deletes another user's backup
  projectedBytes -= blob.size;
  projectedCount -= 1;
  if (projectedCount <= maxCount && projectedBytes <= quotaBytes) break;
}
```

Because eviction deletes the encrypted backups of *other* users, and because there is no per-tenant quota, no per-tenant reservation, and no ownership check on the files being unlinked, any authenticated caller who can push the global usage over either cap will silently destroy other users' encrypted state.

### Exploitability

1. **Creating fresh identities is free and unauthenticated.** `generatePQCredentials` runs entirely in the browser (or a script) and produces a valid `(mldsaPk, mlkemPk)` pair. The `syncId` is just `sha256(mlkemPk || mldsaPk)`. `handleChallenge` will issue a nonce for any well-formed 64-hex `syncId` without any prior registration, and `handleSessionPQ` will issue a session token as long as the caller signs `nonce || syncId` with the matching ML-DSA secret key — which the attacker owns.
2. **Trivial capacity attack.** An attacker generates N distinct PQ keypairs and PUTs a 1 MB blob at each. With `SYNC_BLOB_MAX_COUNT=10_000`, ~10,001 attacker uploads is enough to push over the count cap; from that point on, every subsequent attacker PUT (from *any* attacker identity) triggers eviction of the oldest blob that is not the current caller's — i.e. a real user's backup.
3. **Amplification.** Because the loop keeps evicting until the projection is under both caps, and because each attacker upload uses a fresh `syncId` so the "skip caller's own blob" guard never protects a real user, an attacker can wipe arbitrarily many real users' backups with a small number of subsequent PUTs. Byte-quota attacks (10 GiB default) require more traffic but the count cap makes the file-count path very cheap.
4. **Silent, non-recoverable.** The victim's blob file is `unlink`'d server-side. Because the sync-server holds only ciphertext and the plaintext lives only on the user's original device, a victim who wipes/loses their device before noticing the eviction (e.g., relies on server-side backup) permanently loses their chore/XP/questions/completions history. Even without device loss, any device that had not yet fetched the last-good blob will next issue a `pull()` and get `404`, at which point `src/sync/server.ts::pull` calls `markDirty()` and the next `push()` overwrites whatever fragmented local state remains — the attacker's eviction cascades into the victim's own client silently re-establishing a stale/empty blob.
5. **Rate limits do not mitigate.** `nginx/sync-location.conf.template` rate-limits per `$binary_remote_addr` (5r/m for challenge, 30r/m for `PUT`). At 30 PUT/min per IP, one attacker IP can create ~1,800 distinct blobs/hour; a small rotating IP pool trivially reaches the 10,000 count cap in an hour and then continuously evicts real users.

### Why the existing checks do not save you

- `authenticate` only guarantees the caller owns *their own* `syncId` — it does not check ownership of the files being unlinked. The eviction loop bypasses `authenticate` entirely for the deletion targets.
- The `syncId !== token` forbid-check at line 27 only prevents cross-user *reads/writes* at a given URL; it does nothing for the eviction path, which operates on filenames read directly from the filesystem.
- The comment "Never evict the caller's own blob" is the only ownership protection in the eviction loop, and it protects only the attacker themselves.

### Confidentiality note

The evicted blobs are AES-GCM-encrypted under an ML-KEM-derived shared secret that the attacker does not learn, so this is not a confidentiality breach — but it is an **integrity/availability** breach: attacker-controlled destruction of other tenants' encrypted state, with no audit trail beyond the deleted `mtime`.

### Suggested direction for the fix (informational — Planner owns the plan)

Enforce quota **per `syncId`**, not globally. Since each user has exactly one blob file, the natural policy is: (a) a caller may only overwrite `${token}.enc`; (b) reject with `507 Insufficient Storage` if the caller's own projected size exceeds a per-user cap; (c) never `unlink` any file the caller does not own. Global caps, if needed for operator DoS protection, should reject the caller's own PUT rather than delete other tenants' data. The eviction loop as currently written must be removed or restricted to blobs the caller owns (which, given one-blob-per-user, means no cross-tenant deletion is ever legitimate).

## Validation

**CONFIRMED — High severity. Genuine, exploitable security issue.**

### Verification

All claims verified against source code.

**Q1 — Global eviction loop confirmed:** `sync-server/handlers/blob.ts` lines 80–101 enumerate the entire `BLOB_DIR` via `readdir`, sort all blobs by `mtimeMs` ascending, and `unlink` any blob whose name is not `${token}.enc`. The eviction loop has no ownership check other than skipping the single caller's own file. Any other tenant's blob is eligible for deletion.

**Q2 — Free identity creation confirmed:** `sync-server/handlers/challenge.ts` issues a nonce to any well-formed 64-hex `syncId` with no registration check and no proof of prior existence. `src/sync/credentials.ts::generatePQCredentials` runs entirely client-side using `ml_kem1024.keygen()` + `ml_dsa87.keygen()` with no server interaction. An attacker can generate unlimited distinct valid identities at negligible cost.

**Q3 — Count-cap attack is cheap:** With `SYNC_BLOB_MAX_COUNT=10_000` (default), an attacker needs only 10,001 PUTs using distinct keypairs to push the global count over the cap. From that point, every subsequent attacker PUT triggers the eviction of the oldest blob that is not the current caller's — a real user's backup.

**Q4 — Eviction is permanent and silent:** `unlink` has no recycle bin. Because the server stores only ciphertext and the plaintext lives on the client, a victim who loses their device after eviction permanently loses their data. Even without device loss, the next client `pull()` receives a 404 and `markDirty()` cascades into the client overwriting with stale local state.

**Q5 — Rate limits do not mitigate:** `nginx/sync-location.conf.template` rate-limits by `$binary_remote_addr` (30 r/min for PUT). At 30 PUT/min per IP, a single attacker IP can register 1,800 new distinct blobs/hour; a small rotating IP pool trivially reaches 10,000 in one hour and then continuously evicts real users.

**Q6 — No duplicate in completed reports:** [[SEC-000022-0]] (cache headers, false positive) and [[SEC-000025-3]] (extractable AES key in IndexedDB) address wholly different attack surfaces. Neither involves the cross-tenant eviction path.

### Severity Rationale

**High** (not Critical) because:

- **Availability/integrity impact is severe and permanent.** An attacker can cause irreversible destruction of any or all tenant encrypted backups. Victims with no independent device copy permanently lose their chore/XP history. The cascade into client state re-establishment can corrupt data even for users who retain their device.
- **No confidentiality breach.** The evicted blobs are AES-GCM ciphertext the attacker cannot decrypt without the per-user key. This is purely an availability/integrity attack.
- **Exploitation requires network PUT requests but no prior registration, no credentials, no elevated privilege.** Creating valid identities is free, client-side, and produces legitimately-authenticated sessions for those identities. The attacker never needs to compromise any real account.
- **Not Critical** because the attacker must actively push a large volume of blobs (network cost) to trigger and sustain eviction; it is not a single-request, zero-cost annihilation. An operator can also raise `SYNC_BLOB_MAX_COUNT` as a short-term mitigation. Critical would apply if a single unauthenticated request could wipe all tenants instantly.
- The bug is entirely in the eviction design: a global quota enforced by deleting other tenants' files, with no per-tenant quota and no ownership validation on the files being unlinked.

## Fix Plan

Enforce quota **per `syncId`** and remove the cross-tenant eviction loop entirely. Each user has exactly one blob file, so a per-user cap is both natural and sufficient. Global caps are retained only as a defensive per-write ceiling that rejects the caller's own oversized write — the server must never `unlink` a file that does not belong to the authenticated caller.

**Changes in `sync-server/handlers/blob.ts` (`PUT` branch, lines 40–109):**

1. Replace the two-cap `readCaps()` (global bytes + global count) with a per-user byte cap plus an optional global-count safety valve:
   - Rename/repurpose `SYNC_BLOB_QUOTA_BYTES` semantics to be a **per-syncId** byte cap (default: `MAX_BYTES` = 1 MiB, i.e., the existing per-request payload limit — since each user has exactly one blob, the per-request limit is already the per-user cap).
   - Keep `SYNC_BLOB_MAX_COUNT` as a **global new-identity admission** cap: if the directory already contains `>= SYNC_BLOB_MAX_COUNT` distinct blobs and this PUT would create a new one (i.e., `${token}.enc` does not yet exist), reject with `507 Insufficient Storage`. **Never delete another blob to make room.**
2. Delete the entire eviction loop (lines 80–101). No `unlink` may ever be called on a file whose name is not `${token}.enc`.
3. For overwrite PUTs (the caller's own blob already exists), the count cap does not apply — only the per-user byte cap. Since `MAX_BYTES = 1 MiB` is already enforced at lines 42–44, no additional byte check is needed on the overwrite path.
4. Retain the existing `contentLength > MAX_BYTES` and `data.byteLength > MAX_BYTES` guards; these already enforce the per-user byte cap.

**Effect on operator contract (`docs/DEPLOYMENT.md`, "Blob store capacity" section, lines 27–48):** the LRU-eviction paragraph must be rewritten. New contract: `SYNC_BLOB_MAX_COUNT` caps the number of distinct users the server admits; when reached, new identities are rejected with 507 but existing users continue to sync. There is no cross-tenant deletion. Update the docs in the same commit as the code fix.

Note: [[SEC-000026]] (the ticket that introduced the eviction loop) accepted DoS-via-disk-exhaustion risk in exchange for LRU eviction. This fix reverts that trade-off: an attacker can still exhaust the `MAX_COUNT` slots to deny *new* signups, but can no longer destroy existing users' data. That is the correct trade for a zero-knowledge backup service — availability of new registrations is recoverable by an operator (raise the cap or clean the directory), whereas destruction of ciphertext-only backups is not.

The test fails because the current implementation evicts the oldest blob (tokenA) when the count cap is reached, even though it belongs to a different user. The handler returns 204 (success) instead of 507 (Insufficient Storage).

### Implementation

Fixed `sync-server/handlers/blob.ts` PUT handler to enforce per-user quota instead of global quota with cross-tenant eviction:

1. **Removed cross-tenant eviction loop**: Deleted lines 80–101 that enumerated all blobs, sorted by mtime, and deleted any blob not matching the caller's token.

2. **Enforced per-user byte cap**: The existing `MAX_BYTES` (1 MB) guard at lines 42–44 now serves as the per-user cap. Since each user has exactly one blob file, the per-request payload limit is already the per-user limit.

3. **Changed global count cap to new-identity admission valve**: `SYNC_BLOB_MAX_COUNT` now rejects new blobs (not existing ones) with 507 if the directory already contains `>= SYNC_BLOB_MAX_COUNT` blobs. No deletion occurs.

4. **Preserved overwrite semantics**: Existing users can always overwrite their own blob, even if the count cap is reached.

Updated tests to reflect new contract:
- New test `PUT never evicts another user's blob even when SYNC_BLOB_MAX_COUNT would be exceeded` (RED→GREEN)
- Rewritten `PUT rejects new blob with 507 when SYNC_BLOB_MAX_COUNT is reached` (was `evicts oldest`)
- Rewritten `PUT enforces per-user byte cap via MAX_BYTES guard` (was `QUOTA_BYTES eviction`)
- Rewritten `PUT allows overwrite of existing blob when within per-user cap` (was `isOverwrite + eviction`)
