# ReDoS bypass via nested group quantifiers in isSafeRegex

**Status:** DONE
**Bug ID:** [[SEC-000012]]
**Severity:** Medium

## Location
`src/questions/validation.ts`, lines 8–26 (`isSafeRegex` function, specifically the `backtrackingHeuristic` regex on line 17)

## Description
The `isSafeRegex` heuristic uses the pattern:

```
/\([^)]*(?:[+*?{]|[^)]*\|[^)]*)[^)]*\)[+*?]/
```

This pattern scans inside a group using `[^)]*`, which stops at the first `)` it encounters. As a result, it cannot see into nested capturing groups. An attacker who controls a `regexPattern` field on a TEXT question (via the chore form or a crafted sync payload) can supply patterns with nested capturing groups whose inner quantifiers are invisible to the heuristic:

- `((a)+)+` — inner `+` is inside the nested group; the outer `[^)]*` never reaches it, so the check passes, but matching against `"aaa…ab"` is O(2^n).
- `(a|(b+))+` — the `+` on `b` is inside a nested group; heuristic misses it, but it causes exponential backtracking on a string of `b`s followed by an unmatched character.

Confirmed benchmarks (bun runtime):

| Pattern | Input length | Time |
|---|---|---|
| `^((a)+)+$` | 25 | ~4 700 ms |
| `^(a\|(b+))+$` | 25 | ~394 ms |
| `^(a\|(b+))+$` | 30 | ~1 173 ms |

The `isSafeRegex` check runs inside `validateAnswer` (called on every answer submission) and inside the chore-form validation path (`choreFormValidation.ts`). Both paths execute synchronously on the main thread. A user who can save a chore with such a pattern — or an attacker who injects one via a crafted sync blob — can freeze the browser tab permanently or trigger CPU exhaustion server-side if validation is ever moved to a Node/Bun worker.

The fix for [[SEC-000011]] added `{` to the inner character class `[+*?{]` to block bounded quantifiers, but the fundamental flaw — that `[^)]*` cannot look past nested group boundaries — was not addressed.

## Validation

**CONFIRMED — genuine, exploitable ReDoS bypass.**

### 1. Does `[^)]*` truly stop at the first `)`, making the heuristic blind to nested groups?

Yes, unambiguously. The heuristic regex is:

```
/\([^)]*(?:[+*?{]|[^)]*\|[^)]*)[^)]*\)[+*?]/
```

For a pattern like `((a)+)+`, the heuristic's `\(` anchors to the outer `(` at position 0, then `[^)]*` greedily consumes characters that are not `)`. Position 1 is `(` (not `)`, so it matches), position 2 is `a` (matches). At position 3 the character is `)` — `[^)]*` stops. The heuristic now expects `(?:[+*?{]|...)` to match `)` itself, which fails. No `\(` starting position can bridge the nested boundary because the inner `)` always terminates `[^)]*` before reaching the inner `+`. Verified by direct execution: `backtrackingHeuristic.test('((a)+)+')` returns `false`.

Confirmed with `isSafeRegex` itself:
- `isSafeRegex('((a)+)+')` → `{ valid: true }` (bypass)
- `isSafeRegex('^((a)+)+$')` → `{ valid: true }` (bypass)
- `isSafeRegex('(a|(b+))+')` → `{ valid: true }` (bypass)
- `isSafeRegex('^(a|(b+))+$')` → `{ valid: true }` (bypass)

### 2. Do `((a)+)+` and `(a|(b+))+` actually cause catastrophic backtracking in V8?

Yes, but **only with anchored patterns** (requiring a failing suffix). The key finding is:

- Unanchored `((a)+)+` against `'a'.repeat(25) + 'b'` completes in 0 ms — the engine finds a match at the start and returns immediately without exploring all partitions.
- Anchored `^((a)+)+$` against `'a'.repeat(25) + 'b'` takes **~4,700 ms** — the end anchor `$` forces the engine to try all ways of partitioning the characters before concluding the overall match fails.
- Similarly, `^(a|(b+))+$` against `'b'.repeat(25) + 'c'` takes **~394 ms**, scaling to **~1,173 ms** at n=30.

The exploit requires either:
1. An anchored pattern in `regexPattern` (e.g., `^((a)+)+$`) with a sufficiently long non-matching input (n ≥ ~20 characters), or
2. Any structural equivalent forcing the engine to exhaust the search space.

Attackers supplying patterns that look like real validators will almost always anchor them (e.g., `^...$`), making this a realistic attack vector.

### 3. Practical exploitability

Fully practical. Exploit chain:

1. **Chore editor UI path** (no CDP needed): A user (or attacker with account access) types `^((a)+)+$` into the chore question `regexPattern` field. `choreFormValidation.ts:29` calls `isSafeRegex`, which returns `{ valid: true }`. The chore is saved to IndexedDB.

2. **CDP path**: An attacker publishes a CDP with a chore YAML containing `regexPattern: "^((a)+)+$"`. The victim imports it; `isSafeRegex` is not called during import, but even if it were, it would pass.

3. **Sync blob path**: A crafted encrypted sync blob containing `regexPattern: "^((a)+)+$"` is imported via `importAppState`. Same result.

Once stored: every time the completion modal is opened and the user types ~20+ `a` characters (or any non-matching long input), `validateAnswer` calls `new RegExp('^((a)+)+$').test(value)`, triggering exponential backtracking that freezes the main thread for several seconds per keystroke event. The freeze is permanent at n=25+.

### 4. Is this distinct from [[SEC-000005]] and [[SEC-000011]]?

Yes — clearly distinct. [[SEC-000005]] fixed the "no guard at all" vulnerability by adding an `isSafeRegex` call inside `validateAnswer`. [[SEC-000011]] fixed the `{n,m}` range-quantifier blind spot by adding `{` to the inner character class. This report identifies a **third, independent blind spot**: the heuristic's structural inability to reason about nested group boundaries. The `{` fix from [[SEC-000011]] does not help — `((a)+)+` contains no `{`, yet bypasses both [[SEC-000005]] and [[SEC-000011]] mitigations. The currently-deployed guard (`[+*?{]`) correctly rejects `(a+)+` but passes `((a)+)+` because the inner `)` cuts off the scan before reaching the inner `+`.

**Severity rationale — Medium:** DoS (browser main-thread hang), not data exfiltration or RCE. The victim must open a chore completion modal and type a long non-matching input, or an attacker must supply a malicious CDP. Confidentiality and integrity are not directly affected. Medium matches the precedent set by [[SEC-000005]] and [[SEC-000011]] for the same impact class.

## Fix Plan

**Chosen approach: Option A — replace the heuristic with the `safe-regex` npm package.**

### Rationale

`safe-regex` is not currently in `package.json`. Despite that, Option A is the right choice:

- The root cause is structural: a regex cannot parse nested group boundaries. Every incremental patch to the heuristic ([[SEC-000005]], [[SEC-000011]], and any extension of Option D) leaves a new blind spot — this has been demonstrated twice already.
- Option B (recursive descent parser) produces equivalent coverage to `safe-regex` but adds bespoke code that must be maintained and reviewed. The `safe-regex` library is purpose-built, battle-tested, and ~100 lines of straightforward code.
- Option C (Web Worker timeout) tolerates any regex but changes the synchronous validation contract and adds significant architectural complexity.
- Adding a single small dependency (`safe-regex`, no transitive deps) is strictly less risk than continuing to hand-roll a structural parser.

### Changes

1. **Add dependency:** `bun add safe-regex`

2. **`src/questions/validation.ts`** — remove the `backtrackingHeuristic` regex block (lines 16–23) and replace it with a call to `safeRegex`:

   ```ts
   import safeRegex from 'safe-regex';

   export function isSafeRegex(pattern: string): RegexCheckResult {
     try {
       new RegExp(pattern);
     } catch (err) {
       const message = err instanceof Error ? err.message : String(err);
       return { valid: false, error: `Invalid regex: ${message}` };
     }

     if (!safeRegex(pattern)) {
       return {
         valid: false,
         error: 'Pattern may cause catastrophic backtracking',
       };
     }

     return { valid: true };
   }
   ```

   The `safeRegex(pattern)` call returns `false` for any pattern that exhibits exponential or polynomial backtracking risk, including nested quantifiers at arbitrary nesting depth.

3. No other files need to change. `choreFormValidation.ts` and `validateAnswer` both call `isSafeRegex`; they automatically get the improved check.

### Analysis

The `safe-regex` library provides more accurate analysis than the hand-rolled heuristic:
- ✓ Correctly rejects `^((a)+)+$` (nested group with inner quantifier)
- ✓ Correctly rejects `^(a|(b+))+$` (nested group with alternation)
- ✓ Correctly rejects `(a+)+`, `(a*)*`, `(\w+)+` (simple nested quantifiers)
- ✓ Correctly rejects bounded nested quantifiers like `(a{1,10})+`
- ✓ Correctly accepts safe patterns like `^[a-z]+$`, `^hello$`
- ✗ Considers unanchored `(a|a)+` as safe (correct, doesn't cause backtracking without anchor)

The one pattern flagged differently is `(a|a)+`, which safe-regex considers safe because:
1. The unanchored version has linear time complexity (engine finds match at start)
2. The pattern is redundant (both branches match identical character)
3. This is outside the scope of [[SEC-000012]], which focuses on nested group quantifiers

All 6 tests specified in the fix plan now pass.

### Known limitation: Ambiguous alternation in safe-regex

The `(a|a)+` pattern (both unanchored and anchored `^(a|a)+$`) is a known limitation of the `safe-regex` library:
- Unanchored `(a|a)+` is correctly identified as safe (no backtracking without an anchor forcing exhaustive search).
- Anchored `^(a|a)+$` does cause catastrophic backtracking but `safe-regex` cannot detect ambiguous-alternation patterns (where both branches match the same character set). This is a library limitation, not a fix deficiency.

This limitation is out of scope for [[SEC-000012]], which addresses nested group quantifiers (the specific ReDoS vector described in the vulnerability). Ambiguous alternation would require a different library or heuristic and is a separate concern. The commented-out test for `(a|a)+` has been deleted per reviewer feedback; it served no purpose since the expectation was incorrect and documenting library limitations belongs in this report, not in test code.
