# Missing .dockerignore causes .env.local secrets to be baked into Docker image

**Status:** DONE
**Bug ID:** SEC-000014
**Severity:** High

## Location
`sync-server/Dockerfile`, line 5 (`COPY . .`) — no `.dockerignore` file exists in `sync-server/`

## Description
The `sync-server/Dockerfile` copies the entire build context into the image with `COPY . .` (line 5), but no `.dockerignore` file exists in the `sync-server/` directory. As a result, every file present at build time is baked into the Docker image layers, including:

1. **`sync-server/.env.local`** — contains `SYNC_APP_SECRET=LzFKHoyp/mkP8d6ElloyyCRxnNMNrytwqjpqMipM4bE=` and `REDIS_URL=redis://localhost:6379`. Even though the production deployment passes secrets via `docker-compose.yml` environment variables at runtime, the local dev secret is permanently embedded in image layers and survives even if overridden at runtime.

2. **`sync-server/.dev-sync-data/`** — contains `9159faf3b995c2917e626af301f642730576056d92ee19decfe46a6314747529.enc`, an encrypted blob with real (or realistic) user state from local development sessions. Even though it is AES-GCM encrypted, the filename itself is a valid SHA-256 syncToken that identifies the developer's sync namespace.

3. **`sync-server/node_modules/`** — hundreds of megabytes of dependencies bloat the image and include build-time dev tools never needed at runtime.

**Exploitability:** Anyone who can pull the Docker image — from a CI registry, a misconfigured container registry, or a compromised build server — can inspect the image layers (e.g., `docker save | tar -x`, or `docker history --no-trunc`) and extract the plaintext secret from `.env.local`. Docker layer inspection does not require running the container.

The attack is trivial:
```
docker build -t tasks-harmony-sync ./sync-server
docker save tasks-harmony-sync | tar -xO --wildcards '*/layer.tar' | tar -x ./env.local
```

`SYNC_APP_SECRET` is described in `DEPLOYMENT.md` as the "Pre-shared secret for HMAC challenge-response; written to server `.env` and baked into the client bundle" — the HMAC use was removed in SEC-000006, but the secret value itself is still generated and distributed to the server via `.env`. If the secret ever regains a server-side role, exposure via image layers becomes immediately exploitable. Even today, leaking internal credentials and encrypted user data blobs is a confidentiality breach.

## Validation

All conditions confirmed:

- `sync-server/Dockerfile` line 5 is `COPY . .` with no preceding `.dockerignore`.
- `sync-server/.dockerignore` does **not** exist (`ls` returns ENOENT).
- `sync-server/.env.local` **exists** and contains a real secret value: `SYNC_APP_SECRET=LzFKHoyp/mkP8d6ElloyyCRxnNMNrytwqjpqMipM4bE=` (not a placeholder).
- `sync-server/.dev-sync-data/` **exists** with one `.enc` file present.
- `sync-server/node_modules/` **exists** (12 top-level entries).
- `.gitignore` covers `.env.*`, so `.env.local` is gitignored — but the file exists on the developer machine right now, confirming this is a real-world scenario. The gitignore does not prevent CI pipelines or developers from having the file present at build time.
- `SYNC_APP_SECRET` is still present in `.env.local` with a real key value, despite SEC-000006 removing its server-side HMAC use.

**Severity rationale:** High. The attack requires no special privileges beyond image pull access. Extracting secrets from Docker layers is a well-known, trivial technique. The secret value is real, not a placeholder.

## Fix Plan

### Approach

The fix is a single new file: `sync-server/.dockerignore`. No changes are needed to `Dockerfile`, `package.json`, or any other file.

Docker automatically uses `.dockerignore` from the build-context root when running `docker build`. Because `sync-server/` is the build context (the directory passed to `docker build`), placing `.dockerignore` there is sufficient — no Dockerfile edits are required.

#### Exact `.dockerignore` content

```
# Secrets and local environment overrides — must never be baked into image layers
.env*

# Local development data — contains encrypted blobs and developer sync tokens
.dev-sync-data

# Dependencies are installed inside the image via `bun install --frozen-lockfile --production`
# (see Dockerfile line 4); copying node_modules would shadow that install and bloat layers
node_modules
```

The patterns use the same syntax as `.gitignore`. `.env*` matches `.env`, `.env.local`, `.env.production`, etc.

#### Files to create or modify

| Action | Path | Reason |
|--------|------|--------|
| **Create** | `sync-server/.dockerignore` | Prevents the three sensitive paths from entering the build context |
| **Edit** | `sync-server/dockerfile.test.ts` | Add one new test (see Test Plan below) |

No other files need updating.

### Test Plan

Add one test to the existing `describe('sync-server Dockerfile security', ...)` block in `sync-server/dockerfile.test.ts`:

```ts
it('has a .dockerignore that excludes .env*, .dev-sync-data, and node_modules', () => {
  const dockerignorePath = join(import.meta.dir, '.dockerignore');
  const content = readFileSync(dockerignorePath, 'utf-8');
  expect(content).toMatch(/^\.env/m);
  expect(content).toMatch(/^\.dev-sync-data/m);
  expect(content).toMatch(/^node_modules/m);
});
```

**RED phase:** Before `sync-server/.dockerignore` exists, `readFileSync` throws `ENOENT`, causing the test to fail immediately.

**GREEN phase:** After the file is created with the content above, all three `toMatch` assertions pass.

**No mocking needed.** The test reads a real file — this is an intentional property-based check on the filesystem artifact itself, mirroring the existing pattern in `dockerfile.test.ts` which reads the real `Dockerfile` with `readFileSync`.
