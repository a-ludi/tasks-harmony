# CDP import path lets a malicious pack take over the seeded "personal" pack (or any existing pack) via packId collision, flipping isPersonal:false and grafting an attacker-controlled sourceUrl

**Status:** DONE
**Bug ID:** SEC-000029
**Severity:** High

## Location

- `src/cdp/cdp-import.ts` line 58 — `packId` is derived verbatim from the URL basename:
  ```ts
  const packId = urlPath.substring(urlPath.lastIndexOf('/') + 1);
  ```
  No collision check, no allow-list, no reserved-id list.
- `src/cdp/cdp-import.ts` lines 107–130 — the returned `Pack` has `isPersonal: false` and `sourceUrl: baseUrl` (attacker-controlled URL).
- `src/store/index.ts` lines 245–258 — `importCDP` calls `await putPack(db, pack)` unconditionally.
- `src/db/index.ts` lines 120–121 — `putPack` is a raw `db.put('packs', pack)` against a store whose `keyPath: 'id'` overwrites in place when the id already exists (see `openDB()` at `src/db/index.ts:23`).
- `src/db/seed.ts` lines 15–23 — the app seeds a personal pack with `id: 'personal', isPersonal: true`; this is the pack the user cannot normally delete.
- `src/store/index.ts` line 357 — `deletePack` gate: `if (pack.isPersonal) throw new Error('Cannot delete the personal pack');`. Once `isPersonal` is flipped to `false`, this guard no longer fires.
- `src/store/index.ts` line 266 — `updateCDP` calls `fetchCDP(pack.sourceUrl)` on the (now attacker-controlled) `sourceUrl`.

## Description

The CDP-import path derives `packId` directly from the last path segment of the URL the user pastes, with **no reserved-id list and no collision check against existing packs in IndexedDB**. Because the `packs` object store keys on `id`, `db.put('packs', pack)` **overwrites in place** when a pack with that id already exists.

The seeded pack `personal` (created in `src/db/seed.ts`) is the primary target: it is the only pack the app treats as un-deletable (`if (pack.isPersonal) throw new Error(...)` in `store/index.ts:357`), and it holds every chore the user has created outside of imported CDPs (all `addChore` / `addPack('… personal')` flows default to `packId: 'personal'`). It is also the only pack the user is guaranteed to have.

### The attack

1. Attacker publishes a valid CDP at any URL whose **last path segment is `personal`**, e.g.
   `https://raw.githubusercontent.com/attacker/routines/refs/heads/main/personal`.
   The manifest and chore yaml files are schema-valid — the attack does not rely on schema-validation bypass.
2. Attacker convinces the victim to paste this URL into **Import Chore Pack** (a plausible social-engineering vector: "here's a great personal-routines pack, just paste this URL").
3. `CDPImportDialog.handleImport` calls `importCDP(url)` → `fetchCDP(url)` returns:
   ```ts
   {
     pack: {
       id: 'personal',                                     // ← collides with seeded pack
       manifest: { title: attacker.title, description: ..., ... },
       isPersonal: false,                                  // ← flips the delete guard OFF
       importedAt: now, updatedAt: now,
       sourceUrl: 'https://…/personal',                    // ← attacker URL persists
     },
     chores: [ …attacker's chores… ],
     questions: [ …attacker's questions… ],
   }
   ```
4. `importCDP` runs `await putPack(db, pack)` — this **overwrites the seeded personal pack in place**. The pre-existing chores that belong to `packId: 'personal'` (all of the user's personal chores) are **not** deleted because `putChore` writes to a separate store, but they now belong to a pack whose metadata, `isPersonal` flag, and `sourceUrl` are attacker-controlled.

### Post-exploit primitives

Once the personal pack is hijacked, the attacker has these primitives without any further user interaction:

- **Persistent CDP hijack of the personal pack.** Every subsequent click of **Update** on the personal pack in the CDP dialog runs `updateCDP('personal')` → `fetchCDP(pack.sourceUrl)` (`store/index.ts:266`) → arbitrary fetch to the attacker URL. The attacker can rewrite the personal pack's chores/questions on demand, and the pack's `sourceUrl` never rotates back — the takeover is durable across sessions and across app restarts. This is exactly the impact SEC-000023 identified for the `.zip` path, achieved here through the CDP path which SEC-000023's schema-tightening did not cover.
- **`updatablePacks` visibility.** `CDPImportDialog.tsx:100` filters "Installed packs" by `Boolean(p.sourceUrl)`. Before the attack, the personal pack has no `sourceUrl` and is hidden from this list. After the attack, it appears with an **Update** button — the attacker now has a one-click channel for future rewrites the user is likely to press when a "new version" is announced.
- **Bypass of the un-deletable-personal-pack invariant.** `deletePack` (`store/index.ts:357`) refuses to run when `pack.isPersonal`. After the takeover `isPersonal === false`, so the user (or any UI path that respects this guard) can now delete the personal pack, taking every personal chore's parent metadata with it. Combined with the disposition machinery in `deletePack` (lines 359–397), attacker-crafted follow-up user actions can mass-delete personal chores or reparent them to arbitrary packs.
- **Cross-pack chore overwrite.** `putChore` keys on `${packId}/${choreId}` (`db/index.ts:123`). Any attacker chore that happens to share a `choreId` with an existing personal chore (`floss`, `brush-teeth`, `meditate`, `water-plants` — small, guessable name space) silently overwrites the user's chore during `importCDP`'s `for (const chore of chores) await putChore(db, chore);` loop (line 250). The user's personal chore is replaced by the attacker's definition (title, description, xpSize, recurrence, prompts) with no warning — future completions record against the attacker's chore, and the original chore is unrecoverable without a backup.

### Why this is not covered by SEC-000023

SEC-000023 tightened `src/schemas/appState.schema.json` so that malicious `.zip` backups can no longer inject attacker-controlled packs (including `id: "personal"`) through the Settings → Import path. That fix operates entirely on `unwrapStateFromZip → validateAppState → importAppState`. The CDP import path is a **separate code path** (`importCDP → fetchCDP → putPack`) that:

- Uses `validatePackManifest` / `validateChoreDefinition` (not `validateAppState`) — these schemas do not constrain `packId` at all because `packId` is not in the CDP wire format; it is derived from the URL basename by client code.
- Writes each store item individually (`putPack`, `putChore`, `putQuestion`) rather than round-tripping through the whole-state validator, so no schema check ever sees the composite `{ id, isPersonal, sourceUrl }` shape.

Consequently a `personal`-basename URL is a first-class CDP import request as far as every guard in the pipeline is concerned; nothing between the URL bar and IndexedDB rejects it.

### Prerequisites and social-engineering realism

The attack requires the victim to import a CDP URL of the attacker's choosing. This is the app's primary supported way to add packs; the input is a plain-text URL the user pastes, and the placeholder in `CDPImportDialog.tsx:124` (`"https://raw.githubusercontent.com/user/repo/main/pack-dir"`) explicitly invites arbitrary hosts. The `/personal` basename is unremarkable and appears frequently in real chore-tracking repos, so the URL does not look suspicious. No prompt warns the user that the URL's basename determines an in-app identifier or that a colliding basename overwrites existing packs.

**Reachability**: The attack surface is the CDP Import dialog, which is a primary, user-facing feature. The import URL is unrestricted (any host, any path), and no check is performed between URL submission and `db.put`. The attack is fully reachable with a single paste action.

**Attacker control**: An attacker only needs to host a valid CDP at a URL whose last segment is `personal` (or any other existing pack ID). No privileged access is required; schema-valid YAML is sufficient. The attacker fully controls `isPersonal`, `sourceUrl`, and all chore/question content written into the database.

**Real-world impact**: The seeded `personal` pack is present in every installation. After a single import, the attacker persistently controls the pack metadata and the `sourceUrl` used for all future updates. The `isPersonal` invariant — the sole guard preventing deletion of user-owned chores — is silently flipped. Chores with guessable IDs (e.g. `floss`, `meditate`) are silently overwritten. The takeover survives app restarts and browser refreshes. The social-engineering vector (paste a friend's routine URL) is entirely plausible given the app's design intent.

**Severity rationale (High, not Critical)**: The attack requires user action (pasting a crafted URL) and is scoped to local IndexedDB — there is no network exfiltration of plaintext credentials or cryptographic keys. The impact is persistent data corruption/hijack of the personal pack and all downstream chores, which is severe but falls short of the remote-code-execution or credential-theft bar for Critical.

## Fix Plan

**Approach:** Reject any `importCDP` call whose derived `packId` collides with an already-installed pack. This is the general form of "reject `personal`" — it protects the seeded personal pack and every other pack the user has already installed (via `addPack` or a prior `importCDP`), without needing a maintained reserved-id list. Users who want to refresh an already-imported pack must use the existing **Update** button (`updateCDP`), which is designed for that purpose and which trusts the *already-stored* `sourceUrl` (not the URL currently in the input field), so it does not open a takeover vector.

**Where the check goes:** `src/store/index.ts` `importCDP` — *before* calling `fetchCDP`, look up the derived `packId` in the current in-memory `packs` list and throw if it already exists. Placing the check in `importCDP` (not in `fetchCDP`) is important because `updateCDP` also calls `fetchCDP` and must continue to work when the pack already exists.

**Why check early (before fetch):** rejecting before any network request means the attacker cannot infer anything about the victim's installed packs from server logs, and the failure mode is fast and predictable. The `packId`-derivation logic (`urlPath.substring(urlPath.lastIndexOf('/') + 1)`) is trivial to duplicate inline; a tiny helper `derivePackIdFromUrl(baseUrl)` can be extracted from `cdp-import.ts` if a shared utility is preferred, but the simpler variant is to inline the two-line derivation in `importCDP` — this preserves `fetchCDP` as a pure fetch/parse module and avoids new export surface. The Planner recommends inline for minimality; the Implementer may factor if it improves clarity without expanding scope.

**Error message:** must be actionable — tell the user *which* existing pack collided and point them at the Update flow. Draft:
```
Cannot import: a pack with id '<packId>' already exists. Use the Update button on the installed pack instead.
```

**Non-goals (explicitly out of scope):**
- Namespacing / renaming imported pack IDs on collision (option (c) in triage) — this would break `updateCDP`'s reliance on stable ids and confuse the user.
- Reserved-id allow-list (option (a)) — a subset of this fix; leaves attacker-controlled overwrite of user-imported packs open.
- Tightening chore-level collision (SEC-000029 also notes "cross-pack chore overwrite" as a follow-on primitive) — that primitive is fully neutralised by rejecting the pack-level collision, because chores in a rejected import are never written. If a future report identifies a *same-pack* chore-collision attack via `updateCDP`, that is separate.

### GREEN Phase Implementation

**Change:** Added collision check in `src/store/index.ts` `importCDP` function (lines 248–254).

The fix:
1. Derives `packId` from the URL basename (same logic as `fetchCDP`)
2. Checks if a pack with that `id` already exists in the in-memory `packs` list
3. Throws with actionable message before any network fetch occurs
4. Does not affect `updateCDP` which trusts the already-stored `sourceUrl`

**Code added:**
```typescript
// SEC-000029: Derive packId from URL and check for collision with existing packs before fetch
const urlPath = baseUrl.replace(/\/$/, '');
const derivedPackId = urlPath.substring(urlPath.lastIndexOf('/') + 1);
if (packs.some((p) => p.id === derivedPackId)) {
  throw new Error(`Cannot import: a pack with id '${derivedPackId}' already exists. Use the Update button on the installed pack instead.`);
}
```
