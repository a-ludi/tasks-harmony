# Sync-key import silently destroys local data despite "Your local data is unaffected" consent prompt

**Status:** DONE
**Reviewer:** Arne Ludwig
**Bug ID:** SEC-000018
**Severity:** High

## Location

- `src/components/profile/ProfilePage.tsx`, lines 144–168 — `handleKeyImport` shows a `window.confirm` that promises local data is unaffected, then unconditionally calls `pull(db)` which can overwrite local data
- `src/sync/server.ts`, lines 95–126 — `pull` calls `importAppState` whenever `serverTs > localTs`, without any user prompt
- `src/sync/import.ts`, lines 7–27 — `importAppState` clears every IndexedDB object store (`packs`, `chores`, `questions`, `completions`, `xpSettings`, `profile`, `syncState`, `quickAnswerSets`) and replaces them with server state

## Description

`handleKeyImport` in `ProfilePage.tsx` presents the following confirmation to the user before importing a sync-key file:

> **"Importing a new key will make your existing server data inaccessible. Your local data is unaffected. Continue?"**

The second sentence — "Your local data is unaffected" — is **false**. After the confirm, the handler runs:

```ts
const key = await importKeyFile(text);
await putCredentials(db, { id: 'main', cryptoKey: key });
const imported = await pull(db);          // ← can destroy local data
if (imported) await reload();
```

`pull(db)` derives a new syncToken from the imported key, authenticates, and downloads whatever blob the sync server has stored for that token. If the server returns a blob and its decrypted `syncState.lastSyncedAt` is greater than the local `syncState.lastSyncedAt`, `pull` calls `importAppState(db, serverState)`, which:

```ts
await Promise.all(storeNames.map((name) => tx.objectStore(name).clear()));  // wipes ALL local data
await Promise.all([
  ...state.packs.map((p) => tx.objectStore('packs').put(p)),
  ...state.chores.map((c) => tx.objectStore('chores').put(c)),
  // ... every store overwritten with server state
]);
```

The user is never re-prompted before the wipe. `pull` gives no return-value that lets `handleKeyImport` know local data was destroyed vs. kept.

### When the wipe fires

A first-time user's local `syncState.lastSyncedAt` is `undefined` (they have set up chores locally but not synced yet). `pull` computes `localTs = localSyncState?.lastSyncedAt ?? ''`, so `localTs = ''`. Any non-empty `serverTs` on the imported key's blob satisfies `serverTs > ''`, so `importAppState` runs and the user's local chores/packs/completions are **silently destroyed** and replaced with whatever the attacker's key-file-associated blob contains.

Even a user who has previously synced is vulnerable if the attacker's blob has a `lastSyncedAt` newer than the victim's most recent local sync — which the attacker fully controls when they create the blob.

### Concrete exploit — social-engineered data destruction

1. Attacker sets up their own tasks-harmony instance, creates a few plausible-looking chores/packs on their device, and lets it sync (so the server has an encrypted blob at the attacker's syncToken).
2. Attacker clicks "Export Sync Key" and gets `tasks-harmony-sync-key.json` containing the raw AES key.
3. Attacker sends the file to the victim with a pretext such as "Here's your account backup" / "Import this to restore" / "Family shared sync key".
4. Victim opens Profile → Sync section → "Import Key File" → picks the attacker's file.
5. Confirm: **"Importing a new key will make your existing server data inaccessible. Your local data is unaffected. Continue?"** — victim clicks OK because they believe local data will not be touched.
6. `handleKeyImport` overwrites the local credential, then `pull` succeeds, downloads the attacker's blob, decrypts it with the attacker's key, and calls `importAppState`, which wipes every local store and repopulates them with the attacker's chores/packs/profile/etc.
7. Victim's original chores, XP history, completions, streaks, quick-answer sets, and profile settings are permanently gone (no undo — IndexedDB `.clear()` cannot be rolled back).

### Why this qualifies as a security finding, not just a UX bug

- **Consent bypass:** the user explicitly declined to lose local data by relying on the confirm's guarantee. The code contradicts the guarantee it just obtained consent under.
- **Silent, irreversible destruction:** `importAppState` calls `.clear()` on every store and there is no confirmation step, no dry-run, no diff. There is no local undo.
- **Attacker-controlled replacement:** because the wipe replaces local data with the server blob content (which the attacker fully controls — they authored the key and its blob), the attacker can also plant chosen data on the victim's device. The victim may then act on the attacker's fabricated data believing it's their own (e.g. an attacker-provided chore titled "Send 200€ to IBAN X" that the victim treats as a legitimate reminder they set up earlier).
- **Trivial to trigger:** no memory-corruption, no MITM, no privileged position on the server. Just get the victim to import a file they were told is safe.

### Additional evidence — the code paths are unambiguous

- `handleKeyImport` (`ProfilePage.tsx:144`) does not distinguish between "just swap the credential" and "swap the credential AND merge/replace data." It always runs `pull(db)`.
- `pull` (`server.ts:95`) has no branch that checks "was this a key-swap flow?" — it just applies its usual "server newer → import" rule.
- `importAppState` (`import.ts:7`) calls `.clear()` unconditionally on every store name, not merging into local data.
- The confirm string is a single hard-coded literal at `ProfilePage.tsx:150`; there is no code path where the second sentence is true when the server actually has a blob for the imported key.

## Validation

**Verdict: CONFIRMED — High severity**

All three code paths cited in the report were verified against the actual source files.

**Reachability:** The vulnerable flow is reachable through the normal UI. `handleKeyImport` (`ProfilePage.tsx:144–168`) is wired directly to a file-input `onChange` handler in the Profile page's Sync section — no special permissions or auth state required beyond having the app open.

**Attacker control:** The attacker fully controls the server blob content (they authored the key and synced whatever data they chose). They also control `syncState.lastSyncedAt` in that blob, so they can trivially ensure `serverTs > localTs` — including against a victim who has previously synced, by simply setting a timestamp far in the future.

**The false consent is confirmed:** `ProfilePage.tsx:149–151` shows the exact confirm string *"Your local data is unaffected"*. `server.ts:114–116` shows that `pull` unconditionally calls `importAppState` when `serverTs > localTs`. `import.ts:14` shows `importAppState` calling `.clear()` on every object store before repopulating — no merge, no backup, no second prompt.

**The `localTs = ''` edge case is confirmed:** `server.ts:111` uses `localSyncState?.lastSyncedAt ?? ''`. Any non-empty `serverTs` satisfies `serverTs > ''` in JS string comparison, meaning a first-time user (no prior sync) is unconditionally wiped.

**Impact:** A social-engineering attack (share a crafted key file with a convincing pretext) causes silent, irreversible destruction of all user data across every IndexedDB store: packs, chores, questions, completions, XP settings, profile, sync state, and quick-answer sets. There is no undo path. The replacement data is entirely attacker-chosen, enabling secondary manipulation (e.g. planting fabricated reminders the victim acts on).

**Why High and not Critical:** The attack requires social engineering — the victim must be persuaded to import a file from the attacker. There is no remote code execution, no privilege escalation, and no path to impact users who never interact with the key-import UI. However, data destruction is permanent and the misleading consent prompt meaningfully increases the probability of victim compliance, elevating this above a purely self-inflicted mistake.

## Fix Plan

### Overview

The root cause is that `pull(db)` unconditionally calls `importAppState` — which
`.clear()`s every IndexedDB store — whenever the server blob's timestamp is newer than
local. `handleKeyImport` invokes `pull(db)` immediately after swapping credentials,
under a confirm prompt that falsely promises local data is untouched.

The minimal fix combines **option 1 (accurate confirm text)** with **option 2 (a
separate explicit destructive-action confirmation)** by teaching `pull` to be
non-destructive by default when the caller opts in to that mode. This keeps the
public `pull` API backwards-compatible (background sync callers keep the current
behaviour) and lets `handleKeyImport` gate the wipe behind its own second prompt
with accurate wording.

Concretely:

1. Add an optional `options` parameter to `pull` with a single field
   `overwriteLocal?: boolean` (default `true` — preserves current behaviour for the
   existing background sync callers). When `overwriteLocal === false` and the server
   blob is newer than local, `pull` **does not** call `importAppState`; it returns a
   discriminated result indicating a replacement was skipped so the caller can prompt.
2. Change `pull`'s return type from `boolean` to
   `PullResult = { imported: false, skipped?: 'server-newer' } | { imported: true }`
   so `handleKeyImport` can distinguish "nothing to do" from "server has data and we
   didn't touch local yet". Update the one non-UI call site (`SyncPanel` /
   background sync) to unwrap the boolean via `result.imported`.
3. Rewrite `handleKeyImport` to:
   a. Show a truthful first confirm about the credential swap only.
   b. Swap credentials and call `pull(db, { overwriteLocal: false })`.
   c. If the result is `{ imported: false, skipped: 'server-newer' }`, show a second,
      explicitly destructive confirm and, only on accept, call
      `pull(db, { overwriteLocal: true })` and `reload()`.
   d. If the user declines the second confirm, leave local data intact. (An offer to
      push local instead is optional and out of scope for this minimal fix.)

### Changes to `src/sync/server.ts`

Introduce a `PullResult` type and add the `options` parameter. The default value
(`overwriteLocal: true`) preserves existing behaviour for any caller that does not
pass options, so this is a non-breaking widening of the API.

```ts
export type PullResult =
  | { imported: true }
  | { imported: false; skipped?: 'server-newer' };

export async function pull(
  db: IDBPDatabase<TasksHarmonyDB>,
  options: { overwriteLocal?: boolean } = {},
): Promise<PullResult> {
  const { overwriteLocal = true } = options;
  if (!SYNC_URL) return { imported: false };
  const key = await getOrCreateSyncKey(db);
  const syncToken = await deriveSyncToken(key);

  try {
    const res = await authorizedFetch('GET', syncToken);
    if (res.status === 404) { markDirty(); return { imported: false }; }
    if (!res.ok) return { imported: false };

    const blob = new Uint8Array(await res.arrayBuffer());
    const serverState = await decryptState(key, blob);
    const validation = validateAppState(serverState);
    if (!validation.valid) return { imported: false };

    const localSyncState = await getSyncState(db);
    const localTs = localSyncState?.lastSyncedAt ?? '';
    const serverTs = serverState.syncState.lastSyncedAt ?? '';

    if (serverTs > localTs) {
      if (!overwriteLocal) return { imported: false, skipped: 'server-newer' };
      await importAppState(db, serverState);
      return { imported: true };
    }

    if (localTs > serverTs) {
      markDirty();
    }
    return { imported: false };
  } catch {
    return { imported: false };
  }
}
```

### Changes to callers of `pull` (return-type migration)

`pull` currently returns `boolean`. After the change it returns `PullResult`.
There are exactly two non-test call sites in `src/` (verified via
`grep -rn "pull(" src/ --include=*.ts --include=*.tsx`):

1. `src/components/profile/ProfilePage.tsx:160` — `handleKeyImport`, rewritten below
   to use the new `overwriteLocal: false` mode plus a second confirm.
2. `src/hooks/useSync.ts:57` — startup pull. Currently:
   ```ts
   pull(db).then(async (imported) => {
     if (imported) await reload();
   });
   ```
   Update to:
   ```ts
   pull(db).then(async (result) => {
     if (result.imported) await reload();
   });
   ```
   This caller keeps the destructive default (`overwriteLocal: true`) — startup
   pull for a device that already owns the credential is the correct place for the
   existing "server-wins-when-newer" behaviour, and no consent regression is
   introduced there.

### Changes to `src/components/profile/ProfilePage.tsx`

Replace the confirm string and split the flow into "swap credentials" and (only if
needed) "replace local data with server data".

```ts
async function handleKeyImport(e: React.ChangeEvent<HTMLInputElement>) {
  const file = e.target.files?.[0];
  if (!file || !db) return;
  setKeyImportError(null);
  setKeyImportSuccess(false);

  // First confirm — only about the credential swap. This is truthful because the
  // pull call below runs with overwriteLocal:false and cannot touch local data.
  const okSwap = window.confirm(
    'Importing a new key will change which server account this device syncs with. '
    + 'Your existing server data (encrypted with the old key) will no longer be '
    + 'accessible from this device. Continue?'
  );
  if (!okSwap) {
    if (keyFileInputRef.current) keyFileInputRef.current.value = '';
    return;
  }

  try {
    const text = await file.text();
    const key = await importKeyFile(text);
    await putCredentials(db, { id: 'main', cryptoKey: key });

    // Non-destructive pull: never overwrites local data.
    const result = await pull(db, { overwriteLocal: false });

    if (result.imported === false && result.skipped === 'server-newer') {
      // Second, explicitly destructive confirm — accurate about what will happen.
      const okReplace = window.confirm(
        'The imported key has a synced backup on the server that is newer than '
        + 'your local data. Replacing your local data with the server backup will '
        + 'DESTROY all local chores, packs, completions, XP history, and settings '
        + 'on this device. This cannot be undone.\n\n'
        + 'Replace local data with the server backup?'
      );
      if (okReplace) {
        const replace = await pull(db, { overwriteLocal: true });
        if (replace.imported) await reload();
      }
      // If declined: leave local data intact. Credential is already swapped so the
      // next push will overwrite the server blob with local state (existing dirty
      // marker / SyncPanel path handles this).
    } else if (result.imported) {
      // Should be unreachable with overwriteLocal:false, but reload to be safe.
      await reload();
    }

    setKeyImportSuccess(true);
  } catch {
    setKeyImportError('Invalid key file.');
  } finally {
    if (keyFileInputRef.current) keyFileInputRef.current.value = '';
  }
}
```

### Why this is minimal

- No changes to `importAppState` (`src/sync/import.ts`) — the destructive clear
  remains, it's just no longer reachable without an accurate second confirm.
- No changes to sync-server, encryption, or storage schema.
- `pull`'s existing behaviour is preserved for every non-key-import caller via the
  `overwriteLocal: true` default. Only the return-type shape changes (boolean →
  discriminated object), which is a compile-time-visible mechanical migration.
- No new UI components, no dialog framework, no route changes.

**Supporting test (regression guard — should be added alongside):**

Name: `'still calls importAppState when overwriteLocal is true and server blob is newer'`

Body: identical setup but call `pull({} as never, { overwriteLocal: true })` (or
`pull({} as never)` to also cover the default). Assert
`spy.mock.calls.length === callsBefore + 1` and `result.imported === true`.

**Why these tests are sufficient**

- The critical security property under `handleKeyImport`'s new first-prompt flow is
  precisely "`pull` under `overwriteLocal: false` never calls `importAppState`".
  Test 1 asserts exactly that at the seam where the destruction happens.
- The regression guard ensures the default (used by the background/sync-panel paths)
  is unchanged.
- The `mockFetch([200])` path already returns a decryptable-mocked blob via the
  existing `decryptState` mock, so no new fixtures are needed.

**FAILS before fix:**
`pull` does not accept an `options` parameter (TypeScript compile error) — or, if
`options` is silently ignored, `importAppState` is called and
`spy.mock.calls.length` increments by 1, failing `expect(...).toBe(callsBefore)`.

**PASSES after fix:**
`pull` accepts `{ overwriteLocal: false }`, short-circuits before
`importAppState`, returns `{ imported: false, skipped: 'server-newer' }`, and the
spy call count is unchanged.

### Out of scope for this fix

- Rewriting the sync architecture (three-way merge, per-record CRDT, undo journal).
- Offering a "push local instead" affordance on the second confirm — the credential
  is already swapped and the existing dirty flag will cause the next push to
  upload local state; adding a dedicated button can be a follow-up.
- Backporting to any encrypted backup `.enc` import path (that path is guarded by
  its own confirm — see SEC-000016 fix context — and is not the reported vector).
