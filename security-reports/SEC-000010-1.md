# Sync server container runs as root (no USER directive in Dockerfile)

**Status:** DONE
**Bug ID:** SEC-000010
**Severity:** Low

## Location
`sync-server/Dockerfile` — entire file, no `USER` directive present

## Description
The sync server `Dockerfile` has no `USER` instruction, so the Bun process runs as **root** (UID 0) inside the container. All files written by the server — encrypted blob files under `/data`, the Unix socket at `/run/sync/sync.sock` — are owned by root. The socket is then `chmod 0o666`'d by the server at startup (`sync-server/index.ts` line 23) so that nginx can write to it without a shared group, which works but only because the socket is world-writable (readable/writable by any process, including unprivileged ones that can reach the filesystem).

**Why this matters:**

1. **Blast radius of any RCE in the server process.** If an attacker exploits a vulnerability in Bun itself, in `ioredis`, or in the application code (e.g., a path traversal bypassing the `TOKEN_RE` validation in `index.ts`), they obtain a root shell inside the container. A non-root process would limit the attacker to an unprivileged user confined to the container. Root widens the attack surface for container-escape techniques (e.g., writing to mounted host paths, abusing `/proc/1`, exploiting privileged kernel interfaces).

2. **Mounted volumes are owned by root.** The `sync-data` Docker volume is mounted at `/data` and `redis-data` at its own mount point. Blob files written to `/data` by the root-running process are owned by `root:root` with default umask. If the volume is ever bind-mounted or inspected on the host, the files cannot be read or deleted without sudo on the host — a nuisance that also signals a security posture issue.

3. **Docker best practice violation.** Running application code as root inside a container is universally classified as a security anti-pattern in Docker's own documentation and in NIST SP 800-190. The `oven/bun:1-alpine` base image already creates a non-root `bun` user (UID 1000) intended for exactly this use case.

**Concrete exploit scenario:**

If a future bug allows an attacker to execute arbitrary code within the Bun process (for example, via a malformed request body that triggers a Bun runtime bug, or a deserialization vulnerability in `ioredis`), the attacker immediately has root inside the container. From there:
- They can read all blob files in `/data` (all users' encrypted sync blobs).
- They can connect to the Redis container on the internal bridge network (no auth on Redis — `docker-compose.yml` uses the default `redis:7-alpine` with no `requirepass`).
- They can read and delete all Redis keys, including all active session tokens and nonces.
- They can attempt container-escape techniques that require a root process (e.g., abusing `CAP_SYS_ADMIN` if the container was started without `--cap-drop ALL`).

**Redis has no authentication:** The `docker-compose.yml` starts Redis with `redis-server --appendonly yes` and no password. The Redis instance is only accessible on Docker's internal bridge network (not exposed on the host). However, if the sync server container is compromised (especially running as root), the attacker can directly query Redis without any credential — reading all session tokens, nonces, and syncToken mappings.

**Fix:**

Add a `USER bun` directive to the Dockerfile (the `bun` user, UID 1000, is pre-created in the `oven/bun:1-alpine` base image). The Unix socket `chmod 0o666` approach already handles nginx access without needing root. Blob files should be written to a directory pre-created with the correct ownership during the Docker build.

```dockerfile
FROM oven/bun:1-alpine
WORKDIR /app
COPY package.json bun.lock* ./
RUN bun install --frozen-lockfile --production
COPY . .
RUN mkdir -p /data && chown bun:bun /data
USER bun
CMD ["bun", "run", "index.ts"]
```

## Validation

**CONFIRMED — Low severity (defence-in-depth)**

All factual claims in the report were verified against the codebase:

1. **No `USER` directive in Dockerfile** — Confirmed. `sync-server/Dockerfile` is 6 lines with no `USER` instruction. The Bun process runs as root (UID 0).

2. **Redis has no authentication** — Confirmed. `docker-compose.yml` runs `redis-server --appendonly yes` with no `requirepass` and no `ports:` mapping on the redis service. Redis is unreachable from outside the Docker bridge network. However, from within a compromised sync container it is directly queryable with no credentials.

3. **`bun` user exists in `oven/bun:1-alpine`** — Confirmed by the official Bun Docker image specification. UID 1000 `bun` user is pre-created and the fix as proposed is valid.

4. **Socket `chmod 0o666`** — Confirmed at `sync-server/index.ts` line 23. This is intentional for nginx interoperability and does not itself constitute a vulnerability, but it is noted for completeness.

5. **Blob files written by root** — Confirmed. `sync-server/handlers/blob.ts` `writeFile` creates `{token}.enc` files in `/data` owned by root with default umask (0644). Not world-writable, but inaccessible to any non-root process on the host without `sudo`.

**Exploit reachability:** No direct exploit exists from the running state. The attack chain requires a prior RCE (e.g., a Bun runtime bug or application vulnerability) before root provides additional leverage. This makes it a defence-in-depth issue, not an independently exploitable finding.

**Why not DISCARDED:** The combination of root process + unauthenticated Redis represents a meaningful escalation path post-RCE. A non-root process would limit the attacker; root enables container-escape techniques requiring elevated capabilities and trivially exposes all Redis state (session tokens, nonces, syncToken mappings). The fix is low-effort and well-supported by the base image. Severity is **Low** rather than Informational because the blast-radius amplification is concrete and the fix is straightforward.

## Fix Plan

Edit `sync-server/Dockerfile` to add two lines between the final `COPY . .` and the `CMD` directive:

1. `RUN mkdir -p /data && chown bun:bun /data` — creates the blob storage directory during the build (while still root) and transfers ownership to the `bun` user so the server process can write to it at runtime without elevated privileges.
2. `USER bun` — switches the effective user for all subsequent layers and the container entry-point to UID 1000 (`bun`), which is pre-created by the `oven/bun:1-alpine` base image.

The final Dockerfile should read:

```dockerfile
FROM oven/bun:1-alpine
WORKDIR /app
COPY package.json bun.lock* ./
RUN bun install --frozen-lockfile --production
COPY . .
RUN mkdir -p /data && chown bun:bun /data
USER bun
CMD ["bun", "run", "index.ts"]
```

No changes are needed to `sync-server/index.ts` — the existing `chmod(socket, 0o666)` call at line 23 continues to make the Unix socket world-writable for nginx, and that works equally well from a non-root process.
