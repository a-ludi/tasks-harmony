# Sync server has no blob-deletion endpoint, so rotating a compromised key leaves the old encrypted blob permanently readable to anyone still holding the old sync token

**Status:** DONE
**Bug ID:** [[SEC-000032]]
**Severity:** Medium

## Location

- `sync-server/index.ts` (lines 16–23) — router only accepts `POST /sync/challenge`, `POST /sync/session`, and `GET`/`PUT /sync/{token}`; no `DELETE` verb is dispatched.
- `sync-server/handlers/blob.ts` (lines 23–115) — `handleBlob` only implements `GET` and `PUT`; there is no path that unlinks a caller-controlled blob.
- `src/sync/server.ts` (all of `push`, `pull`, `authorizedFetch`) — client has no code path that asks the server to remove data.
- `src/components/profile/ProfilePage.tsx` (lines 144–197, `handleKeyImport`) — the key-rotation UI only calls `putCredentials(...)` locally and `pull(...)`; it never contacts the server to remove the blob written under the previous key.
- `src/sync/credentials.ts` (lines 5–15, `getOrCreateSyncKey`) — every new key generates a fresh `syncToken`, and therefore a fresh server-side path (`{syncToken}.enc`), leaving the previous file orphaned.

## Description

### Threat model

The sync server stores each client's encrypted state at a filesystem path derived directly from `syncToken = SHA-256(rawAesKey)` (see `sync-server/handlers/blob.ts` line 29:
`const blobPath = join(BLOB_DIR, `${token}.enc`);`). Any party that possesses the raw AES key can, at any time, recompute the same `syncToken`, complete the challenge/session handshake (`handleChallenge`, `handleSession`), and download the ciphertext at that path. Because the AES key is the *only* thing needed to both authenticate as "the blob's owner" and to decrypt the contents, key confidentiality is the sole boundary protecting the entire history of a user's data.

The application ships an in-app credential-import flow ("Import sync key" on `ProfilePage`, lines 144–197) that lets a user replace their local `credentials.main.cryptoKey` — for example, in response to compromise of the previous key (leak of the exported `.json` key file, theft of a device, or malware exfiltration of the extractable IndexedDB key). The UI explicitly frames this as a rotation: *"Importing a new key will change which server account this device syncs with. Your existing server data (encrypted with the old key) will no longer be accessible from this device."*

### The vulnerability

The client's key-rotation flow does **not** cause the server to delete the blob written under the old syncToken, because there is no endpoint that can do so. The router in `sync-server/index.ts` only dispatches `POST /sync/challenge`, `POST /sync/session`, and `GET`/`PUT /sync/{token}`; every other method to `/sync/{token}` falls through and returns `405 Method Not Allowed` (blob.ts line 112). There is also no client code path that requests removal — `push` only writes, `pull` only reads, and `handleKeyImport` never invokes the sync server for the old key.

As a consequence, after a user rotates their key:

1. The old file `${oldSyncToken}.enc` continues to exist on the server's disk, unchanged, containing the entire user state at the moment of the last successful push.
2. The old syncToken is still a valid identifier at the server. Because `handleChallenge` and `handleSession` simply echo whatever `syncToken` the caller submits (see the finding excluded from this scan re: bearer semantics), any party still in possession of the compromised key can:
   - recompute the old `syncToken` via `deriveSyncToken(oldKey)`,
   - obtain a fresh 24-hour session token from `/sync/challenge` + `/sync/session`,
   - `GET /sync/{oldSyncToken}` to retrieve the ciphertext,
   - decrypt with the compromised key.
3. The attacker can also `PUT /sync/{oldSyncToken}` with new (encrypted-with-old-key) content, which the sync server accepts unconditionally as long as the syncToken matches the session — nothing on the server ties the "activity" of a syncToken to a legitimate live client. Because the write refreshes the file's mtime, LRU eviction (see `docs/DEPLOYMENT.md`, "Blob store capacity") will never reclaim the blob as long as the attacker touches it periodically.

### Why this survives rotation

The user's mental model, reinforced by the UI copy above, is that importing a new key severs the device from the previous server-side state ("*your existing server data will no longer be accessible from this device*"). That is accurate for *this device*, but it is silently inaccurate for the *attacker*: the previous server-side state is unchanged, and the attacker keeps the same access they had before rotation. The attacker's window of access is therefore not the ~24 h session TTL and not until the next LRU eviction — the attacker can, by periodically overwriting or reading the blob, keep the file "fresh" and unpruned indefinitely, and can freshly re-authenticate at any time from the compromised key alone.

Independently, this also creates a persistent data-remanence problem: users who intentionally uninstall the app or wish to withdraw their (albeit encrypted) data from the server have no way to do so, since the client never issues a delete and no admin surface is documented.

### Impact

- **Loss of the rotation escape hatch.** The only remediation the product offers for a compromised sync key is not effective against the very threat it visibly claims to address. A user who correctly diagnoses a leak and correctly performs the documented rotation still has to trust that the attacker never again wants the last-pre-rotation snapshot — plus every subsequent snapshot the attacker chooses to write.
- **Indefinite readability of the pre-rotation snapshot.** Everything in scope of an encrypted `AppState` (packs, chores, questions, completions with free-text answers, XP history, profile including `email` and `displayName`, sync state) remains recoverable by the attacker for as long as the file exists — and the attacker controls how long that is via write-refresh.
- **Silent server-side write-back.** An attacker with the old key can overwrite the blob at the old path with arbitrary (validly-encrypted) content. The victim never sees this, because they no longer read that path. But an attacker who *also* obtains the AES key on a *new* device via key export/import on the victim's flow (e.g., replays the victim's own future workflow of exporting the key from a synced device) may be able to seed misleading state — this is a smaller, more speculative concern, but it is enabled by the same missing endpoint.
- **No user-initiated erasure.** Users cannot ask the server to forget their encrypted data. Even under a benign uninstall, the file persists until LRU eviction, which is bounded only by other users' write pressure.

### Fix direction (for Planner)

At minimum, add an authenticated `DELETE /sync/{token}` handler (behind the same challenge/session flow as `PUT`), and have `handleKeyImport` invoke it against the *old* syncToken before overwriting `credentials.main.cryptoKey`. Doing the delete *before* the credential swap is important: once the credential store is overwritten, the client no longer has the old key and cannot derive the old syncToken to authenticate the delete. A well-formed fix will also decide the failure-mode contract (best-effort delete? block rotation on delete failure? surface a warning?) and update the confirm dialog copy to reflect what the rotation actually guarantees.

## Validation

**CONFIRMED — Medium severity. Genuine, exploitable security issue.**

### Verification

All material claims verified against source:

**Q1 — No DELETE endpoint:** Confirmed. `sync-server/index.ts` line 21 dispatches only `GET` and `PUT` to `/sync/{token}`. Everything else returns 404 (line 22 — note: the report says 405 but the router actually returns 404; this is a minor inaccuracy that does not affect the substance). `handleBlob` in `blob.ts` likewise handles only `GET` and `PUT`, returning 405 only as an internal fallback within the handler (line 112), which is in practice unreachable since the router only forwards GET/PUT.

**Q2 — `handleKeyImport` never contacts the server for the old key:** Confirmed. `src/components/profile/ProfilePage.tsx` lines 144–197 call only `importKeyFile` (local key parsing), `putCredentials` (local IndexedDB write), and `pull(db, ...)` (reads from server using the *new* key). There is no delete, no reference to the old syncToken, and no network call that could remove the old blob.

**Q3 — Attacker with old key can re-authenticate indefinitely:** Confirmed. `sync-server/handlers/challenge.ts` accepts any well-formed syncToken from the caller (line 21 stores `nonce → syncToken` directly). `sync-server/handlers/session.ts` lines 23–25 verify only that the nonce-stored value matches the submitted syncToken — a pure round-trip echo, no proof-of-knowledge beyond possession of the syncToken itself. Since `syncToken = SHA-256(rawAesKey)` (credentials.ts lines 17–23), any party holding the raw AES key can recompute the syncToken and complete a fresh session exchange at any time.

**Q4 — LRU eviction bypass via write-refresh is correct:** Confirmed. `blob.ts` line 87 explicitly skips eviction for `blob.name === \`${token}.enc\``, meaning the caller's own blob is never removed during their own PUT. An attacker performing periodic PUTs under the old syncToken will continuously refresh the file's mtime, preventing LRU eviction as long as the writes continue.

**Q5 — UI copy explicitly misrepresents what rotation achieves:** Confirmed. `ProfilePage.tsx` lines 152–156 present the confirm dialog: *"Importing a new key will change which server account this device syncs with. Your existing server data (encrypted with the old key) will no longer be accessible from this device."* The statement is accurate for the *device* but false for any *attacker* who holds the old key — the server data remains accessible to them indefinitely.

**Q6 — No duplicate in completed reports:** [[SEC-000022-0]] concerns cache headers; [[SEC-000025-3]] concerns the extractable key. Neither addresses the absent DELETE endpoint or the key-rotation escape-hatch failure. Not a duplicate.

### Severity Rationale

**Medium** (not High, not Low):

- **Exploitability is bounded:** The attack requires the attacker to already possess the pre-rotation raw AES key. This is precisely the scenario rotation is supposed to address, but it means the vulnerability does not create a *new* initial access path — it only extends the window of an already-established compromise.
- **Impact on the rotation use-case is total:** From the victim's perspective, key rotation is the *only* documented remediation for a compromised sync key. An attacker who holds the old key retains full read/write access to the pre-rotation blob, can keep it alive via write-refresh indefinitely, and the victim has no server-side mechanism to force removal. The rotation provides zero benefit against the threat it is designed to counter.
- **Scope is real but bounded:** Only users who (a) use encrypted sync and (b) perform key rotation are in scope. The vulnerability is not remotely exploitable without a prior key compromise.
- **Not High** because no new initial access vector is created — the attacker already had the key.
- **Not Low** because the failure is silent, the UI falsely implies remediation, and the attacker can maintain access indefinitely at will.

## Fix Plan

Add a minimal, authenticated `DELETE /sync/{token}` endpoint and wire the key-rotation flow on the client to invoke it against the *old* syncToken *before* the credential swap. Failure of the delete must not block the rotation (best-effort semantics), but the confirm-dialog copy should stop implying the pre-rotation blob is scrubbed.

**Server changes**

1. `sync-server/handlers/blob.ts` — extend `handleBlob` with a `DELETE` branch after the existing `PUT` branch:
   - Reuse the existing `authenticate(req)` gate (401 on missing/invalid session, 403 on session-token mismatch — identical to GET/PUT).
   - Compute `blobPath = join(BLOB_DIR, `${token}.enc`)`.
   - Call `await unlink(blobPath).catch((err) => { if (err.code !== 'ENOENT') throw err; })`.
   - Return `204 No Content` on success (including the ENOENT-idempotent case).
   - No quota/eviction machinery is needed — delete only shrinks disk usage.

2. `sync-server/index.ts` — add `DELETE` to the router dispatch:
   ```ts
   if (m && (req.method === 'GET' || req.method === 'PUT' || req.method === 'DELETE')) return handleBlob(req, m[1]!);
   ```

**Client changes**

3. `src/sync/server.ts`:
   - Broaden `authorizedFetch`'s `method` type union to `'GET' | 'PUT' | 'DELETE'`.
   - Export a new `deleteRemote(db, key)` helper (best-effort, side-effect free on failure):
     - Derive syncToken from the *supplied* `CryptoKey` (do not read the stored credential — the caller has the old key in hand and is about to overwrite the stored one).
     - `const res = await authorizedFetch('DELETE', syncToken)` — 204 or 404 are success; other statuses are silently ignored (best-effort). Wrap in try/catch so network errors also do not throw.
     - Return `{ deleted: boolean }` for observability (used by tests).
   - Rationale: expose the key parameter explicitly rather than reading from the DB because `handleKeyImport` calls this at a moment when the "old key" only exists in memory.

4. `src/components/profile/ProfilePage.tsx` (`handleKeyImport`):
   - Before `putCredentials(db, { id: 'main', cryptoKey: key })` (line 165), fetch the *current* stored key via `getOrCreateSyncKey(db)`, then `await deleteRemote(db, oldKey)`. Await the result but do not gate the rotation on it — a network failure must still allow the user to switch keys locally.
   - Only invoke `deleteRemote` if `getOrCreateSyncKey` returned an existing key (i.e., there was actually a prior key to clean up). Since `getOrCreateSyncKey` auto-creates when missing, gate this by first calling `getCredentials(db)` (already available from `@/db`) and skipping when null. This avoids spurious DELETEs during first-time setup on a fresh device.
   - Update the confirm-dialog copy on lines 152–156 to reflect that we now attempt a server-side scrub, with a truthful hedge for the failure case, e.g.:
     "Importing a new key will change which server account this device syncs with. This device will attempt to remove the encrypted backup stored under your old key from the server; if that fails (e.g., you're offline), the old backup may remain on the server until it is evicted."

**Session invalidation is out of scope for this fix** — the report notes a separate concern that any holder of the old raw key can re-authenticate. That is genuinely a distinct issue (session issuance has no proof-of-possession beyond the syncToken echo), and layering it into this fix would over-engineer the change. The delete + updated copy is the correct minimal scope: it collapses the *persistence* of the pre-rotation snapshot to a single successful HTTP call and stops the UI from lying about what rotation guarantees.
