# Decompression bomb in decryptState — unbounded gzip expansion OOMs browser tab

**Status:** DONE (Reviewed)
**Bug ID:** [[SEC-000013]]
**Severity:** Medium

## Location
`src/sync/encrypt.ts`, lines 22–38 (`decompress` function) and line 56 (`decryptState` call site)

## Description
`decryptState` pipes the ciphertext through `DecompressionStream('gzip')` with no cap on
how many bytes the stream may emit. An encrypted blob stored on the sync server is
`[12-byte IV][AES-GCM ciphertext]`; the AES-GCM tag ensures authenticity, so a
legitimately created blob cannot be tampered with in transit. However, **the user
themselves (or any code that can write to the sync endpoint, such as a compromised or
self-hosted server) can craft a gzip bomb**: a short compressed payload that expands to
gigabytes of repeated bytes.

Concrete attack path:

1. Attacker obtains a valid session for a syncToken (e.g. their own account, or via a
   previously exploited session).
2. Attacker constructs a gzip bomb (e.g. 1 MB compressed → 1 GB+ expanded, well within
   the 1 MB PUT limit enforced by the server).
3. Attacker encrypts the gzip bomb with the correct AES-GCM key and uploads the blob via
   `PUT /sync/<syncToken>`.
4. Any client that calls `pull()` will:
   a. Decrypt the AES-GCM ciphertext successfully (tag checks out).
   b. Call `decompress()`, which streams the expansion into unbounded Uint8Array chunks.
   c. Exhaust available browser/tab memory, causing a crash or freeze.

Even outside a multi-user attack scenario, a **user who imports a maliciously crafted
key file** triggers the same code path via `decryptedImport` in `src/sync/import.ts`
(line 35), because that function also calls `decryptState`.

The `MAX_BYTES = 1_048_576` check in `blob.ts` only limits the *compressed* (ciphertext)
size; it offers no protection against unbounded decompression output.

## Validation

Confirmed by code review. Key findings:

1. **`decompress()` has no size cap** — `src/sync/encrypt.ts` lines 22–38 collect all
   chunks into an unbounded array with zero byte-count guard. Confirmed.

2. **Server's 1 MB limit does not prevent gzip bombs** — `sync-server/handlers/blob.ts`
   line 6 sets `MAX_BYTES = 1_048_576` and checks it on the raw (compressed + encrypted)
   upload size. Standard gzip bombs achieve ~1000× expansion ratios, so 1 MB compressed
   can yield 1 GB+ decompressed. The server-side guard is irrelevant to decompression
   safety.

3. **Blob write access is scoped per-syncToken** — `blob.ts` lines 19–20 verify that
   the authenticated session's stored syncToken matches the URL token exactly. This
   prevents cross-user blob overwrite: an attacker **cannot** write a bomb to another
   user's syncToken without that user's session or AES-GCM key.

4. **AES-GCM key required for exploitation via sync** — The bomb payload must be
   encrypted with the target syncToken's AES-GCM key (derived from the user's secret).
   A third-party attacker without the key cannot forge a valid ciphertext. This narrows
   the sync-path attack to: (a) self-inflicted (user crafts their own bomb), (b) key
   compromise (attacker obtained the user's key), or (c) a compromised/malicious
   self-hosted sync server that stores a pre-crafted blob.

5. **Import path is the more realistic social-engineering vector** — `decryptedImport`
   in `src/sync/import.ts` (line 35) also calls `decryptState`. However, it uses
   `getOrCreateSyncKey(db)` — the local user's own key — so a foreign encrypted file
   will fail AES-GCM authentication. The import attack also requires the attacker to
   know (or have obtained) the user's own AES-GCM key.

6. **Impact is browser-tab DoS** — `pull()` in `src/sync/server.ts` line 106 calls
   `decryptState()` with no decompression guard. A successful attack exhausts the
   browser tab's memory, causing a crash or freeze. No code execution, no data
   exfiltration, no cross-user impact.

**Severity rationale (Medium):** The vulnerability is a real, unfixed code defect with
no decompression size cap. However, exploitability requires either key compromise or
self-inflicted crafting, and impact is limited to browser DoS (no RCE, no data breach,
no cross-user escalation). The import-path concern is real but also key-gated.

## Fix Plan

### Overview

Add a decompressed-byte cap inside `decompress()` in `src/sync/encrypt.ts`. The check runs in the streaming accumulation loop, so memory is never allocated beyond the limit — the function throws before constructing the final `Uint8Array`.

### Changes to `src/sync/encrypt.ts`

1. Add a module-level constant immediately before `decompress()`:
   ```ts
   const MAX_DECOMPRESSED_BYTES = 10 * 1024 * 1024; // 10 MB
   ```

2. Inside `decompress()`, replace the bare chunk-push loop (lines 29–32) with a guarded version that tracks a running byte total:
   ```ts
   let totalBytes = 0;
   while (true) {
     const { done, value } = await reader.read();
     if (done) break;
     totalBytes += value.byteLength;
     if (totalBytes > MAX_DECOMPRESSED_BYTES) {
       throw new Error(
         `Decompressed size exceeds limit of ${MAX_DECOMPRESSED_BYTES} bytes`
       );
     }
     chunks.push(value);
   }
   ```

No other files require changes. The constant and the guard are entirely internal to `decompress()`; both call sites (`decryptState` in `encrypt.ts` and `decryptedImport` via `src/sync/import.ts`) benefit automatically.

### Test Plan

**File:** `src/sync/encrypt.test.ts`

Add a new `it` block inside the existing `describe('encryptState / decryptState', ...)` suite. The test needs a helper that produces a valid gzip stream whose decompressed size exceeds `MAX_DECOMPRESSED_BYTES` (10 MB). We build it with the browser-native `CompressionStream` (same runtime as the production code), compressing a large `Uint8Array` of repeated bytes.

**Test name:** `'decryptState rejects a decompression bomb'`

```ts
it('decryptState rejects a decompression bomb', async () => {
  // Build a gzip stream that expands to > 10 MB (our limit)
  const expandedSize = 11 * 1024 * 1024; // 11 MB — just over the cap
  const plainBomb = new Uint8Array(expandedSize); // all-zero bytes compress very well

  // Compress with the same CompressionStream the production code uses
  const cs = new CompressionStream('gzip');
  const csWriter = cs.writable.getWriter();
  csWriter.write(plainBomb);
  csWriter.close();
  const compressedChunks: Uint8Array[] = [];
  const csReader = cs.readable.getReader();
  while (true) {
    const { done, value } = await csReader.read();
    if (done) break;
    compressedChunks.push(value);
  }
  const compressedTotal = compressedChunks.reduce((n, c) => n + c.length, 0);
  const compressed = new Uint8Array(compressedTotal);
  let off = 0;
  for (const c of compressedChunks) { compressed.set(c, off); off += c.length; }

  // Encrypt the compressed payload with a valid key (AES-GCM tag will verify)
  const key = await makeKey();
  const iv = crypto.getRandomValues(new Uint8Array(12));
  const ciphertext = await crypto.subtle.encrypt(
    { name: 'AES-GCM', iv },
    key,
    compressed,
  );
  const blob = new Uint8Array(12 + ciphertext.byteLength);
  blob.set(iv, 0);
  blob.set(new Uint8Array(ciphertext), 12);

  await expect(decryptState(key, blob)).rejects.toThrow(
    /exceeds limit/,
  );
});
```

**Why this test is sufficient:**
- The round-trip test that already exists (`'round-trips app state'`) covers the happy path — a real `AppState` JSON compresses to well under 10 MB.
- The new test exercises the exact guard path: valid AES-GCM ciphertext whose decompressed content exceeds the cap, confirming the promise rejects before OOM rather than succeeding silently.
