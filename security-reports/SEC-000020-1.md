# Multi-entry zip bomb bypasses per-entry size guard in backup import — allocations sum to unbounded memory

**Status:** DONE
**Reviewer:** Arne Ludwig (Claude Sonnet 4.6), 2026-07-03
**Bug ID:** [[SEC-000020]]
**Severity:** Medium

## Location

- `src/backup/backup.ts`, lines 16–23 — `unwrapStateFromZip` `filter` callback validates each `file.originalSize` individually, but does not track the **sum** of `originalSize` across entries in one ZIP
- `src/components/profile/ProfilePage.tsx`, lines 104–113 — backup import handler calling `unwrapStateFromZip` on user-selected file
- Underlying: `node_modules/fflate/esm/index.mjs`, lines 2692–2707 (`unzipSync`) — the loop invokes `filter` per file and then executes `inflateSync(..., { out: new u8(su) })` per file with **no cumulative allocation cap across the batch**

## Description

### Background

[[SEC-000016]] added a `filter` callback to `unzipSync` inside `unwrapStateFromZip` to guard against
a single-entry zip bomb that declared an oversized `originalSize` in the central directory
(fflate pre-allocates `new u8(originalSize)` before decompression, so the declared size is a
memory-allocation vector even for microscopic compressed payloads).

The current filter (`src/backup/backup.ts` lines 17–22):

```ts
export function unwrapStateFromZip(zipBytes: Uint8Array): AppState {
  const files = unzipSync(zipBytes, {
    filter(file) {
      if (file.originalSize > MAX_UNCOMPRESSED_BYTES)
        throw new Error(`Backup entry "${file.name}" is too large to decompress safely`);
      return true;
    },
  });
  ...
}
```

This blocks any **single** ZIP entry whose `originalSize` exceeds 10 MB. But it does not
accumulate across entries.

### The bypass

fflate's `unzipSync` (`node_modules/fflate/esm/index.mjs` lines 2692–2707) iterates every
entry in the central directory and, for each entry that passes the filter, allocates a
dedicated output buffer of the declared size:

```js
for (var i = 0; i < c; ++i) {
    var _a = zh(data, o, z), c_2 = _a[0], sc = _a[1], su = _a[2], fn = _a[3], no = _a[4], off = _a[5], b = slzh(data, off);
    o = no;
    if (!fltr || fltr({ name: fn, size: sc, originalSize: su, compression: c_2 })) {
        if (!c_2)
            files[fn] = slc(data, b, b + sc);
        else if (c_2 == 8)
            files[fn] = inflateSync(data.subarray(b, b + sc), { out: new u8(su) });  // ← alloc per file
        ...
    }
}
```

There is **no cumulative cap**. An attacker crafts a ZIP with many entries, each declaring
`originalSize = 10 MB` (or 10 MB − 1, safely under the strict `>` check) and each carrying
a near-empty deflate payload (~20 bytes). The ZIP on disk fits in a few KB but declares
tens of gigabytes of expansion in aggregate.

### Concrete attack path

1. Attacker crafts a ZIP with, say, 1 000 file entries in the central directory. Each entry:
   - `originalSize = 10 485 760` (exactly the `MAX_UNCOMPRESSED_BYTES` threshold — passes
     the strict-`>` filter)
   - Compressed size ≈ 20 bytes (empty deflate stream, or a single-byte payload)
   - Filenames can all be different (e.g., `f0.bin`, `f1.bin`, …) or duplicates — the
     allocation loop runs regardless.
2. Total ZIP-on-disk size: ≈ 60 KB (mostly central-directory metadata). Well under any
   user-facing "large file" heuristic; passes the file-picker without suspicion.
3. The attacker social-engineers a victim into importing the file (e.g. "here's a starter
   pack backup", exactly the scenario [[SEC-000016]] modeled).
4. In `handleImport` (`ProfilePage.tsx` lines 108–110):
   ```ts
   const zipBytes = new Uint8Array(buffer);
   state = unwrapStateFromZip(zipBytes);
   ```
5. Inside `unwrapStateFromZip`, `unzipSync` iterates all 1 000 entries:
   - Filter is called with `originalSize = 10 485 760` — not `> 10_485_760`, so passes.
   - `inflateSync(…, { out: new u8(10_485_760) })` allocates 10 MB.
   - Repeat 1 000 times → cumulative allocation ≈ 10 GB.
6. The browser's JS heap grows past the tab's memory limit. Chromium's default per-tab
   heap limit is ~4 GB on 64-bit desktop, lower on mobile. The tab crashes long before the
   loop completes; on constrained devices, the whole browser process may become
   unresponsive or be OOM-killed.

### Why the [[SEC-000016]] fix does not cover this

[[SEC-000016]] was framed around a **single** oversized entry (the report and its test both
craft a single-file ZIP and set the size field to 0xFFFFFFFF). The fix's per-entry `>`
comparison is correct for that variant. It does not accumulate `originalSize` across
entries, so an attacker who stays under the per-entry cap can still exhaust memory by
scaling horizontally instead of vertically.

The existing regression test (`src/backup/backup.test.ts` lines 68–100) verifies only the
single-entry case (patches one entry's originalSize to 0xFFFFFFFF). No test exercises the
many-entries variant, so this bypass survives the current test suite.

### Fix direction (for the Planner)

The `filter` callback must track the cumulative declared `originalSize` and refuse to
process any entry that would push the sum past `MAX_UNCOMPRESSED_BYTES`. Something like:

```ts
let totalDeclared = 0;
const files = unzipSync(zipBytes, {
  filter(file) {
    totalDeclared += file.originalSize;
    if (file.originalSize > MAX_UNCOMPRESSED_BYTES || totalDeclared > MAX_UNCOMPRESSED_BYTES) {
      throw new Error(`Backup ZIP declares oversized decompression (…)`);
    }
    return true;
  },
});
```

Since `state.json` is the only expected file (`STATE_FILENAME`), an even tighter fix is to
refuse the ZIP up-front if the central directory contains more than one entry — but the
cumulative cap is the general-purpose fix that keeps the code robust to future format
additions.

## Validation

**CONFIRMED — genuine, exploitable denial-of-service via multi-entry zip bomb.**

### Reachability

The vulnerable path is directly reachable from untrusted user input. `ProfilePage.tsx` lines 108–109 pass a raw user-supplied file straight into `unwrapStateFromZip` with no pre-flight entry count or aggregate size check. Any user who opens the import dialog and selects an attacker-supplied file triggers the vulnerable code.

### Attacker control

The attacker has full control over the ZIP binary — in particular the number of entries in the central directory and each entry's declared `originalSize` field. The only constraint is that each compressed payload must be syntactically valid deflate, which is satisfied by a near-empty stream (~20 bytes). A 1 000-entry bomb fits in ~60 KB on disk.

### Why the bypass works

The filter at `backup.ts:19` uses a strict `>` comparison (`file.originalSize > MAX_UNCOMPRESSED_BYTES`). An attacker sets each entry's `originalSize` to exactly `10_485_760` (= `MAX_UNCOMPRESSED_BYTES`), which is not strictly greater and therefore passes. fflate's `unzipSync` then executes `inflateSync(…, { out: new u8(su) })` for each passing entry with no cross-entry accumulation. 1 000 entries × 10 MB = ~10 GB of declared allocation — far beyond Chromium's per-tab heap limit (~4 GB on 64-bit desktop, lower on mobile). The tab crashes before the loop completes.

### Impact

Denial-of-service: the victim's browser tab (or in constrained environments the entire browser process) is OOM-killed. No code execution, data exfiltration, or authentication bypass. The attack requires social engineering (convince the victim to import a crafted "backup" file), which the existing [[SEC-000016]] threat model already accepted as a realistic scenario.

### Test coverage gap

`src/backup/backup.test.ts` lines 68–100 test only the single-entry `0xFFFFFFFF` case introduced by [[SEC-000016]]. No test exercises multiple entries each at or below the per-entry cap, so this bypass survives the current regression suite.

### Severity rationale: Medium

Impact is limited to per-user DoS with a social-engineering precondition. The vulnerability is mechanically straightforward to exploit once the precondition is met, and the [[SEC-000016]] fix creates false confidence that the zip-bomb vector is fully closed — making this a meaningful residual risk that warrants a fix.

## Fix Plan

### Scope

Modify **only** `src/backup/backup.ts` — the `unwrapStateFromZip` function. No other files change. No new constants, no new exports.

### Change 1 — Tighten per-entry check from `>` to `>=`

An entry declaring exactly `MAX_UNCOMPRESSED_BYTES` (10 MB) is already at the ceiling of what
the app promises to decompress; there is no legitimate reason a single `state.json` payload
would hit that exact figure, and the confirmed exploit relies on the boundary passing. Reject
at the boundary too.

### Change 2 — Add a cumulative total-size cap

Track a `totalDeclared` accumulator in the closure over the `filter` callback. Each call adds
the entry's `originalSize` to it. If either the per-entry value **or** the running total
reaches `MAX_UNCOMPRESSED_BYTES`, throw.

Reuse the same `MAX_UNCOMPRESSED_BYTES` constant for both caps — the aggregate is intentionally
the same 10 MB budget, not larger. `state.json` is the only expected file, so the entire
legitimate payload is one entry well under the cap; there is no legitimate multi-entry
consumer to break.

### Exact edit

Replace lines 16–23 of `src/backup/backup.ts`:

```ts
export function unwrapStateFromZip(zipBytes: Uint8Array): AppState {
  let totalDeclared = 0;
  const files = unzipSync(zipBytes, {
    filter(file) {
      totalDeclared += file.originalSize;
      if (file.originalSize >= MAX_UNCOMPRESSED_BYTES || totalDeclared >= MAX_UNCOMPRESSED_BYTES)
        throw new Error(`Backup entry "${file.name}" is too large to decompress safely`);
      return true;
    },
  });
  const stateBytes = files[STATE_FILENAME];
  if (!stateBytes) throw new Error(`ZIP does not contain ${STATE_FILENAME}`);
  return JSON.parse(strFromU8(stateBytes)) as AppState;
}
```

Notes for the implementer:
- Keep the error message wording identical to the existing text so the existing regression
  test (`/too large/i` matcher at `backup.test.ts:98`) continues to pass.
- Do not extract a new constant for the aggregate cap; the intent is that the aggregate
  budget equals the per-entry budget.
- Do not add a "count-of-entries" pre-check. The cumulative-size guard is sufficient and
  keeps the code robust to any future single-legitimate-entry evolution.

### Existing-behavior compatibility

- The happy-path round-trip test at `backup.test.ts:26` writes a `state.json` of ~500 bytes.
  `originalSize` is well under 10 MB and the total is that one entry. Still passes.
- The existing single-entry `0xFFFFFFFF` bomb test at `backup.test.ts:69` sets one entry to
  ~4 GB. That trips both the per-entry `>=` check and the cumulative check on the first
  iteration. Still throws with `/too large/i`. Still passes.
- The "missing state.json" test at `backup.test.ts:36` uses a ZIP with a tiny `other.json`;
  the filter allows it (tiny size), then the `STATE_FILENAME` lookup throws. Still passes.

### Test Plan

**File:** `src/backup/backup.test.ts` — extend the existing `describe('unwrapStateFromZip (zip bomb guard)')` block (starts at line 68).

**Test name:** `'throws when the sum of declared originalSize across entries exceeds the cap'`

**Placement:** Add as a new `it(...)` inside the existing `describe` block at line 68, immediately after the existing single-entry test (i.e. after line 99, before the closing `});` at line 100).

**Approach for constructing the malicious ZIP:**

1. Use `fflate.zipSync` (already imported at line 2) to build a two-entry ZIP: `state.json`
   and a filler entry `pad.bin`, each with a tiny payload.
2. Walk the produced bytes to find every central-directory file-header signature
   (little-endian bytes `50 4B 01 02` = `0x02014B50`) — same technique as the existing
   single-entry test at lines 82–88, but collect **all** offsets rather than the first.
3. For each central-directory offset, patch bytes `[cdOffset+24 .. cdOffset+27]`
   (`originalSize`, little-endian uint32) to `MAX_UNCOMPRESSED_BYTES - 1`
   (10 485 759 = `0x009FFFFF`, LE bytes `FF FF 9F 00`).

   Rationale for `MAX_UNCOMPRESSED_BYTES - 1` rather than exactly `MAX_UNCOMPRESSED_BYTES`:
   the tightened per-entry `>=` check (Change 1) would fire on the *first* entry if we set
   each to exactly `MAX_UNCOMPRESSED_BYTES`, which would still pass the test but would not
   exercise the cumulative-guard code path — it would exercise the per-entry guard. Using
   `MAX_UNCOMPRESSED_BYTES - 1` per entry keeps each individual entry strictly under the
   per-entry cap, so only the cumulative guard (`totalDeclared >= MAX_UNCOMPRESSED_BYTES`
   after the second entry, since 2 × (10 MB − 1) > 10 MB) can trip the throw. This makes
   the test target Change 2 specifically.

4. There is no need to patch the local-file-header size fields. fflate's `unzipSync` reads
   `originalSize` from the central directory, and the filter is invoked before any local-
   header parsing that would care about the size.

**Exact test code to add:**

```ts
it('throws when the sum of declared originalSize across entries exceeds the cap', () => {
  // Build a two-entry ZIP with tiny payloads.
  const twoEntryZip = zipSync({
    'state.json': strToU8('{}'),
    'pad.bin':    strToU8('x'),
  });
  const patched = new Uint8Array(twoEntryZip);

  // Find every central-directory file-header signature (0x02014B50, LE: 50 4B 01 02).
  const cdOffsets: number[] = [];
  for (let i = 0; i < patched.length - 4; i++) {
    if (patched[i] === 0x50 && patched[i+1] === 0x4b &&
        patched[i+2] === 0x01 && patched[i+3] === 0x02) {
      cdOffsets.push(i);
    }
  }
  expect(cdOffsets.length).toBe(2);

  // Patch each entry's uncompressed-size field to MAX_UNCOMPRESSED_BYTES - 1
  // (10 485 759 = 0x009FFFFF, LE bytes FF FF 9F 00).
  // Each entry individually is strictly under the per-entry cap, so only the
  // cumulative guard can reject the ZIP.
  for (const cd of cdOffsets) {
    patched[cd + 24] = 0xff;
    patched[cd + 25] = 0xff;
    patched[cd + 26] = 0x9f;
    patched[cd + 27] = 0x00;
  }

  // Before fix: per-entry check passes for each (10 MB - 1 is not > 10 MB), no
  // cumulative accumulator exists, so unzipSync proceeds to allocate ~20 MB. No throw.
  // After fix: cumulative accumulator reaches ~20 MB on the second entry, trips the
  // >= MAX_UNCOMPRESSED_BYTES check, throws.
  expect(() => unwrapStateFromZip(patched)).toThrow(/too large/i);
});
```

**Failure output expected during RED phase:**

The `expect(...).toThrow(/too large/i)` assertion fails because `unwrapStateFromZip` returns
successfully (or throws a JSON-parse error on the empty-inflated `{}` after allocating ~20 MB —
either way, not a `/too large/i` error). Bun test reports the expected-vs-actual mismatch on
the `toThrow` matcher.

**Pass output expected during GREEN phase:**

The second `filter` invocation pushes `totalDeclared` to `2 × (10 485 760 - 1) = 20 971 518`,
which is `>= MAX_UNCOMPRESSED_BYTES`. The filter throws `Backup entry "pad.bin" is too large
to decompress safely` (or `"state.json"` depending on central-directory order), matching
`/too large/i`. Test passes.
