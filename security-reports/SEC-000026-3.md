# Sync server accepts unbounded new sync tokens with no quota, enabling unauthenticated disk-exhaustion DoS

**Status:** REVIEW
**Bug ID:** SEC-000026
**Severity:** High

## Location
- `sync-server/handlers/challenge.ts` (lines 4–23) — accepts any 64-hex-character string as `syncToken` and stores a nonce for it.
- `sync-server/handlers/session.ts` (lines 4–30) — issues a session token for any nonce+syncToken pair the requester holds (both of which the requester itself supplied).
- `sync-server/handlers/blob.ts` (lines 17–47) — `PUT /sync/{token}` writes up to 1 MB per token to `${BLOB_DIR}/${token}.enc`. There is no per-IP quota, per-token quota, blob expiry, or ceiling on the total number of tokens the server will accept.
- `nginx/sync-location.conf.template` (lines 6–17) — `sync_challenge` is capped at 5 req/min and `sync_write` at 30 req/min **per IP**, but nothing limits the number of *distinct* `syncToken` values one IP may register or the number of blob files that accumulate.

## Description
The sync server has no notion of registration, quota, blob expiry, or garbage collection. Any Internet-reachable client can obtain a fresh, persistent 1 MB blob slot by:

1. Generating a random 64-hex string as a "syncToken" (no client key material or HMAC is required — see the existing "HMAC challenge-response is unimplemented" note in `exclusions.txt`).
2. `POST /sync/challenge` with that string. `handleChallenge` only validates the shape (`^[a-f0-9]{64}$`) and stores `nonce:<nonce>` → `syncToken` in Redis with a 60-second TTL. No proof-of-work, no captcha, no account, no HMAC.
3. `POST /sync/session` with the returned nonce and the same syncToken. `handleSession` compares the two strings the *same requester* just supplied, then writes `session:<sessionToken>` → `syncToken` to Redis with an 86 400-second TTL.
4. `PUT /sync/{syncToken}` with a 1 MB body. `handleBlob` calls `writeFile(join(BLOB_DIR, ${token}.enc), Buffer.from(data))` — the file has no TTL and no cleanup path anywhere in the codebase (`grep -rn "unlink\|delete\|cleanup" sync-server/handlers` returns nothing).

Consequences:

- **Unbounded blob-directory growth.** Each new random syncToken produces one 1 MB file that lives forever. There is no expiry, no LRU, no per-IP cap on distinct tokens, no total-storage limit.
- **DoS via disk exhaustion.** The `sync_challenge` nginx zone caps *one IP* at 5 requests/minute, but every one of those requests can initialize a new syncToken and thus a new 1 MB slot. That is 5 × 60 × 24 ≈ 7 200 blobs/day/IP ≈ **7.2 GB/day/IP** of permanent, unrecoverable disk usage. A distributed attacker fills a typical VPS in hours.
- **Unbounded Redis growth.** Each authenticated request also plants a `session:<64-hex>` entry with a 24-hour TTL. At 5 req/min/IP that is ~7 200 keys/day/IP alive at any moment — again per attacker IP.
- **No log discrimination between attacker floods and legitimate use.** All writes come from valid sessions and 204 successfully.
- **The design amplifies the "sync auth is effectively a bearer token" issue.** Because the auth model does not tie a syncToken to any account or key material, the server cannot even in principle reject "unknown" tokens — every new random string is treated as a first-time user.

The `MAX_BYTES = 1024 * 1024` cap in `blob.ts` bounds the size of *one* blob but does nothing about the *number* of blobs, which is the actual attack vector. `Bun.serve({ maxRequestBodySize: MAX_BODY_SIZE })` in `index.ts` similarly caps per-request size, not aggregate storage.

This is distinct from the two exclusions:
- Exclusion 1 concerns *authentication strength* (any holder of a syncToken can read/write that specific blob). This finding concerns *resource exhaustion* — an anonymous attacker who has never possessed any legitimate token can still fill the disk with new tokens they invent.
- Exclusion 2 concerns *client-side key exfiltration*. This finding is server-side and does not depend on any XSS, IndexedDB access, or existing user.

## Validation

**CONFIRMED — High severity. Genuine, exploitable resource-exhaustion DoS.**

### Duplicate check

Completed reports checked: SEC-000022-0 (cache headers, discarded), SEC-000024-3 (unimplemented HMAC/bearer token), SEC-000025-3 (extractable AES key in IndexedDB). None covers unbounded blob-directory growth or disk-exhaustion DoS. Not a duplicate.

Note: SEC-000006-1.md (lines 282–291) explicitly acknowledges this gap ("Long-tail storage growth → no — anyone can PUT 1 MB to a fresh random syncToken; nothing caps total disk") and deferred it ("No follow-up ticket filed yet"). SEC-000024-3.md references it as "recommended future hardening." This report is the follow-up ticket that was never filed.

### Verification

All claims verified against source code:

**Q1 — `handleChallenge` accepts any 64-hex syncToken with no quota or prior-registration check:** Confirmed. `challenge.ts` line 16 validates only the regex `^[a-f0-9]{64}$` and then writes `nonce:${nonce} → syncToken` to Redis with a 60-second TTL. There is no check for whether the syncToken has been seen before, no per-token rate limit, no cap on how many distinct tokens one caller may register.

**Q2 — `handleBlob` PUT writes an unbounded-lifetime file with no cleanup path:** Confirmed. `blob.ts` line 40 calls `writeFile(blobPath, Buffer.from(data))`. The file has no TTL, no expiry callback, and no companion delete path. A grep for `unlink`, `cleanup`, `quota`, `evict`, and `expire` across all handler files returns zero results in the handlers directory (the only `unlink` in the package is in `index.ts` line 26, which removes the Unix socket on startup).

**Q3 — nginx rate limits are per-IP only and do not bound aggregate blob count:** Confirmed. `nginx/sync-location.conf.template` defines `sync_challenge` at 5 req/min per `$binary_remote_addr`. This bounds the rate from a single IP but does not limit the number of distinct syncToken values that IP may register, and does nothing against a distributed (multi-IP) attacker. The math in the report is correct: 5 req/min × 60 × 24 = 7,200 distinct blobs/day/IP = 7.2 GB/day/IP.

**Q4 — No other quota or cleanup mechanism in the codebase:** Confirmed. Neither `index.ts`, the handlers, nor any cronjob, systemd timer, or Docker volume configuration contains blob expiry, LRU eviction, or total-storage limits. The Dockerfile and `docker-compose.yml` do not configure any volume size limits.

**Q5 — The attack requires zero legitimate credentials:** Confirmed. An attacker generates a random 64-hex string locally, calls `/sync/challenge` (returns a nonce), calls `/sync/session` (returns a sessionToken — because the client supplies both the nonce and the syncToken, it trivially passes the comparison in `session.ts:25`), then calls `PUT /sync/{syncToken}` with a 1 MB body. This entire flow is unauthenticated in the meaningful sense: no pre-existing account, no secret, no relationship with any real user.

**Q6 — Redis unbounded session-key growth is a secondary confirmed vector:** Each completed attack cycle plants a `session:*` key with a 24-hour TTL in Redis. At 5 tokens/min/IP this is ~7,200 live keys/day/IP, which accumulates in Redis memory in proportion to the attack intensity. This compounds the disk-exhaustion DoS with a memory-exhaustion DoS against Redis.

### Severity Rationale

**High** (not Critical) because:

- **Availability impact is severe and cumulative.** An attacker can permanently fill the host disk with junk blobs at a rate of 7.2 GB/day per IP, with no reclaim mechanism. A single-IP attacker empties a 100 GB VPS in under two weeks; a modest botnet does it in hours. Once full, the sync server returns 500 for all users and the disk may affect other services on the host.
- **Fully unauthenticated; no prior knowledge of any legitimate syncToken is required.** This is materially worse than the blob-overwrite vector in SEC-000024, which requires a leaked syncToken.
- **Not Critical** because the attack is rate-limited per IP by nginx (reducing single-source impact), does not directly compromise confidentiality or integrity of any user's data (blobs are new random tokens, not overwrites of existing ones), and requires sustained sustained network activity that is visible in logs and blockable by IP.
- The deferred hardening recommendation in SEC-000006-1.md ("Disk quota + LRU eviction on the blob store: highest-leverage") precisely describes the mitigation; the fact that it was explicitly deferred rather than implemented makes this a known unmitigated risk, not a theoretical one.

## Fix Plan

### Status: REVIEW — needs policy decision before implementation

This finding is the follow-up ticket that SEC-000006-1.md:291 said "was never filed." SEC-000006 explicitly considered this exact risk on 2026-07-04 and **accepted it as a deferred residual** with three mutually-exclusive hardening options on the table (SEC-000006-1.md:285–291). None of them is a purely technical choice a planner can make unilaterally, because each carries a distinct product/operator policy implication and each has *different failing tests*.

**The three options SEC-000006 identified, restated in policy terms:**

1. **Disk quota + LRU eviction on the blob store.** SEC-000006's own recommendation, described there as "highest-leverage" but explicitly gated on "documenting a 'sync at least every X months to persist' contract." That is a **product contract change**: users who go quiet for the eviction window silently lose their server-side backup, and the app must expose that guarantee (or lack thereof) to the user. Choosing an eviction window (30 days? 6 months? 2 years?) and a total-disk cap (10 GB? 100 GB? operator-configurable with what default?) are operator/policy calls, and the app's "encrypted sync + device pairing" UX has to be updated to communicate the new contract. This also interacts with SEC-000025's device-pairing story, which is itself in REVIEW.

2. **Cloudflare Turnstile (or hCaptcha) on `/sync/challenge`.** Adds a **third-party dependency** to a service whose current stack is deliberately self-hostable (bun + redis + nginx). Turnstile embeds a Cloudflare script in the app bundle and sends every challenge request through Cloudflare's fraud-detection pipeline — a privacy and deployment-story change that is not the planner's to make. hCaptcha has the same shape with a different vendor. This option also does not close the underlying "no cumulative quota" gap; it only raises the cost of entry.

3. **Client-side proof-of-work on `/sync/challenge`.** No external dependency, but imposes ~500 ms CPU on every legitimate client challenge, which is a **UX regression** on mobile and low-power devices. Difficulty tuning is operator policy, and (as SEC-000006-1.md:289 notes) "sophisticated attackers can rent compute cheaply" — so this option raises attacker cost without bounding cumulative damage.

**Why this cannot be planned autonomously:**

- **SEC-000006 already resolved this exact question as "defer with recommendation, no ticket filed."** Overturning that acceptance is a policy reversal, not a bug fix. The planner would be substituting its judgment for the reviewer's prior explicit choice to accept the risk. If the answer is "SEC-000006's acceptance stands and we file no follow-up," that is a legitimate WONTFIX-with-cross-reference, but it requires the reviewer to reaffirm the SEC-000006 decision in light of this fresh report of the same underlying weakness.
- **SEC-000024-3.md is itself in REVIEW** and lists this exact DoS control as its **Option 3** ("Adopt a stronger control that closes the DoS gap without the bundle-secret fiction … disk quota with LRU eviction (SEC-000006-1.md:287, 'highest-leverage'), or Turnstile, or PoW"). Picking a resolution here without coordinating with SEC-000024 could either preempt or contradict SEC-000024's still-open review. The two reviews should be resolved together.
- **Each option has a different failing test.** There is no single "the fix" whose test can be written down without first choosing. Disk-quota tests assert `507 Insufficient Storage` past a threshold; LRU tests assert eviction of the oldest blob past a count/size cap; Turnstile tests assert `403` without a valid token; PoW tests assert `400` without a valid solution. Committing to any one of these locks in the corresponding operator/product contract.
- **A hybrid "cheap holding fix" (e.g. hard-cap total blob count in Redis, 507 past the limit) still requires a policy value.** The threshold, the response code semantics, and the operator-recovery story are all policy calls. Even the "safest" hybrid — say, a global 10 GB cap that returns 507 past that point with no eviction — degrades service for *legitimate* new users once an attacker fills the quota, which is arguably worse than the current DoS. Without an eviction/expiry story, a hard quota simply moves the failure mode from "disk full" to "sync locked out," and picking between those failure modes is the same policy call.

**Recommended reviewer decision path:**

1. **Ratify SEC-000006's acceptance** — mark SEC-000026 WONTFIX with a cross-reference to SEC-000006-1.md:283–291, and either (a) genuinely accept the residual risk with an operator-visible warning in `docs/DEPLOYMENT.md` about monitoring blob-directory size, or (b) file a formally-tracked "future hardening" ticket in the project issue tracker with an assigned owner and a scheduled review date. The current state ("no follow-up ticket filed yet") is not a resolution.
2. **Implement Option 1 (disk quota + LRU eviction)** — SEC-000006's own recommendation. Requires a product decision on the eviction window and its exposure in the UI, plus a docs update to `docs/DEPLOYMENT.md` describing the "sync at least every X months to persist" contract. If chosen, this also closes SEC-000024's Option 3.
3. **Implement Option 2 (Turnstile) or Option 3 (PoW)** — SEC-000006's alternatives. Requires product sign-off on the third-party dependency (Turnstile) or the mobile UX regression (PoW).
4. **Hybrid: Option 1 + rotate the residual concern into SEC-000024.** Land disk quota + LRU as a scoped fix here; leave the "unauthenticated Redis key growth" secondary vector for SEC-000024's HMAC decision to address (a shared-secret HMAC gate on `/sync/challenge` bounds Redis growth to authenticated clients, which is Option 2 of SEC-000024's own REVIEW).

The reviewer needs to pick 1, 2, 3, or 4 (or an explicit hybrid) before an implementer can proceed. All are defensible; the choice depends on how much cumulative-abuse risk the operator accepts, whether a third-party captcha or a mobile CPU tax is tolerable, and whether SEC-000006's "no follow-up ticket" state should be closed by acceptance-with-monitoring or by shipping a control.

### Test Plan

Deferred until the policy decision is made. Each option has a different failing test:

- **Option 1 (disk quota + LRU eviction):** `sync-server/handlers/blob.test.ts`, new test `PUT /sync/{token} returns 507 when aggregate blob directory exceeds SYNC_BLOB_QUOTA_BYTES` — assert `response.status === 507` after seeding N blobs summing above the quota, followed by a further PUT. Companion LRU test `PUT /sync/{token} evicts the oldest blob when the count exceeds SYNC_BLOB_MAX_COUNT` — assert the least-recently-modified blob file no longer exists after a fresh PUT once the count cap is hit. RED: current handler unconditionally writes; both assertions fail. GREEN: after quota + eviction logic lands.
- **Option 2 (Turnstile on `/sync/challenge`):** `sync-server/handlers/challenge.test.ts`, invert an existing test to `returns 403 when Turnstile token is missing` and add `returns 200 when Turnstile token is valid` (mocking the verify endpoint). RED: current handler ignores captcha entirely. GREEN: after Turnstile verify lands.
- **Option 3 (proof-of-work on `/sync/challenge`):** `sync-server/handlers/challenge.test.ts`, new tests `returns 400 when PoW solution is missing` and `returns 200 when PoW solution matches issued difficulty target`. RED: current handler ignores PoW entirely. GREEN: after PoW verification lands.
- **WONTFIX (ratify SEC-000006):** no test; `docs/DEPLOYMENT.md` gains a monitoring section and SEC-000026 is closed with a cross-reference.
