# Zip bomb in backup import — unbounded fflate allocation OOMs browser tab

**Status:** DONE
**Bug ID:** SEC-000016
**Severity:** Medium

## Location
`src/backup/backup.ts`, line 16 (`unwrapStateFromZip`, call to `unzipSync`)
`src/components/profile/ProfilePage.tsx`, lines 104–113 (backup import handler calling `unwrapStateFromZip`)

## Description

`unwrapStateFromZip` in `src/backup/backup.ts` calls `fflate.unzipSync(zipBytes)` with no size
limit or filter option:

```ts
export function unwrapStateFromZip(zipBytes: Uint8Array): AppState {
  const files = unzipSync(zipBytes);           // ← no opts.filter, no size cap
  const stateBytes = files[STATE_FILENAME];
  if (!stateBytes) throw new Error(`ZIP does not contain ${STATE_FILENAME}`);
  return JSON.parse(strFromU8(stateBytes)) as AppState;
}
```

`fflate.unzipSync` allocates the output buffer using the **uncompressed size declared in the
ZIP central directory** (`originalSize` field). From the fflate source:

```js
files[fn] = inflateSync(data.subarray(b, b + sc), { out: new u8(su) });
//                                                           ^^^^^^^^^
//                  su = originalSize read from the ZIP header — fully attacker-controlled
```

An attacker can craft a malicious ZIP file in which a tiny deflate-compressed payload
(well under 1 MB so it looks plausible as a backup) declares an `originalSize` up to
4 294 967 295 bytes (~4 GB). When a user tries to restore this file:

1. `unzipSync` reads `su = 4_294_967_295` from the central directory.
2. Before any decompression, it executes `new u8(4_294_967_295)` — a pre-allocation of
   ~4 GB.
3. The browser immediately attempts to grow the JavaScript heap by 4 GB. On devices with
   less RAM (phones, low-end laptops, constrained desktop tabs), this exhausts available
   memory and crashes or freezes the tab.
4. If the OS OOM killer does not intervene, the heap grows and `inflateSync` begins
   writing into the huge buffer; a genuine gzip bomb (highly repetitive compressed data)
   then produces a gigabyte-scale expansion that amplifies the DoS further.

**Contrast with the fixed sync path:** `src/sync/encrypt.ts` was updated (SEC-000013 fix)
to cap decompression at `MAX_DECOMPRESSED_BYTES = 10 MB` using a streaming
`DecompressionStream` with an incremental byte counter. The backup path was not updated
alongside it and remains unguarded.

**Attack scenario:** An attacker social-engineers a user into importing a "shared
configuration backup" or "starter pack preset" ZIP file. The file is <50 KB on disk
(compressed), declares a 4 GB originalSize, and causes an immediate OOM when the user
clicks "Restore from backup". No authentication, no network access to the sync server,
and no existing data are required — the only prerequisite is convincing the user to
open the file in the Profile → Backup section of the app.

## Validation

Confirmed by code review. Key findings:

1. **`unwrapStateFromZip` calls `unzipSync` with no options** — `src/backup/backup.ts`
   line 16 is a bare `unzipSync(zipBytes)` call. No `filter` callback, no size guard.
   Confirmed by direct file inspection.

2. **fflate pre-allocates based on `originalSize` before decompression** — In
   `node_modules/fflate/esm/browser.js` line 2686, the `unzipSync` implementation reads
   `su` (uncompressed size) from the ZIP header via `zh()`, then passes `{ out: new u8(su) }`
   to `inflateSync`. The filter callback at line 2677–2682 is only invoked if `opts.filter`
   is present; without it, the allocation at line 2686 is unconditional. The `su` value is
   fully attacker-controlled from the ZIP central directory. The report's claim about
   pre-allocation is accurate.

3. **No file-size check exists before calling `unzipSync`** — `ProfilePage.tsx`
   lines 85–109 read the file into a `Uint8Array` via `arrayBuffer()` and pass it
   directly to `unwrapStateFromZip`. There is no check on `file.size`, no `filter` option
   passed, and no decompressed-byte cap anywhere in the backup path.

4. **The backup path is a separate code path not covered by the SEC-000013 fix** —
   SEC-000013 fixed `src/sync/encrypt.ts`'s `decompress()` function (gzip streaming via
   `DecompressionStream`). The backup path uses `fflate.unzipSync` in `src/backup/backup.ts`
   and was not touched by that fix. Confirmed by grepping: `MAX_DECOMPRESSED_BYTES` and
   `DecompressionStream` appear only in `src/sync/encrypt.ts`.

5. **The attack vector is real and requires no authentication** — `ProfilePage.tsx`
   `handleImport` (lines 85–123) exposes a standard `<input type="file">` UI element.
   The only barrier is a `window.confirm()` dialog shown when existing data is present.
   A user who accepts a malicious ZIP and clicks through the confirmation dialog
   (or has no existing data, bypassing it entirely) immediately triggers the OOM via
   `unwrapStateFromZip`. No sync credentials, no server access, and no existing account
   data are needed.

**Severity rationale (Medium):** The vulnerability is a real, unguarded code defect with
no decompression size cap and no input size validation. Exploitability requires only
social engineering — lower barrier than SEC-000013 which required key compromise or a
malicious sync server. Impact is limited to browser-tab DoS (no RCE, no data breach,
no cross-user escalation), keeping it at Medium rather than High. Matches the severity
assigned to SEC-000013, which has a harder-to-exploit attack path.

## Fix Plan

### Overview

Add a `filter` callback to the `unzipSync` call in `unwrapStateFromZip` that rejects any
ZIP entry whose declared `originalSize` exceeds 10 MB. The `filter` callback is invoked
by fflate before it calls `new u8(originalSize)`, so the guard fires before any large
allocation is attempted.

### Changes to `src/backup/backup.ts`

```ts
const MAX_UNCOMPRESSED_BYTES = 10 * 1024 * 1024; // 10 MB

export function unwrapStateFromZip(zipBytes: Uint8Array): AppState {
  const files = unzipSync(zipBytes, {
    filter(file) {
      if (file.originalSize > MAX_UNCOMPRESSED_BYTES) {
        throw new Error(
          `Backup file too large: entry '${file.name}' declares ${file.originalSize} bytes uncompressed (limit ${MAX_UNCOMPRESSED_BYTES})`
        );
      }
      return true;
    },
  });
  const stateBytes = files[STATE_FILENAME];
  if (!stateBytes) throw new Error(`ZIP does not contain ${STATE_FILENAME}`);
  return JSON.parse(strFromU8(stateBytes)) as AppState;
}
```

**Test name:** `'unwrapStateFromZip throws on ZIP with oversized declared originalSize (zip bomb guard)'`

**Assertion (failing before fix, passing after):**

```ts
it('unwrapStateFromZip throws rather than allocating unbounded memory for declared originalSize', async () => {
  // Build a valid ZIP with an artificially large originalSize in its central directory.
  // fflate's zipSync produces correct headers; we patch the originalSize field
  // in the central directory to 0xFFFFFFFF (max uint32 ≈ 4 GB).
  const tinyPayload = { 'state.json': strToU8('{}') };
  const realZip = zipSync(tinyPayload);

  // Patch the 'uncompressed size' field (4 bytes, little-endian) in the central directory.
  // Central directory starts at the offset stored at byte [EOCD - 6] (4 bytes, LE).
  // For a single-file ZIP from fflate the layout is predictable enough to patch.
  const patched = new Uint8Array(realZip);
  // Find the central directory file header signature 0x02014B50.
  let cdOffset = -1;
  for (let i = 0; i < patched.length - 4; i++) {
    if (patched[i] === 0x50 && patched[i+1] === 0x4b &&
        patched[i+2] === 0x01 && patched[i+3] === 0x02) {
      cdOffset = i;
      break;
    }
  }
  expect(cdOffset).toBeGreaterThan(-1);
  // Bytes [cdOffset+24..cdOffset+27] = uncompressed size (LE).
  patched[cdOffset + 24] = 0xff;
  patched[cdOffset + 25] = 0xff;
  patched[cdOffset + 26] = 0xff;
  patched[cdOffset + 27] = 0xff;

  // Before fix: throws with an OOM / range error (or crashes the process).
  // After fix: throws a controlled 'Backup file too large' error before allocating.
  expect(() => unwrapStateFromZip(patched)).toThrow(/too large/i);
});
```

The fix must use `fflate.unzipSync`'s `opts.filter` callback to reject any file whose
`originalSize` exceeds 10 MB (matching the sync-path cap) before any allocation occurs.
