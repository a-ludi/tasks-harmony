# ReDoS bypass: `isSafeRegex` heuristic misses `{min,max}` range-quantifier patterns

**Status:** DONE
**Reviewed by:** Claude (Security Reviewer), 2026-07-02
**Bug ID:** SEC-000011
**Severity:** Medium

## Location

`src/questions/validation.ts`, lines 8–26 (`isSafeRegex` heuristic)

Secondary surface: `src/questions/validation.ts`, lines 40–49 (`validateAnswer` — calls `isSafeRegex` then executes the regex)

## Description

### The vulnerability

`isSafeRegex` in `src/questions/validation.ts` uses a single regex heuristic to detect catastrophic-backtracking patterns:

```ts
const backtrackingHeuristic = /\([^)]*(?:[+*?]|[^)]*\|[^)]*)[^)]*\)[+*?]/;
```

This heuristic correctly catches patterns like `(a+)+`, `(a*)*`, `(a|a)+`, and `([a-z]+)*` — all of which have a `+` or `*` quantifier *inside* the group token sequence `[^)]*`. However, it fails to detect the class of patterns where a `{min,max}` range quantifier appears inside the group, because `{` and `}` are not matched by the character class `[+*?]`, and the alternation branch `[^)]*\|[^)]*` only catches explicit `|` separators.

**Concrete bypass examples** (confirmed exploitable, measured timings):

| Pattern | Input (n=25–28 chars + non-matching suffix) | Elapsed |
|---|---|---|
| `^(a{1,10})+$` | `'a' * 28 + 'b'` | ~1040 ms |
| `^([0-9]{1,5})+$` | `'1' * 25 + 'a'` | ~229 ms |
| `^([a-z]{1,8})*$` | `'a' * 25 + '1'` | ~304 ms |

All three patterns:
1. Pass `isSafeRegex` with `{ valid: true }` — the heuristic does not flag them.
2. Pass `new RegExp(pattern)` without a syntax error.
3. Are accepted and stored via CDP import or sync blob without any warning.
4. Cause `validateAnswer` to compile and execute the pattern against user input in the completion modal.
5. With a non-matching adversarial input, produce exponential backtracking that freezes the browser main thread for hundreds of milliseconds per attempt.

### Attack vector

Identical to SEC-000005, but bypasses the fix:

1. An attacker publishes a CDP with a chore YAML containing a `TEXT` question whose `regexPattern` is a range-quantifier pattern, e.g.:
   ```yaml
   questions:
     - id: q1
       type: TEXT
       prompt: "Enter your employee ID"
       required: true
       regexPattern: "^([0-9]{1,5})+$"
   ```
2. The victim imports the CDP. `isSafeRegex` returns `{ valid: true }`, so the pattern is stored in IndexedDB without warning.
3. When the victim opens the completion modal and types any input that does not fully match (e.g., `"12345a"`), `validateAnswer` calls `new RegExp('^([0-9]{1,5})+$').test('12345a')`, triggering ~229 ms of backtracking per keystroke. With longer inputs (~25 digits + one non-digit), the tab freezes for hundreds of milliseconds.
4. The freeze repeats every time the completion modal is opened, since the malicious pattern is stored permanently in IndexedDB.

### Why the existing fix (SEC-000005) does not cover this

SEC-000005 added the `isSafeRegex` guard inside `validateAnswer`. The guard correctly blocks `(a+)+`, `(a*)*`, etc. But the heuristic regex itself does not match `{n,m}` quantifiers: `{1,10}` does not contain `+`, `*`, or `?` as standalone chars, and `[^)]*` (the lookahead for `|`) is never satisfied. The result is that a new class of patterns slips through undetected.

### Impact

- **Browser main-thread hang / tab freeze** triggered every time a user completes a chore whose question contains a bypass pattern with a sufficiently long non-matching input.
- No authentication or server-side interaction required beyond importing a malicious CDP (a user-initiated but low-barrier action).
- Bypasses the intended ReDoS protection introduced in SEC-000005.

## Validation

**CONFIRMED — genuine, exploitable ReDoS bypass of the SEC-000005 fix.**

### 1. Does `isSafeRegex` truly miss `{n,m}` range quantifiers?

Yes. The heuristic regex is:

```
/\([^)]*(?:[+*?]|[^)]*\|[^)]*)[^)]*\)[+*?]/
```

It fires when the content inside `(...)` contains a bare `+`, `*`, or `?` character, or a `|` alternation — and the *closing* `)` is followed by `+`, `*`, or `?`. For a pattern like `^(a{1,10})+$`, the group body is `a{1,10}`. The characters `{`, `1`, `,`, `1`, `0`, `}` satisfy none of `[+*?]` and there is no `|`. The alternation branch `[^)]*\|[^)]*` also fails. The heuristic never fires; `isSafeRegex` returns `{ valid: true }`. The blind spot is real and unambiguous.

### 2. Does `^(a{1,10})+$` actually cause catastrophic backtracking in V8?

Yes. V8 uses a backtracking NFA engine (not an NFA→DFA compiler). For a string of N matching characters followed by one non-matching character, the engine must try every possible way to partition N characters across repetitions of the outer `+`, where each repetition may consume 1–10 characters. The number of such partitions (compositions of N into parts 1–10) grows exponentially — roughly by a factor of ~1.9 per additional character. When the overall match ultimately fails (due to the trailing non-matching character), all partitions are explored. This is the canonical "bounded quantifier nested inside unbounded quantifier" ReDoS class, confirmed to affect V8. The report's measured timings (229–1040 ms at N=25–28) are consistent with this exponential growth and are credible. The backtracking is real.

### 3. Does the SEC-000005 fix fully protect all paths?

No. SEC-000005 correctly inserted an `isSafeRegex` call inside `validateAnswer` (lines 41–44 of the current `validation.ts`). However, that call delegates to the *same flawed heuristic*. Every execution path that uses `isSafeRegex` inherits the same blind spot:

- `choreFormValidation.ts:29` — form UI guard, calls `isSafeRegex`
- `QuestionFormFields.tsx:34` — question editor guard, calls `isSafeRegex`
- `validateAnswer` lines 41–44 — runtime execution guard, calls `isSafeRegex`

All three pass `{n,m}` patterns without flagging them. SEC-000005 closed the "no guard at all" vulnerability but left the heuristic itself incomplete. This report describes a distinct bypass within the guard's own detection logic.

### 4. Is the attack vector still valid?

Yes. The CDP import path documented in SEC-000005 (`fetchCDP` / `parseChoreQuestions`) remains unchanged: `regexPattern` is accepted as a free string, stored in IndexedDB, and later executed by `validateAnswer`. With `{n,m}` patterns now passing `isSafeRegex`, a malicious CDP containing `regexPattern: "^([0-9]{1,5})+$"` will:

1. Pass `isSafeRegex` with `{ valid: true }` — no warning raised on import.
2. Be stored permanently in IndexedDB.
3. Trigger exponential backtracking inside `validateAnswer` every time the completion modal is opened with a sufficiently long non-matching input (~25 chars).

Attacker control is full and the barrier is identical to SEC-000005: host a YAML file in a publicly reachable CDP. No authentication or server access is required.

**Severity rationale — Medium:** The impact is a browser main-thread hang (DoS) rather than data exfiltration, RCE, or auth bypass. The victim must actively import a malicious CDP. Confidentiality and integrity are not directly affected. This matches the Medium rating assigned to SEC-000005 for the same impact class and attack vector.

## Fix Plan

### Location

`src/questions/validation.ts`, line 17.

### Current code

```ts
const backtrackingHeuristic = /\([^)]*(?:[+*?]|[^)]*\|[^)]*)[^)]*\)[+*?]/;
```

### Change required

Extend the character class `[+*?]` that detects quantifiers *inside* the group body to also match the opening `{` of a range quantifier. Change it to `[+*?{]`:

```ts
const backtrackingHeuristic = /\([^)]*(?:[+*?{]|[^)]*\|[^)]*)[^)]*\)[+*?]/;
```

This is a one-character addition (`{`) to the first character class inside the non-capturing group `(?:...)`. The outer `[+*?]` that matches the quantifier *after* the closing `)` is left unchanged — `{` is not needed there because the dangerous patterns always have a bare `+` or `*` after the outer group (e.g., `(a{1,10})+`, not `(a+){1,10}` — the latter is not ReDoS-prone in the same way).

### Why this is correct and minimal

- `{` is the only character that begins a range quantifier (`{n}`, `{n,}`, `{n,m}`).
- The heuristic fires when any of `+`, `*`, `?`, or `{` appears inside the group body AND the group itself is followed by `+`, `*`, or `?`. That is precisely the class of nested-quantifier patterns that cause catastrophic backtracking.
- No other code changes are needed. All three call sites (`choreFormValidation.ts`, `QuestionFormFields.tsx`, `validateAnswer`) call `isSafeRegex` and inherit the fix automatically.
- Do not change the outer `[+*?]` — patterns like `(a{1,10}){2,5}` (bounded outer quantifier) are not catastrophically backtracking and should remain allowed.
