# syncToken transmitted in URL path is written to nginx access logs, permanently exposing every user's sync credential to anyone with log access

**Status:** DONE
**Bug ID:** [[SEC-000028]]
**Severity:** High

## Location

- `src/sync/server.ts:44` — client puts the `syncToken` in the request URL path: `fetch(\`${SYNC_URL}/sync/${syncToken}\`, ...)`
- `sync-server/index.ts:9,20-22` — server route matches `/^\/sync\/([a-f0-9]{64})$/` and extracts the token from the path.
- `sync-server/handlers/blob.ts:21` — the token from the URL path is used as the authorisation identity: `if (storedSyncToken !== token) return 403`.
- `nginx/sync-location.conf.template:12-17` — the nginx `location ~ "^/sync/[a-f0-9]{64}$"` block proxies to the socket but declares **no `access_log off;`** directive. It also proxies without stripping the URL, so the URL (including the syncToken) is written to nginx's default `access_log`.
- `docs/DEPLOYMENT.md:63-66` — the deployment instructions configure the reverse proxy but never disable access logging for `/sync/{token}` requests, so the default combined log format (which includes `$request`, i.e. method + full URI) applies.

## Description

The `syncToken` is the long-term credential that grants read and write access to a user's encrypted backup blob on the sync server. Per the challenge/session flow in `sync-server/handlers/challenge.ts` and `sync-server/handlers/session.ts`, anyone who presents a valid-format 64-char hex `syncToken` is issued a session and can then GET or PUT `/sync/{syncToken}` (see the excluded SEC finding on HMAC being unimplemented). The `syncToken` is derived deterministically from the master AES key (`deriveSyncToken` in `src/sync/credentials.ts`) and is therefore **stable for the lifetime of that key** — it never rotates, is never revoked, and is the same on every device that imports the key.

The client sends this token in the URL path of every blob request (`GET /sync/{syncToken}` and `PUT /sync/{syncToken}`). Because it is in the request-line, it is captured by every layer that logs request lines:

1. **nginx access logs.** The default `combined` log format logs `$request`, which is `GET /sync/aaaa...aaaa HTTP/1.1`. The bundled `nginx/sync-location.conf.template` does not turn access logging off for this location, and `docs/DEPLOYMENT.md` never instructs the operator to do so. So `/var/log/nginx/access.log` on the sync host contains one full syncToken per request, per user, forever.
2. **Log aggregation / backups.** Ops teams routinely ship nginx logs to central log aggregators (Loki, ELK, Datadog, S3 archives). Anyone with read access to those systems — often a much larger blast radius than the sync host itself — obtains every user's syncToken in plaintext.
3. **Proxy / CDN logs upstream of nginx.** If the sync host sits behind Cloudflare, an ISP-run reverse proxy, or a cloud load balancer with request logging, those logs also contain the token.
4. **Browser history / referer chains.** Because the token is in the URL, it can also leak into browser history dumps if the sync URL is ever navigated to instead of fetched (less realistic here, but the industry-standard reason secrets don't go in URLs).

Anyone who obtains a leaked syncToken can:
- Immediately mint a session (`POST /sync/challenge` → `POST /sync/session`) and impersonate the victim on the sync server.
- **Overwrite the victim's encrypted backup** via `PUT /sync/{syncToken}` with arbitrary 1MB of chosen bytes, destroying the ciphertext. Because `pull()` in `src/sync/server.ts` gates re-imports on `serverTs > localTs`, the attacker can also stall future pulls or, if they can craft a valid ciphertext (they cannot without the master key), force-replace state on the victim's other devices.
- **Download and archive the ciphertext** for later offline attack. The blob is AES-256-GCM encrypted with a random 256-bit key, so this is not immediately exploitable, but it collapses the security posture from "backup is unreachable without both the sync host and the master key" to "backup is reachable by anyone with log access; only the master key stands in the way." Combined with the excluded [[SEC-000024]]#2 (master key is exportable), any subsequent XSS on any device — even years later — decrypts every archived blob.

The token also cannot be revoked. There is no server-side "invalidate this syncToken" operation; the only remediation is for the victim to generate a fresh master key (`getOrCreateSyncKey`), which discards all synced backups on the server and requires re-importing the new key on every device.

Putting long-term bearer credentials in URLs is a well-known anti-pattern (OWASP ASVS V8.3.1, "sensitive data must not be sent in the URL"). The standard fix is to move the token to the `Authorization: Bearer` header (which nginx does not log by default) and identify the blob on disk by a hash of the token or by an opaque account ID resolved after authentication. The existing session token is already sent this way — the same channel should carry the syncToken during challenge and blob requests. Alternatively, at minimum, the nginx template should ship with `access_log off;` (or `access_log /dev/null;`) inside the `location ~ "^/sync/[a-f0-9]{64}$"` block **and** the `/sync/challenge` and `/sync/session` blocks (whose POST bodies contain the token — nginx doesn't log bodies by default, but any request-body-logging middleware would capture them).

## Validation

**CONFIRMED — High severity.**

All claims verified against source code:

1. **Reachability confirmed.** `src/sync/server.ts:44` places the `syncToken` directly in the URL path (`/sync/${syncToken}`) for every GET and PUT request. `nginx/sync-location.conf.template:12-17` has no `access_log off;` directive in the matching `location ~ "^/sync/[a-f0-9]{64}$"` block. nginx's default `combined` log format records `$request`, which includes the full URI. The token is therefore logged on every sync operation with no operator instruction to suppress it.

2. **Attacker control confirmed.** Any actor with read access to nginx access logs — sysadmins, ops staff with log aggregator access (Loki, ELK, Datadog, S3 archives), CDN/cloud-LB operators, or anyone who gains read access to `/var/log/nginx/access.log` — obtains valid syncTokens in plaintext.

3. **Real-world impact confirmed.** The `syncToken` is derived deterministically from the AES-256 master key via SHA-256 (`credentials.ts:17-23`) and never rotates. It serves as the effective long-term bearer credential: `sync-server/handlers/blob.ts:21` compares the URL-extracted token against the session-resolved token to authorise GET/PUT. A stolen token allows immediate session minting (challenge → session flow) and full read/write access to the victim's encrypted blob. Blob overwrite destroys backup data; blob download enables offline ciphertext archiving for future attack if the master key is later compromised. Revocation requires generating a new master key and re-importing on all devices — a disruptive, non-transparent remediation.

4. **Severity rationale — High (not Critical).** The attack requires log access on the sync host or an upstream system, meaning it is not directly exploitable by an unauthenticated remote attacker with no foothold. The encrypted blob itself remains protected by the AES-256 master key (which is not exposed by this finding alone). However, the blast radius is wide (every sync user, every operation, permanently archived in logs), the credential is non-revocable, and the fix is straightforward (move token to `Authorization` header; add `access_log off;` to the nginx location block). These factors place it firmly at High.

## Fix Plan

### Chosen approach: Option (a) — Suppress nginx access logging for token-carrying locations, and document the invariant

**Why (a) over (b) and (c):**

- **Option (b) — move syncToken to `Authorization` header** would close the log-exposure path most thoroughly but requires a coordinated client + server + on-disk-storage change: the blob handler currently authenticates by comparing `URL-path token` against `session-stored token` (`sync-server/handlers/blob.ts:21`), and blobs are stored on disk keyed by the syncToken (`join(BLOB_DIR, \`${token}.enc\`)`). Moving the token off the URL means introducing an opaque blob identifier or an on-disk hash-derived filename, updating the blob handler to read the token from either the `Authorization` header (currently occupied by the *session* token) or a new custom header, updating the client, and migrating existing blobs. That is a much larger surface than a security fix should introduce in one step, and it invalidates the existing [[SEC-000007]] architecture that (correctly) treats the session-token check and the URL-path-token check as two independent gates. High blast-radius change; disproportionate to the minimum-viable fix.

- **Option (c) — hash the token in the URL** merely renames the secret. `SHA-256(syncToken)` becomes an equivalent bearer credential on the server (server would have to compare submitted-hash against stored-hash, so the hash IS the credential). It buys nothing over the raw token from a leak-analysis standpoint: a hash in nginx logs still lets an attacker impersonate. This is theatre.

- **Option (a) — `access_log off;` on the location that carries the token in the URL** eliminates the actual leak vector called out by the report (nginx access logs on the sync host, which is by far the most common and highest-blast-radius log surface). It leaves upstream-proxy logs as a residual risk that must be documented — but any operator who fronts the sync host with a CDN/LB is already responsible for their own log hygiene, and this is standard OWASP guidance ("if you must put a secret in a URL, at minimum suppress access logging on that path"). Two-line change to `nginx/sync-location.conf.template`, mirrored comment in `docs/DEPLOYMENT.md`.

The report itself explicitly names option (a) as an acceptable "at minimum" fix; [[SEC-000007]] previously accepted the log-exposure risk as residual under Medium severity, but this finding correctly re-raises it to High because of the wide blast radius via log aggregation. Suppressing the log entirely on the token-carrying location is the smallest change that turns the finding from a real leak into a documented, operator-managed residual risk.

### What changes

**1. `nginx/sync-location.conf.template`** — add `access_log off;` inside the `location ~ "^/sync/[a-f0-9]{64}$"` block (the only location whose URL path contains the syncToken). The `/sync/challenge` and `/sync/session` locations receive the token in POST bodies; nginx does not log bodies by default, so those locations do not need `access_log off;` — but we will document that operators must not enable request-body logging on the sync locations.

**2. `docs/DEPLOYMENT.md`** — add a brief "Log hygiene" subsection under the nginx setup section, explaining:
- The token-carrying location has `access_log off;` baked in and MUST NOT be removed.
- Operators fronting the sync host with an upstream proxy (CDN, cloud LB, ISP proxy) must either disable request-line logging for `/sync/*` on that upstream OR accept that the syncToken will be logged there.
- Do not enable request-body logging (e.g. via any body-logging module) on the sync locations.

**Files to touch:**
- `nginx/sync-location.conf.template` — add `access_log off;` to the `location ~ "^/sync/[a-f0-9]{64}$"` block
- `sync-server/nginx-config.test.ts` — add the failing test described below
- `docs/DEPLOYMENT.md` — add the "Log hygiene" subsection

### Test Plan

**File:** `sync-server/nginx-config.test.ts`

**Test name:** `'suppresses access logging inside the syncToken-carrying location block to prevent token leakage into nginx access logs'`

**How the test works:**

The existing test file already reads `nginx/sync-location.conf.template` into a `config` string and asserts structural properties of specific location blocks. The new test extracts the body of the `location ~ "^/sync/[a-f0-9]{64}$"` block (using the same regex style as the existing `sessionBlockMatch` / `catchallMatch` tests) and asserts that it contains `access_log off;`.

```ts
it('suppresses access logging inside the syncToken-carrying location block to prevent token leakage into nginx access logs', () => {
  // The block matched by 'location ~ "^/sync/[a-f0-9]{64}$"' carries the syncToken
  // verbatim in the URL path. Without 'access_log off;' inside this block, nginx's
  // default combined log format writes the full URL (including the token) to
  // /var/log/nginx/access.log on every GET/PUT. See SEC-000028.
  const tokenBlockMatch = config.match(
    /location ~ "\^\/sync\/\[a-f0-9\]\{64\}\$" \{[^}]+\}/s,
  );
  expect(tokenBlockMatch).not.toBeNull();
  expect(tokenBlockMatch![0]).toContain('access_log off;');
});
```

**Assertion that FAILS before the fix:** `expect(tokenBlockMatch![0]).toContain('access_log off;')` — the current block contains only `limit_req`, `client_max_body_size`, `proxy_pass`, and `proxy_http_version`. The `toContain('access_log off;')` assertion fails.

**Assertion that PASSES after the fix:** After adding `access_log off;` to the block, the substring is present and the assertion passes.

The existing `nginx-config.test.ts` suite continues to pass — the added directive does not affect any other structural check (rate limit zones, block ordering, etc.).
